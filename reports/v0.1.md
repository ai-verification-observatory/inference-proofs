# Benchmark release v0.1: report (draft, release candidate)

This is the draft report of the v0.1 release candidate, open for review from 2026-11-06 to 2026-11-20 ([RFC-0009 §Review window](../rfcs/0009-results-and-publication.md#review-window)). Every number is copied from [`releases/v0.1/index.json`](../releases/v0.1/index.json) with its unit, scope, grade and tier; the report computes none. Rows are listed alphabetically.

## What changed since the last release

This is the first release. Systems, workloads and pins:

- Reference systems `ref-serve` and `ref-recompute` (RFC-0015, vLLM v0.32.0), images pinned in their `system.yaml`. On the two SASH workloads they serve FP8 W8A8 in place of INT8 W8A8, a declared substitution (RFC-0015 PM-4): every quantity of those rows carries `precision_substituted`.
- Proving systems `sash` (SASH zk-inference-prover at `eb95bfa`) and `flashprove` (FlashProve at `9e2bdd8`), with unreviewed claim cards. No system maintainer is named for either: the teams have not been reached (RFC-0001 §System inclusion).
- Workloads `sash-l31-8b-c4096`, `sash-l31-8b-c1024`, `fp-maverick-w1024-b1`, `fp-maverick-w1024-b24` (RFC-0003).
- Every run in this release is on the profile `prover-h100-hosted` ([RFC-0006 §Hosted execution](../rfcs/0006-reference-hardware-and-cost.md#hosted-execution)): a provider-started container on one H100 SXM, driver 610.57.04, with a passing hosted calibration self-test (RFC-0011). Its network is not isolated and its CPUs are shared under a quota, so these rows are their own configurations.

## What failed

- `ref-serve` on `fp-maverick-w1024-b1` and `fp-maverick-w1024-b24` (GH-REF-MAVERICK-ATTEMPT, NM-1): both runs failed at `prove`, kind `adapter`, exit 1. vLLM v0.32.0 rejects the `UD-Q4_K_XL` GGUF folder: "Unrecognized model in .../UD-Q4_K_XL. Should have a `model_type` key in its config.json." There is therefore no reference row for the FlashProve workloads in v0.1.
- `ref-serve` on the Maverick workloads: there is therefore no completed reference row to set beside FlashProve's.
- `sash` on `sash-l31-8b-c1024`: the one self-tested run failed at `verify`, kind `timeout`, "verify exceeded 3600.0 s", the default limit (RFC-0005). `systems/sash/system.yaml` now declares 21,600 s. SASH has no row in this candidate.
- Earlier runs on `main` that predate the hosted self-test, or failed before a step for reasons since fixed (a relative path, a refused configuration), are recorded as such and are not part of the release.

## What the numbers do not show

- FlashProve has rows on both workloads; `fp-maverick-w1024-b24` has one run, below the three-repetition minimum, and is marked so. SASH has no row: its one self-tested run failed at verify; a run with the declared verify limit is pending. Each configuration's archived proof is in the public dataset `abdelstark/inference-proofs-archive` (RFC-0009 Q1).
- The reference rows time vLLM's engine start inside `prove.session`, from a cold cache in every run.
- `ref-recompute` here replays `ref-serve`'s own claims: its agreement counts compare vLLM's serving path with a teacher-forced pass of the same engine, not a prover's claims.
- Hosted-profile risks (RFC-0006): shared CPUs and an open network make these timings weaker evidence than a dedicated docker host would give.
- Open RISKs in the RFCs apply unchanged, among them RFC-0006's emulated verifier host (#79, not run).
