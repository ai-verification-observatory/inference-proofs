# SASH zk-inference-prover

Adapter for [`sg-ai-safety-hub/zk-inference-prover`](https://github.com/sg-ai-safety-hub/zk-inference-prover) (RFC-0005). Level 1 v1.0 runs commit `4f41667`, the head of pull request #36 (see below), and both the claim card and properties file are evaluated at that commit. This page documents the subcommand mapping (RFC-0005 README requirements 1 to 4, 6, and 7) along with how SASH structures its proof grid and how the benchmark accounts for it. The technical sections below were authored against upstream commit `eb95bfa887299d1637550228d42086c27cbb2b3b` and the companion results repository `sg-ai-safety-hub/zk-inference-results` at `11decec3c0b62c707618aab5deb82750b355d202`. Wherever upstream documentation is silent, this page explicitly marks it "not stated" (AGENTS.md rule 9).

**Level 1 v1.0 pin (2026-11-12).** The adapter is pinned at `4f41667297430a598165c4a8604258fe37d952ae`, the head of [pull request #36](https://github.com/sg-ai-safety-hub/zk-inference-prover/pull/36) (not yet merged upstream). Upstream `eb95bfa` rejects one Level 1 prompt during witness extraction (a table-of-contents prompt whose attention output overflows the no-wrap window by one bit), and PR #36 adds the product form needed to compose it. This pull request was authored by this project's owner. All three Level 1 v1.0 sessions run this commit, and both `claim.yaml` and `properties.yaml` reflect it; once upstream merges a fix, future releases will move to an upstream commit. Note that the v1.0 SASH manifests record `system.upstream.repo` as `sg-ai-safety-hub/zk-inference-prover` and `runner.affiliated_systems` as `[]` even though the PR was written by the benchmark operator (RFC-0014 §Manifest). Because run records are append-only and digest-verified, those manifests remain untouched; any SASH session run after 2026-11-15 declares `affiliated_systems: ["sash"]` ([`sash-slot2-rerun.md`](../../docs/runbooks/sash-slot2-rerun.md)).

See [`claim.yaml`](claim.yaml) (RFC-0002) for the exact statement established by an accepted proof, its assumptions, and its bound edges.

## Grid geometry and proof release

### What one proof is

- A single segment represents "one transformer layer applied to one block of `S` token positions with a context of `C` earlier positions, or the language-model head applied to one block. A sequence is proved as a grid of such segments, and `boundary-grid` checks that the segments fit together" ([statement.md](https://github.com/sg-ai-safety-hub/zk-inference-prover/blob/eb95bfa887299d1637550228d42086c27cbb2b3b/docs/statement.md#L3-L6)). Upstream notes that "Every recorded run has `S = 512`" ([GLOSSARY.md](https://github.com/sg-ai-safety-hub/zk-inference-prover/blob/eb95bfa887299d1637550228d42086c27cbb2b3b/GLOSSARY.md#L7-L9)).
- Each block's context must be an exact multiple of `S`: `boundary-grid` rejects any `C` not divisible by `S` ([boundary.rs](https://github.com/sg-ai-safety-hub/zk-inference-prover/blob/eb95bfa887299d1637550228d42086c27cbb2b3b/prover/src/boundary.rs#L1285-L1305)), and the witness extractor refuses ragged trailing blocks ([extract.py](https://github.com/sg-ai-safety-hub/zk-inference-prover/blob/eb95bfa887299d1637550228d42086c27cbb2b3b/harness/witness/extract.py#L715-L721)).
- The language-model head is proved over both the final prompt block and the generated block ([decision of 2026-09-08](https://github.com/sg-ai-safety-hub/zk-inference-prover/blob/eb95bfa887299d1637550228d42086c27cbb2b3b/docs/decisions/2026-09-08-the-head-is-proved-over-the-last-prompt-block.md#L5-L11), [plan.py](https://github.com/sg-ai-safety-hub/zk-inference-prover/blob/eb95bfa887299d1637550228d42086c27cbb2b3b/harness/witness/plan.py#L230-L238)).
- Prompt and continuation blocks are proved uniformly ("the loop already proves a prompt chunk as readily as a decode one", [chunks.rs](https://github.com/sg-ai-safety-hub/zk-inference-prover/blob/eb95bfa887299d1637550228d42086c27cbb2b3b/prover/src/chunks.rs#L63-L70)). `boundary-grid` checks every prompt token ID against the supplied prompt and every generated token ID against the previous position's proved argmax ([boundary.rs](https://github.com/sg-ai-safety-hub/zk-inference-prover/blob/eb95bfa887299d1637550228d42086c27cbb2b3b/prover/src/boundary.rs#L1148-L1156)). The README's earlier phrasing ("a STARK prover for the decode step", [README.md](https://github.com/sg-ai-safety-hub/zk-inference-prover/blob/eb95bfa887299d1637550228d42086c27cbb2b3b/README.md#L3-L4)) predates this capability.

### The two v0.1 shapes

| Workload shape | Upstream geometry |
|---|---|
| 4,096 prompt + 512 continuation positions | Recorded upstream: `"context": 4096, "s": 512, "positions": 4608, "blocks": 9, "layers": 32, "segments": 290, "head_blocks": "7,8"` ([headline run config](https://github.com/sg-ai-safety-hub/zk-inference-results/blob/11decec3c0b62c707618aab5deb82750b355d202/runs/2026-09-09-headline-c4096-h100/config.json#L1-L7)); "a grid of 290 segments over 32 layers" ([decision of 2026-09-09](https://github.com/sg-ai-safety-hub/zk-inference-prover/blob/eb95bfa887299d1637550228d42086c27cbb2b3b/docs/decisions/2026-09-09-the-verifier-derives-the-shape-root.md#L37-L40)). 9 blocks × 32 layers + 2 head segments = 290. |
| 1,024 prompt + 64 continuation positions | Not stated: upstream has no run, plan, or driver at this shape. Every recorded run sets the continuation to one block of size `S`; applying `S = 64` gives 17 blocks and 546 segments by arithmetic, though upstream does not explicitly document it. |

### When proofs are written

- `compose-chunks --ser-dir` writes each segment's three files (`<tag>.fixed.json`, `<tag>.claims.json`, `<tag>.proof.json`) immediately after proving that segment ([chunks.rs](https://github.com/sg-ai-safety-hub/zk-inference-prover/blob/eb95bfa887299d1637550228d42086c27cbb2b3b/prover/src/chunks.rs#L570-L575), [cli.rs](https://github.com/sg-ai-safety-hub/zk-inference-prover/blob/eb95bfa887299d1637550228d42086c27cbb2b3b/prover/src/cli.rs#L1484-L1500)).
- Verification occurs only after the entire proving loop finishes: "**Nothing is proved until everything is.** `rows` holds every chunk's `Composed` *and* its serialized bytes until the loop is over, because the verifier runs afterwards on purpose" ([chunks.rs](https://github.com/sg-ai-safety-hub/zk-inference-prover/blob/eb95bfa887299d1637550228d42086c27cbb2b3b/prover/src/chunks.rs#L73-L79)).
- `boundary-grid --verify --prompt` loads every segment's serialized files, verifies each proof, derives every shape root from the published calibration, and validates all layer links, token links, and token IDs ([boundary.rs](https://github.com/sg-ai-safety-hub/zk-inference-prover/blob/eb95bfa887299d1637550228d42086c27cbb2b3b/prover/src/boundary.rs#L1489-L1531), [#L1445-L1477](https://github.com/sg-ai-safety-hub/zk-inference-prover/blob/eb95bfa887299d1637550228d42086c27cbb2b3b/prover/src/boundary.rs#L1445-L1477)). It exits 0 only if every check passes and 1 otherwise ([boundary.rs](https://github.com/sg-ai-safety-hub/zk-inference-prover/blob/eb95bfa887299d1637550228d42086c27cbb2b3b/prover/src/boundary.rs#L1120-L1124)).

## Subcommand mapping

Upstream does not ship a single monolithic CLI command that takes a model and prompt and produces a proved grid. Instead, its recorded H100 runs are driven by [`sequence-job.sh`](https://github.com/sg-ai-safety-hub/zk-inference-results/blob/11decec3c0b62c707618aab5deb82750b355d202/tools/drivers/lib/sequence-job.sh) (configured by [`headline-c4096.sh`](https://github.com/sg-ai-safety-hub/zk-inference-results/blob/11decec3c0b62c707618aab5deb82750b355d202/tools/drivers/headline-c4096.sh#L44-L93)), and commitments are built by [`model-commitment.sh`](https://github.com/sg-ai-safety-hub/zk-inference-results/blob/11decec3c0b62c707618aab5deb82750b355d202/tools/drivers/model-commitment.sh#L137-L144). This adapter executes the exact same sequence of commands and flags. Every Python step runs as upstream invokes it: `uv run --project /src/harness --no-group cpu --group cuda python ...` ([driver.sh](https://github.com/sg-ai-safety-hub/zk-inference-results/blob/11decec3c0b62c707618aab5deb82750b355d202/tools/drivers/lib/driver.sh#L264-L280)) with `ZK_MODEL=/models ZK_DEVICE=cuda ZK_THREADS=<n> ZK_OUT=/io/state/zk-out` ([common.py](https://github.com/sg-ai-safety-hub/zk-inference-prover/blob/eb95bfa887299d1637550228d42086c27cbb2b3b/harness/witness/common.py#L12-L18)).

All flags match `headline-c4096.sh` verbatim: quantization spec `y-delay-vw12`; shared flags `--round even --numbits 9 --z-hi-bits 7 --variants intexp --head-groups 16,8,8 --tight-table`; layer flags `--round even --diagonal-block` plus the five reductions (`--gkr-key-tiles --gkr-dequant --gkr-residual-stream --gkr-freivalds --gkr-attnout`); head flags with those five reductions; head dump at layer 16 over the final prompt block and generated block; 64 segments per proving process; and `ZK_PIPELINE=1`. No skip flags are passed in measured runs. Block length `S` is set to the workload's output token count so the continuation occupies one block, matching upstream runs.

### `verify`

Runs `zk-prover-simd boundary-grid --dir <proof_dir> --plan <proof_dir>/plan.txt --expect-layer-links N --expect-token-links M --verify --prompt prompt.json --verify-calibration model-roots.json --expect-model-roots model-roots.json`, combining the recorded grid check ([sequence-job.sh](https://github.com/sg-ai-safety-hub/zk-inference-results/blob/11decec3c0b62c707618aab5deb82750b355d202/tools/drivers/lib/sequence-job.sh#L404-L414)) with the commitment verification from `model-commitment.sh` ([model-commitment.sh](https://github.com/sg-ai-safety-hub/zk-inference-results/blob/11decec3c0b62c707618aab5deb82750b355d202/tools/drivers/model-commitment.sh#L199-L220)). `--verify-calibration` is mandatory alongside `--verify` ([boundary.rs](https://github.com/sg-ai-safety-hub/zk-inference-prover/blob/eb95bfa887299d1637550228d42086c27cbb2b3b/prover/src/boundary.rs#L1205-L1220), [prover/README.md](https://github.com/sg-ai-safety-hub/zk-inference-prover/blob/eb95bfa887299d1637550228d42086c27cbb2b3b/prover/README.md#L32-L59)). Expected link counts come from the commit record rather than the proof (`B * (32 - 1) + 2` layer links and `(B - 1) * 32` token links, [headline-c4096.sh](https://github.com/sg-ai-safety-hub/zk-inference-results/blob/11decec3c0b62c707618aab5deb82750b355d202/tools/drivers/headline-c4096.sh#L106-L114)), ensuring omitted segments fail verification. `prompt.json` contains `{"ids": request}`. Verification executes on CPU via the SIMD backend without weight access, matching upstream.

Because `boundary-grid` checks generated IDs against proved head argmaxes without taking `claimed_output` as input, the adapter cross-checks `claimed_output` against `tok_in` in the reply block's layer-0 statement (`B<B-1>L0.fixed.json`, which `verify_composed` binds to its proof, [boundary.rs](https://github.com/sg-ai-safety-hub/zk-inference-prover/blob/eb95bfa887299d1637550228d42086c27cbb2b3b/prover/src/boundary.rs#L1148-L1156)) and logs any mismatch under `warnings`. That warning never overrides the verdict, which belongs solely to `boundary-grid` (RFC-0018 AD-6); C1 delivers mutated replies via `mutate_reply` (see §Level 1).

## Verdict mapping

Upstream defines `boundary-grid` as returning "exit status 0 only when every implied link ran and chained on its own axis, every tag sits where its statement says it sits, every position's id is the prompt's or the previous position's proved argmax, the pinned counts (if given) are met, and -- under `--verify` -- every chunk proof verifies; 1 otherwise, after the JSON is written" ([boundary.rs](https://github.com/sg-ai-safety-hub/zk-inference-prover/blob/eb95bfa887299d1637550228d42086c27cbb2b3b/prover/src/boundary.rs#L1102-L1124)). The adapter parses `result.verified`, `result.tokens`, `result.all_chain`, and `result.failures` from that JSON output:

| Upstream signal | Verdict |
|---|---|
| Exit 0; `verified.run > 0`, `verified.accepted == verified.run`, `verified.all`, `tokens.all`, and `all_chain` all true | `accept` |
| Exit 1 and `verified.accepted < verified.run` (at least one segment proof rejected) | `reject` |
| Exit 1 and `all_chain` false, `tokens.all` false, or `failures` non-empty (grid validation failed) | `reject` |
| Anything else: missing JSON (panic exit 101 or refused exit 1 without JSON), JSON contradicting exit code, zero segments verified, or unreadable statement | `no_verdict` |

`raw_exit_code` records `boundary-grid`'s exit status, and `raw_last_line` captures the last non-empty stderr line (or stdout if stderr is empty), truncated to 4,096 bytes. `invalid_call` is never returned because upstream has no distinct exit code for malformed proofs. If the verifier files' combined hash does not match `commitment_id`, `verify` exits non-zero before invoking `boundary-grid`.

| `commitment_id` | `sha256:` over `<file name>\t<sha256>` lines for the two verifier files, sorted by filename. Whereas upstream's own digest hashes only layer, model root, and model hash ([model-commitment.sh](https://github.com/sg-ai-safety-hub/zk-inference-results/blob/11decec3c0b62c707618aab5deb82750b355d202/tools/drivers/model-commitment.sh#L158-L176)), the adapter hashes the complete files because the calibration rows also determine derived shape roots. |
| `prover_files` | `/io/state/zk-out/attn_ranges.json` (attention calibration used by the extractor to quantize K, V, and Q, [extract.py](https://github.com/sg-ai-safety-hub/zk-inference-prover/blob/eb95bfa887299d1637550228d42086c27cbb2b3b/harness/witness/extract.py#L636-L642), [ppl.py](https://github.com/sg-ai-safety-hub/zk-inference-prover/blob/eb95bfa887299d1637550228d42086c27cbb2b3b/harness/witness/ppl.py#L26)) and `/io/state/zk-out/tokens.npz` (containing the `calib` slice used to compute it, [common.py](https://github.com/sg-ai-safety-hub/zk-inference-prover/blob/eb95bfa887299d1637550228d42086c27cbb2b3b/harness/witness/common.py#L280-L291)). |

Each row of `model-roots.json` also carries a `source` label, the witness directory `model-roots` read ([layer.rs](https://github.com/sg-ai-safety-hub/zk-inference-prover/blob/4f41667297430a598165c4a8604258fe37d952ae/prover/src/layer.rs#L692)). When `/io` is mapped to a host directory, as on a hosted runner, that label would hold the run's own directory, and the file and its commitment id would change with the place a run happens in. `commit` writes the label as the container path (`/io/state/commit-witness/...`), as a run in the image does, so the same model, shape and pin give the same id anywhere. No verifier reads `source`: rows are matched by layer and `c` and compared on their roots and calibration ([boundary.rs](https://github.com/sg-ai-safety-hub/zk-inference-prover/blob/4f41667297430a598165c4a8604258fe37d952ae/prover/src/boundary.rs#L1700-L1770)). Runs made before this change carry the host path, so their ids differ from later ones though every root is equal.

Upstream explains that calibration is "a property of the weights and the quantization variant and not of the prover", that a model root "is keyed by the layer alone and is a function of the model", and that a shape-root row applies only to the specific plan it was derived over ([driver.sh](https://github.com/sg-ai-safety-hub/zk-inference-results/blob/11decec3c0b62c707618aab5deb82750b355d202/tools/drivers/lib/driver.sh#L143-L150), [#L207-L213](https://github.com/sg-ai-safety-hub/zk-inference-results/blob/11decec3c0b62c707618aab5deb82750b355d202/tools/drivers/lib/driver.sh#L207-L213)). Accordingly, `commit` derives the commitment once over upstream's corpus and `verify` checks arbitrary prompt grids via `--expect-model-roots` and `--verify-calibration` (omitting `--expect-pre-roots`). Upstream also notes: "The commitment is a function of the weights as this harness loads and quantizes them. Nothing here compares those weights against a published checkpoint" ([REPRODUCE.md](https://github.com/sg-ai-safety-hub/zk-inference-results/blob/11decec3c0b62c707618aab5deb82750b355d202/REPRODUCE.md#L1449-L1452)); the benchmark's model digest (RFC-0014) supplies that verification.

## Kernels

The CUDA backend proves a segment only through device kernels generated for its shape and compiled in. The adapter keeps one kernel store, `/io/state/build/gen`, which both emitters extend: a shape already stored is carried forward and a new one is added ([cudagen.rs](https://github.com/sg-ai-safety-hub/zk-inference-prover/blob/4f41667297430a598165c4a8604258fe37d952ae/prover/src/cudagen.rs#L2549-L2577), [#L3476-L3520](https://github.com/sg-ai-safety-hub/zk-inference-prover/blob/4f41667297430a598165c4a8604258fe37d952ae/prover/src/cudagen.rs#L3476-L3520)).

**What v1.0 did.** `prove` emitted and rebuilt the CUDA backend for every reply. The skip meant to stop that never fired, because its key hashed the emission lines and those name the reply's own witness directory, so a reply rebuilt even when its emission added no kernel to the store.

**`commit`.** Before the commitment sequence's witness is deleted, `commit` emits into the store, from that witness:

- (a) the lines a reply's emission would run on that sequence's plan: `emit.txt` and every head line ([sequence-job.sh](https://github.com/sg-ai-safety-hub/zk-inference-results/blob/11decec3c0b62c707618aab5deb82750b355d202/tools/drivers/lib/sequence-job.sh#L309-L357)). The commitment sequence has the request's geometry, so this gives the kernels fixed by the model and the geometry;
- (b) every other line of the same plan. `plan.py` keys a line by its prefix, table width, head, flags and the attention output's form ([plan.py](https://github.com/sg-ai-safety-hub/zk-inference-prover/blob/4f41667297430a598165c4a8604258fe37d952ae/harness/witness/plan.py#L415-L418), [#L446](https://github.com/sg-ai-safety-hub/zk-inference-prover/blob/4f41667297430a598165c4a8604258fe37d952ae/harness/witness/plan.py#L446), [#L507-L509](https://github.com/sg-ai-safety-hub/zk-inference-prover/blob/4f41667297430a598165c4a8604258fe37d952ae/harness/witness/plan.py#L507-L509)), not by its limb widths, so a segment whose attention-output limbs differ from its key's first line gets its kernels only from its own line;
- (c) the lines of (a) again with each of the two pins `sequence-job.sh` passes widened one step at a time above the pin the line is emitted at: `--ao-rem-bits` up to 20 and `--fold-rem-bits` up to 19.

Then the two families whose shapes depend on the data, over their bound (see what a reply can need, below):

- (d) the attention output's constraint kernels in the magnitude form and in the product form at each low limb 4 to 16: one `cudaemit` per form with `--ao-acc-mag`, or `--ao-acc-prod --ao-acc-lo-bits L`, on the first commitment line that admits it, layer lines before head lines. `params_of` sizes the high limb to the line's own accumulator ([cli.rs](https://github.com/sg-ai-safety-hub/zk-inference-prover/blob/4f41667297430a598165c4a8604258fe37d952ae/prover/src/cli.rs#L1274-L1303)). `cudaemit --params FILE` would read a statement a proof left ([cli.rs](https://github.com/sg-ai-safety-hub/zk-inference-prover/blob/4f41667297430a598165c4a8604258fe37d952ae/prover/src/cli.rs#L1101-L1124)); `commit` proves nothing, so it passes the flags on the line instead, which give the same `Params` edit;
- (e) the attention output's generation shapes: one `genemit --families zk_attn_out_eval` per point `(form, lo, hi, rem, denp2)` that `params_of`'s choice gives over accumulator widths 1 to 26 bits, high exponents 4 to 30 and divisor ranges 10 to 20 (494 points), each passed with its own limbs as `--ao-acc-lo-bits`, `--ao-acc-hi-bits`, `--ao-rem-bits` and, where the point has them, `--ao-acc-mag`, `--ao-acc-prod`, `--ao-denp2`. It lowers `genemit`'s synthetic segment, which it builds when no `--witness` is given ([cli.rs](https://github.com/sg-ai-safety-hub/zk-inference-prover/blob/4f41667297430a598165c4a8604258fe37d952ae/prover/src/cli.rs#L1050-L1080)), as upstream's [synthetic-digests.sh](https://github.com/sg-ai-safety-hub/zk-inference-results/blob/11decec3c0b62c707618aab5deb82750b355d202/tools/drivers/synthetic-digests.sh#L116-L125) emits kernels with no witness. Its arguments are `SYNTH` in the entrypoint: the request's rounding and variants, a 32-token segment, `--layout zfold`, `--synth-ao-bits 12`, the 8B extraction's attention-output width ("a real dump declares its width in the manifest, a synthetic one takes it here", [cli.rs](https://github.com/sg-ai-safety-hub/zk-inference-prover/blob/4f41667297430a598165c4a8604258fe37d952ae/prover/src/cli.rs#L1055-L1059)), and `--numbits 1`. Each override must clear the segment's own value ([cli.rs](https://github.com/sg-ai-safety-hub/zk-inference-prover/blob/4f41667297430a598165c4a8604258fe37d952ae/prover/src/cli.rs#L1298-L1299), [#L1317-L1320](https://github.com/sg-ai-safety-hub/zk-inference-prover/blob/4f41667297430a598165c4a8604258fe37d952ae/prover/src/cli.rs#L1317-L1320)); at `--numbits 1` the segment's nmax is 1 ([#L148](https://github.com/sg-ai-safety-hub/zk-inference-prover/blob/4f41667297430a598165c4a8604258fe37d952ae/prover/src/cli.rs#L148)), so its own accumulator (at most 8 bits) and divisor range lie below every point, and all 494 are admitted;
- (f) the fold's generation shapes: one `genemit --families zk_dequant_eval --deq-per-row P --fold-rem-bits F` for each F of 1 to 19 and each per-row target P the commitment's lines pass: 16 on a layer line, which names none ([cli.rs](https://github.com/sg-ai-safety-hub/zk-inference-prover/blob/4f41667297430a598165c4a8604258fe37d952ae/prover/src/cli.rs#L1351)), and 501 on a head line ([plan.py](https://github.com/sg-ai-safety-hub/zk-inference-prover/blob/4f41667297430a598165c4a8604258fe37d952ae/harness/witness/plan.py#L209)). The v fold's shape has 16 slots on a layer line and 512 on a head line, and both read the same `--fold-rem-bits`, so each layout has the five remainder classes (generic, 7, 11, 13, 16; [dequant/mod.rs](https://github.com/sg-ai-safety-hub/zk-inference-prover/blob/4f41667297430a598165c4a8604258fe37d952ae/prover/src/gadgets/dequant/mod.rs#L269-L284)). It reads a model-only dump the adapter writes from constants (`fold_dump` in the entrypoint: 16 heads of 32, 32 tokens, seven 512 by 512 matrices of zero int8 weights, v as the fold and the six others as chains, as an 8B statement has them; about 1.8 MB, removed once emitted), through `--witness DUMP --weights-only --params DUMP/params.json`, the model-only load `expect-root` uses ([cli.rs](https://github.com/sg-ai-safety-hub/zk-inference-prover/blob/4f41667297430a598165c4a8604258fe37d952ae/prover/src/cli.rs#L981-L1037), [layer.rs](https://github.com/sg-ai-safety-hub/zk-inference-prover/blob/4f41667297430a598165c4a8604258fe37d952ae/prover/src/layer.rs#L735-L935)). That load stands in a token scale exponent of 127 ([layer.rs](https://github.com/sg-ai-safety-hub/zk-inference-prover/blob/4f41667297430a598165c4a8604258fe37d952ae/prover/src/layer.rs#L858)), and the dump's v exponents set the channel side, so the remainder `params_of` sees is `max(G_t + G_c) - 13` with `G_t = 7` and `G_c = 7` ([layer.rs](https://github.com/sg-ai-safety-hub/zk-inference-prover/blob/4f41667297430a598165c4a8604258fe37d952ae/prover/src/layer.rs#L1199-L1225), [dequant/trace.rs](https://github.com/sg-ai-safety-hub/zk-inference-prover/blob/4f41667297430a598165c4a8604258fe37d952ae/prover/src/gadgets/dequant/trace.rs#L53-L57)): its own remainder is 1 and every F of 1 to 19 is admitted. The synthetic segment's own remainder is 13 or more ([cli.rs](https://github.com/sg-ai-safety-hub/zk-inference-prover/blob/4f41667297430a598165c4a8604258fe37d952ae/prover/src/cli.rs#L1374-L1381)), so it cannot give the classes 7 and 11. No prompt, corpus text or model value is in the dump.

Only the named family is stored from either input ([cudagen.rs](https://github.com/sg-ai-safety-hub/zk-inference-prover/blob/4f41667297430a598165c4a8604258fe37d952ae/prover/src/cudagen.rs#L3518-L3520)), and the store's other families are carried forward whatever `--families` says ([#L3486-L3491](https://github.com/sg-ai-safety-hub/zk-inference-prover/blob/4f41667297430a598165c4a8604258fe37d952ae/prover/src/cudagen.rs#L3486-L3491)). A point an emitter refuses is recorded with the prover's own message and adds nothing; on the CPU build none is refused.

**Why these inputs give a reply's kernels.** `genemit` reads its input only through `params_of`: the kernel it lowers is `build_components(Plan::new(params))` with drawn relations and placeholder claims ([cudagen.rs](https://github.com/sg-ai-safety-hub/zk-inference-prover/blob/4f41667297430a598165c4a8604258fe37d952ae/prover/src/cudagen.rs#L3427-L3475)). A shape is identified by `Ir::fingerprint`, which hashes the operations with their constants, the widths, the constraints, the lookups and the scalar slots, and not the table sizes or the scalar values, which are passed at run time ([cudagen.rs](https://github.com/sg-ai-safety-hub/zk-inference-prover/blob/4f41667297430a598165c4a8604258fe37d952ae/prover/src/cudagen.rs#L1576-L1613)). So a segment of other dimensions gives a reply's attention-output or fold kernel when its `Params` agree on what the fingerprint hashes. Checked on the pinned commit built for CPU: every shape the CPU emission shares with the final stores of sessions 2 and 3 (74 and 73) has a byte-identical source block in the store's `.cu` file (the shape's index in the file aside) and the same row in the per-shape tables; and the 116 generation shapes no session store holds come out byte-identical from a second input: every attention-output shape from a model-only dump at `--numbits 9`, fold class 11 at 16 slots from a synthetic segment whose own remainder is 11 (`--s 16 --ctx 16 --seed 114`), and every fold shape from a second constants dump of other dimensions and exponents (32 heads, 1,024-wide matrices, own remainder 2). The 14 attention-output constraint kernels no session store holds come, on the CPU, from the recorded 8B statements, and on the GPU host from the commitment's own lines.

It then builds once, with the architecture check of `prove`. The commit output carries the phases `witness`, `model_roots` (with the witness's deletion, as in v1.0), `kernels_emit` and `kernels_build`, and a `kernels` record: the store's constraint kernel count (`shapes.json`), generation shape count (`gen_shapes.json`), build key and shape set, the emitter runs, the refusals, the override flags, the synthetic segment's arguments and the fold dump's line. The same record is kept as `/io/state/build/kernels.json`. Its stderr (kept by the harness as the step's log) gives each emission group's lines, runs and first refusals. The commitment still covers the two verifier files alone.

**What a reply can need.** 230 kernels: 73 constraint kernels and 157 generation shapes. A reply's shapes are a function of its 66 lines' `Params` (2 blocks of 32 layers and 2 heads: `gen_ids` decodes exactly 512 tokens and never stops at an end-of-text token, [gen_ids.py](https://github.com/sg-ai-safety-hub/zk-inference-prover/blob/4f41667297430a598165c4a8604258fe37d952ae/harness/witness/gen_ids.py#L71-L80), and `shift_ids` checks the count, [shift_ids.py](https://github.com/sg-ai-safety-hub/zk-inference-prover/blob/4f41667297430a598165c4a8604258fe37d952ae/harness/witness/shift_ids.py#L54-L63)). Of those fields, only the attention output's limbs, form and divisor range and the fold's remainder change a fingerprint with the data; the others the data moves (`kmax`, the exp table's size under `--tight-table`, the fold's alpha, the window of exponents) change table sizes only. **Build time.** The three commit builds of this branch, 98 kernels, took 1,351 to 1,379 s (n = 3); the reply rebuilds with 99 to 101 kernels took 1,352 to 1,370 s (n = 5). **`prove`.** Each reply runs upstream's own per-sequence emission on its plan into the same store, then compares the store's build key with the key of the store last built. It rebuilds only when they differ, so only when the emission added a kernel; the run goes on either way. Its phases are `ids`, `witness`, `kernels_emit`, `kernels_build` (0 when no build ran) and `prove`, summed over the replies. The setup's emission is meant to hold every kernel a reply can need, so a reply that builds is a defect of the setup: the prove output's `kernels` record gives the store after the last reply, `replies_built`, the count of replies that had to build, and `setup_defects`, one entry per such reply with the shapes its emission added (list, family, first-seen name), the counts and the build's seconds; each also adds a warning that names it a setup defect, and stderr a `SETUP DEFECT` line. The reply still builds and proves, so no proving work is lost. A kernel that is in neither the store nor the reply's emission still stops the reply: the adapter never sets `ZK_KERNEL_FALLBACK` and refuses any `kernel fallback:` line (§Backend).

**The two digests.** The build key is sha256 over `<file name>\t<sha256>` lines of the store's files in name order. On the pinned commit built for CPU, a second emission of stored shapes rewrites every store file byte for byte except `manifest.json` and `gen_manifest.json`, which also record the last run's `source` (a witness path), `components` and new-shape count ([cudagen.rs](https://github.com/sg-ai-safety-hub/zk-inference-prover/blob/4f41667297430a598165c4a8604258fe37d952ae/prover/src/cudagen.rs#L2816-L2826), [#L3730-L3737](https://github.com/sg-ai-safety-hub/zk-inference-prover/blob/4f41667297430a598165c4a8604258fe37d952ae/prover/src/cudagen.rs#L3730-L3737)). For those two the key takes only `families`, the field the install scripts read ([install_constraint_kernels.py](https://github.com/sg-ai-safety-hub/zk-inference-prover/blob/4f41667297430a598165c4a8604258fe37d952ae/prover/kernels/install_constraint_kernels.py#L81-L83), [install_witness_gen_kernels.py](https://github.com/sg-ai-safety-hub/zk-inference-prover/blob/4f41667297430a598165c4a8604258fe37d952ae/prover/kernels/install_witness_gen_kernels.py#L128-L130)). No path enters the key. The store files keep shapes in the order they were first seen ([cudagen.rs](https://github.com/sg-ai-safety-hub/zk-inference-prover/blob/4f41667297430a598165c4a8604258fe37d952ae/prover/src/cudagen.rs#L2553-L2601), [#L3480-L3545](https://github.com/sg-ai-safety-hub/zk-inference-prover/blob/4f41667297430a598165c4a8604258fe37d952ae/prover/src/cudagen.rs#L3480-L3545)), so two sessions that reach the same shapes in another order have two build keys. To compare sessions, the shape set is sha256 over the sorted `<list>\t<family>\t<sha256 of the shape's Ir>` lines of `shapes.json` and `gen_shapes.json`, which depends only on which shapes the store holds.

## Setup

The commitment and the kernel build are made once, by a setup run, and every session reuses them. A setup run is `info`, `setup` and `commit` with no prompt: its `commit` is the one above, and the harness keeps the whole `/io/state` it leaves (verifier files, prover files, the kernel store, `kernels.done`, `kernels.json` and the CUDA build under `/io/state/build/t-cuda`) with the setup record. A session that names a setup restores that state under `/io/state` and its `commit` job carries `setup_state`: the setup's `commitment_id` and the store's `build_key`, both from the setup record. `commit` then extracts, derives, emits and builds nothing. It checks that the four files are there, that the verifier files hash to `commitment_id`, that `grid.json` is this request's grid, that the store's build key equals `build_key` and `kernels.done`, that the CUDA binary is there, and that its library carries this card's `sm_` code (`nvidia-smi` and `cuobjdump`, as `build` checks it). It returns the same commitment, the `kernels` record and one phase, `setup_check`. A state that fails any check stops the run; `commit` never makes the state again in its place. A MODEL control's `commit` (W' mounted at `/models`) refuses `setup_state`, and makes the commitment alone, with the phases `witness` and `model_roots`: it emits no kernel and builds nothing, since no proof is made from W' state (P1 proves from the session's own) and the job's directory is dropped once the commitment files are copied out. The harness side is `iproofs run --make-setup` (the setup run, which writes the record `setup/1` and `state.tar`) and `iproofs run --setup DIR` (a session, whose `commit_seconds` and `whole_wall_seconds` are null `setup_reused`: the setup record holds the commitment's and the build's seconds, and run.json `kernels` keeps the store each step reported and the replies that rebuilt it); on Hugging Face Jobs, `hf-job.sh setup` and a run step's `setup=PATH` (docs/runbooks/hf-jobs.md).

## Backend

Proving runs on the CUDA backend, matching every recorded H100 sequence run ([sequence-job.sh](https://github.com/sg-ai-safety-hub/zk-inference-results/blob/11decec3c0b62c707618aab5deb82750b355d202/tools/drivers/lib/sequence-job.sh#L370), [REPRODUCE.md](https://github.com/sg-ai-safety-hub/zk-inference-results/blob/11decec3c0b62c707618aab5deb82750b355d202/REPRODUCE.md#L281-L285)), while kernel emission, `model-roots`, and `boundary-grid` run on the SIMD backend as upstream does. The adapter never falls back silently: a failed kernel compilation, missing GPU architecture target, or stderr fallback line aborts `prove`.

The CUDA binary prebuilt into the image cannot prove an 8B segment out of the box. Upstream's CUDA backend "proves through device kernels generated per segment shape, so the job emits the kernels for every distinct shape in the plan into one store, installs them into the vendored library and rebuilds" ([REPRODUCE.md](https://github.com/sg-ai-safety-hub/zk-inference-results/blob/11decec3c0b62c707618aab5deb82750b355d202/REPRODUCE.md#L281-L285)); as `prover/README.md` puts it, "The CUDA backend's build is the same commit with the generated kernel store installed into the vendored library, which is how a device build is made at all" ([prover/README.md](https://github.com/sg-ai-safety-hub/zk-inference-prover/blob/eb95bfa887299d1637550228d42086c27cbb2b3b/prover/README.md#L250-L255)). Because segment shapes depend on witnesses extracted on the GPU, `commit` builds the binary inside a working copy of the source from the commitment sequence's kernels, and `prove` rebuilds it only when a reply's emission adds a kernel to the store (§Kernels). While upstream docs mention that a clean CUDA build "evaluates constraints on the CPU" before kernels are installed ([prover/README.md](https://github.com/sg-ai-safety-hub/zk-inference-prover/blob/eb95bfa887299d1637550228d42086c27cbb2b3b/prover/README.md#L17-L19), [prover/kernels/README.md](https://github.com/sg-ai-safety-hub/zk-inference-prover/blob/eb95bfa887299d1637550228d42086c27cbb2b3b/prover/kernels/README.md#L3-L4)), at the pinned commit the default `ZK_DEVICE_WITNESS_GEN_KEY_TILE=1` places key-tile columns on the GPU ([compose.rs](https://github.com/sg-ai-safety-hub/zk-inference-prover/blob/eb95bfa887299d1637550228d42086c27cbb2b3b/prover/src/compose.rs#L6976-L6979)), where a missing generation kernel panics instead of falling back ([devfrac.rs](https://github.com/sg-ai-safety-hub/zk-inference-prover/blob/eb95bfa887299d1637550228d42086c27cbb2b3b/prover/src/devfrac.rs#L193-L206), [#L293-L298](https://github.com/sg-ai-safety-hub/zk-inference-prover/blob/eb95bfa887299d1637550228d42086c27cbb2b3b/prover/src/devfrac.rs#L293-L298); the checked-in table is only a placeholder in [gencudakernels.rs](https://github.com/sg-ai-safety-hub/zk-inference-prover/blob/eb95bfa887299d1637550228d42086c27cbb2b3b/prover/src/gencudakernels.rs)).

In addition, the vendored CUDA library detects GPU architecture by calling `nvidia-smi` before `project()`, defaulting to `89;100;120` when no GPU is present ([CMakeLists.txt](https://github.com/sg-ai-safety-hub/zk-inference-prover/blob/eb95bfa887299d1637550228d42086c27cbb2b3b/nitroo/crates/stwo/src/stwo_cuda/cuda/CMakeLists.txt#L7-L32)); `CUDAARCHS` is "only advisory here" ([on-card.sh](https://github.com/sg-ai-safety-hub/zk-inference-prover/blob/eb95bfa887299d1637550228d42086c27cbb2b3b/tools/gate/on-card.sh#L27-L31), [tools/gate/README.md](https://github.com/sg-ai-safety-hub/zk-inference-prover/blob/eb95bfa887299d1637550228d42086c27cbb2b3b/tools/gate/README.md#L111-L123)). Because container images build on CPU hosts, the prebuilt `libstwo_cuda.a` likely lacks `sm_90` code; rebuilding inside `prove` with the GPU visible and verifying via `cuobjdump` ensures the right architecture is compiled.

## Deviations from upstream's measuring setup

- **Prompt injection.** `gen_ids` reads prompts strictly from upstream's corpus cache (`ZK_OUT/tokens.npz`, via `common.tokens()`, [gen_ids.py](https://github.com/sg-ai-safety-hub/zk-inference-prover/blob/eb95bfa887299d1637550228d42086c27cbb2b3b/harness/witness/gen_ids.py#L54-L60), [common.py](https://github.com/sg-ai-safety-hub/zk-inference-prover/blob/eb95bfa887299d1637550228d42086c27cbb2b3b/harness/witness/common.py#L280-L291)) and exposes no documented CLI option for arbitrary prompts. The adapter injects the job's prompt into that cache under `eval`, preserves upstream's `calib` slice, and runs `gen_ids --offset 0`. Although no upstream source or flag is modified, using a cache file as an input mechanism is undocumented and should be confirmed with upstream before publishing a row.
- **Kernel build in `commit` and `prove`.** Upstream emits, installs, and compiles kernels prior to its timed proving loop and excludes that time ([REPRODUCE.md](https://github.com/sg-ai-safety-hub/zk-inference-results/blob/11decec3c0b62c707618aab5deb82750b355d202/REPRODUCE.md#L318-L332)). Here `commit` emits and builds them (phases `kernels_emit` and `kernels_build`), once per setup (§Setup), and each reply's own emission and any rebuild it needs run inside `prove`, recorded as its `kernels_emit` and `kernels_build` phases, while extraction (also outside upstream's `loop` and `whole wall` scopes) is recorded as the `witness` phase. v1.0 sessions recorded one `kernels` phase in `prove`, a rebuild on every reply (§Kernels).
- **Commitment derivation.** Upstream computes `model-roots` over the plan of the target sequence ([model-commitment.sh](https://github.com/sg-ai-safety-hub/zk-inference-results/blob/11decec3c0b62c707618aab5deb82750b355d202/tools/drivers/model-commitment.sh#L13-L20)); here `commit` computes it over upstream's corpus before prompts are supplied.
- **1,024 + 64 shape.** Uses 64-token blocks, whereas upstream only records `S = 512` (see table above).
- **Proof storage.** Upstream retains serialized proofs on host storage; here they are packaged into the released proof directory (`<tag>.fixed.json`, `<tag>.claims.json`, `<tag>.proof.json` per segment, plus `plan.txt`).
- **Setup reuse.** Upstream reuses witnesses, compiled binaries, and kernel stores across campaigns at a given context length. Here a setup run makes the commitment and the kernel build once, before any session, from upstream's corpus and the sweep alone, and sessions reuse that state (§Setup); nothing a session makes from its prompts is carried to another session.

## Values for `system.yaml`

Based on the facts above, `system.yaml` declares the following settings alongside its pushed image digest:

```yaml
deterministic_proofs: true
incremental_proofs: true
proofs: {granularity: "segment_grid", tokens_covered: "prompt_plus_output", steady_boundary: "first_proof", steady_approximate: false,
         verify_reads: "all"}
forbidden_flags: ["--unsound-skip-", "--unsound-argmax-lax"]
```

- `proofs.granularity: segment_grid`: One benchmark proof corresponds to an entire sequence grid (the unit verified by `boundary-grid`), released once all segments finish (RFC-0005 §system.yaml).
- `proofs.tokens_covered: prompt_plus_output`: Every grid proves both prompt and continuation positions, covering `prompt_tokens + output_tokens` (4,608 or 1,088 for the v0.1 shapes) regardless of block size.
- `incremental_proofs: true` and `proofs.steady_boundary: first_proof`: Multi-request jobs prove sequences sequentially and release each completed grid before starting the next (five proofs per Level 1 session). Single-request v0.1 jobs emit only one release, leaving `prove.steady` null since observing a steady interval requires multiple releases. Individual segment files are written incrementally, though a single segment is not a complete benchmark proof. (Prior to 2026-11-10, these were set to `false` and `not_observable` under RFC-0005 Q1 for single-request jobs.)
- `proofs.steady_approximate: false`: Exact grid release timestamps are observed directly.
- `proofs.verify_reads: "all"`: `verify` inspects every file in the proof directory, so C5, C6, and C8 can sample across all parts ([RFC-0008 §Parts the verifier reads](../../rfcs/0008-negative-controls.md#parts-the-verifier-reads)). `boundary-grid --plan` parses `plan.txt` for `--ser-tag` entries ([boundary.rs](https://github.com/sg-ai-safety-hub/zk-inference-prover/blob/eb95bfa887299d1637550228d42086c27cbb2b3b/prover/src/boundary.rs#L1222-L1224), [#L1060-L1071](https://github.com/sg-ai-safety-hub/zk-inference-prover/blob/eb95bfa887299d1637550228d42086c27cbb2b3b/prover/src/boundary.rs#L1060-L1071)), loads `<tag>.fixed.json` and `<tag>.proof.json` for every tag ([#L1250-L1252](https://github.com/sg-ai-safety-hub/zk-inference-prover/blob/eb95bfa887299d1637550228d42086c27cbb2b3b/prover/src/boundary.rs#L1250-L1252)), and under `--verify` loads `<tag>.claims.json` as well ([#L1492-L1495](https://github.com/sg-ai-safety-hub/zk-inference-prover/blob/eb95bfa887299d1637550228d42086c27cbb2b3b/prover/src/boundary.rs#L1492-L1495)). Every segment file belongs to a tag in that plan (§`prove`), and the adapter additionally inspects `B<B-1>L0.fixed.json` for its claimed-output note (§`verify`).
- `deterministic_proofs: true`: Upstream enforces digest reproducibility across both backends ("A change that should not alter the proof reproduces the recorded digests on both backends before it merges", [README.md](https://github.com/sg-ai-safety-hub/zk-inference-prover/blob/eb95bfa887299d1637550228d42086c27cbb2b3b/README.md#L60-L66)).
- `forbidden_flags`: `--unsound-skip-` and `--unsound-argmax-lax`, each disabling or relaxing a binding edge ([statement.md](https://github.com/sg-ai-safety-hub/zk-inference-prover/blob/eb95bfa887299d1637550228d42086c27cbb2b3b/docs/statement.md#L19-L36), [#L153-L160](https://github.com/sg-ai-safety-hub/zk-inference-prover/blob/eb95bfa887299d1637550228d42086c27cbb2b3b/docs/statement.md#L153-L160)).

Because some crate archives ship owner-only files (such as `fnv` 1.0.7), the `fetch` stage sets `/opt/cargo` world-readable so `prove` can rebuild the CUDA library as the non-root adapter user.
- Installs the CUDA PyTorch dependency group instead of the CPU default, following upstream's CUDA-host instructions.
- Checks out upstream via `git` at the pinned commit and verifies both `git rev-parse HEAD` (INV-ADAPTER-2) and the SHA-256 of `git archive --format=tar HEAD` against `inputs.lock`.
- Pins Ubuntu packages to exact archive versions (PIN-5), since the Ubuntu snapshot service returned HTTP 503 for all dates on 2026-11-04.

## Level 1

RFC-0018 defines the Level 1 request as 512 prompt tokens and a 512-token greedy reply with end tokens ignored, checking every reply token. The workload `l1-l31-8b-p512-o512` runs batch size 1, five requests per session, and one commitment per session. The analysis below was written from source inspection at the pinned commits prior to GPU execution.

### The grid of 512 + 512

- **Adapter geometry.** Sets `S = 512` (matching output length so the reply fits in one block) and `P = 512`, giving `B = 2` blocks (block 0 prompt, block 1 reply), head segments over blocks 0 and 1, `--expect-layer-links` `2 × 31 + 2 = 64`, and `--expect-token-links` `1 × 32 = 32` per upstream's formula ([headline-c4096.sh#L106-L114](https://github.com/sg-ai-safety-hub/zk-inference-results/blob/11decec3c0b62c707618aab5deb82750b355d202/tools/drivers/headline-c4096.sh#L106-L114)). Commands mirror v0.1 with these dimensions: `gen_ids --prefix 512 --offset 0 --new 513`, `shift_ids --prefix 512 --new 512`, `extract --tokens 1024 --chunk 512`, and `plan --blocks 2 --with-block-0 --head-blocks 0,1`, totaling 66 segments (2 × 32 layer segments plus 2 head segments).
- **Documented upstream.** Block size `S = 512` matches "every recorded run has `S = 512`" ([GLOSSARY.md#L7-L9](https://github.com/sg-ai-safety-hub/zk-inference-prover/blob/eb95bfa887299d1637550228d42086c27cbb2b3b/GLOSSARY.md#L7-L9)), and prompt length 512 satisfies being both a power of two and a multiple of 512-token prefill chunks ([gen_ids.py#L52-L53](https://github.com/sg-ai-safety-hub/zk-inference-prover/blob/eb95bfa887299d1637550228d42086c27cbb2b3b/harness/witness/gen_ids.py#L52-L53)). Decoding takes greedy argmax over the full vocabulary including end tokens (`gen_ids.py` L78) without stopping early ("a stop is recorded and passed through rather than truncating the rectangle", [#L73-L84](https://github.com/sg-ai-safety-hub/zk-inference-prover/blob/eb95bfa887299d1637550228d42086c27cbb2b3b/harness/witness/gen_ids.py#L73-L84)), satisfying Level 1's EOS rule. Generating 513 tokens and shifting ensures all `S` reply rows are verified ([shift_ids.py#L28-L31](https://github.com/sg-ai-safety-hub/zk-inference-prover/blob/eb95bfa887299d1637550228d42086c27cbb2b3b/harness/witness/shift_ids.py#L28-L31); [sequence-job.sh#L159-L177](https://github.com/sg-ai-safety-hub/zk-inference-results/blob/11decec3c0b62c707618aab5deb82750b355d202/tools/drivers/lib/sequence-job.sh#L159-L177)), with head segments spanning the last prompt block and the reply block ([plan.py#L230-L238](https://github.com/sg-ai-safety-hub/zk-inference-prover/blob/eb95bfa887299d1637550228d42086c27cbb2b3b/harness/witness/plan.py#L230-L238)).
- **Not recorded upstream.** Upstream has no recorded run at context 512 or with a 2-block grid: its recorded runs cover contexts of 4,096 (`S = 256, 512, or 1,024`: 17, 9, or 5 blocks), 16,384 (33 blocks), and 24,576 (49 blocks) (`runs/*/config.json`). Although `plan.py`'s self-test builds a synthetic `--blocks 2 --with-block-0 --head-blocks 0,1` plan over prefixes 512 and 1,024 ([plan.py#L598-L687](https://github.com/sg-ai-safety-hub/zk-inference-prover/blob/eb95bfa887299d1637550228d42086c27cbb2b3b/harness/witness/plan.py#L598-L687)), that tests plan generation rather than proving. Similarly, a head segment on block 0 (`c = 0`, [plan.py#L33-L36](https://github.com/sg-ai-safety-hub/zk-inference-prover/blob/eb95bfa887299d1637550228d42086c27cbb2b3b/harness/witness/plan.py#L33-L36)) has never appeared in a recorded run (where the first head block always has a non-empty prefix). Kernel shapes for `c = 0` and `c = 512`, resulting extraction pins, and run times are not stated.
- **Omitted verification decode.** `sequence-job.sh` also runs a redundant 512-token decode to verify it matches the first 512 tokens of the 513-token decode ([#L176-L182](https://github.com/sg-ai-safety-hub/zk-inference-results/blob/11decec3c0b62c707618aab5deb82750b355d202/tools/drivers/lib/sequence-job.sh#L176-L182)); the adapter skips this second pass.

### Five requests a session

`commit` runs once over the commitment sequence for the 512 + 512 plan, producing model roots for every layer at `c = 0` and `c = 512`. `prove` then processes the five prompts sequentially: for each prompt it decodes, extracts witnesses, builds the plan, emits that plan's kernels into the store and rebuilds only if the emission added a kernel (§Kernels), proves the grid into `/io/proofs/.tmp-req-<i>`, and atomically renames it to `req-<i>` before moving on (`tests/test_sash_level1.py` checks this sequence). Because each request releases its completed proof incrementally, `system.yaml` sets `incremental_proofs: true` and `steady_boundary: first_proof`. A request whose emission adds a kernel rebuilds the backend (the v0.1 dev run's `kernels` phase, emission and build, was 2,207.8 s, `tests/fixtures/gpu/prove.out.json`) and takes that much longer than one that reuses the build.

### REPLY under SASH: how C1 reaches upstream's verifier

`boundary-grid` does not take a separate claimed-output parameter. It accepts only the prompt (`--prompt FILE`, "the prompt's ids", [boundary.rs#L1115](https://github.com/sg-ai-safety-hub/zk-inference-prover/blob/eb95bfa887299d1637550228d42086c27cbb2b3b/prover/src/boundary.rs#L1115)) and checks every position in blocks with an embedding chunk: prompt positions are checked against the prompt file, while later positions are checked against the head's proved argmax from the preceding position ([#L1148-L1156](https://github.com/sg-ai-safety-hub/zk-inference-prover/blob/eb95bfa887299d1637550228d42086c27cbb2b3b/prover/src/boundary.rs#L1148-L1156), [#L1562-L1601](https://github.com/sg-ai-safety-hub/zk-inference-prover/blob/eb95bfa887299d1637550228d42086c27cbb2b3b/prover/src/boundary.rs#L1562-L1601)). Reply token IDs live inside the segment statements (`tok_in`), tied to the proof in `verify_composed` via a Horner polynomial evaluation over a post-commitment challenge ("a probabilistic binding ..., not a constraint", [compose.rs#L7264-L7272](https://github.com/sg-ai-safety-hub/zk-inference-prover/blob/eb95bfa887299d1637550228d42086c27cbb2b3b/prover/src/compose.rs#L7264-L7272), [#L7845-L7849](https://github.com/sg-ai-safety-hub/zk-inference-prover/blob/eb95bfa887299d1637550228d42086c27cbb2b3b/prover/src/compose.rs#L7845-L7849)).

Putting both prompt and reply into `--prompt` would defeat the REPLY check, because `boundary-grid` skips the argmax check for any position covered by the prompt file (the `continue` at [boundary.rs#L1567-L1573](https://github.com/sg-ai-safety-hub/zk-inference-prover/blob/eb95bfa887299d1637550228d42086c27cbb2b3b/prover/src/boundary.rs#L1567-L1573)). Therefore `verify` passes only the prompt, and C1 tests reply binding via `mutate_reply` (RFC-0018 AD-6). `mutate_reply` duplicates the proof directory byte-for-byte and alters the target reply token at both places `boundary-grid` pairs it: `tok_in[t]` in the reply block's layer-0 statement (`B<B-1>L0.fixed.json`) and the preceding emitted token `tok_out[t-1]` in `B<B-1>head.fixed.json` (or the last `tok_out` of `B<B-2>head.fixed.json` when `t = 0`). Each list is modified minimally as text and reparsed to confirm no unrelated fields changed. Because both ends of the boundary link still agree, any rejection must come from the cryptographic proofs themselves: `verify_composed` recomputes the Horner sums of `tok_in` and `tok_out` against the replayed challenge and checks them against `claims.embed_tok` and `claims.head_tok` ([compose.rs#L7845-L7857](https://github.com/sg-ai-safety-hub/zk-inference-prover/blob/eb95bfa887299d1637550228d42086c27cbb2b3b/prover/src/compose.rs#L7845-L7857)). The runner verifies the mutated proof alongside the original claimed reply; the verdict comes strictly from `boundary-grid`, while the adapter's comparison between claim and proof remains an informational warning (§`verify`). CPU tests cover this against a mock grid, and live C1 trials confirm it on real grids. Note that `compose.rs` describes this binding as "a probabilistic binding over a post-commitment challenge, not a constraint" ([#L7264-L7272](https://github.com/sg-ai-safety-hub/zk-inference-prover/blob/eb95bfa887299d1637550228d42086c27cbb2b3b/prover/src/compose.rs#L7264-L7272)).

### The MODEL check's weight change

SASH quantizes the BF16 checkpoint at load time: per output channel, `s = bf16_ceil(max |w| / 127)` and `q = round-half-away(w / s)` clamped to `±127` ([quant.py#L18-L21](https://github.com/sg-ai-safety-hub/zk-inference-prover/blob/eb95bfa887299d1637550228d42086c27cbb2b3b/harness/witness/quant.py#L18-L21), [#L37-L46](https://github.com/sg-ai-safety-hub/zk-inference-prover/blob/eb95bfa887299d1637550228d42086c27cbb2b3b/harness/witness/quant.py#L37-L46), [#L90-L97](https://github.com/sg-ai-safety-hub/zk-inference-prover/blob/eb95bfa887299d1637550228d42086c27cbb2b3b/harness/witness/quant.py#L90-L97), [#L145-L148](https://github.com/sg-ai-safety-hub/zk-inference-prover/blob/eb95bfa887299d1637550228d42086c27cbb2b3b/harness/witness/quant.py#L145-L148); matrices are transposed so scales reduce over the input axis, [model.py#L193-L216](https://github.com/sg-ai-safety-hub/zk-inference-prover/blob/eb95bfa887299d1637550228d42086c27cbb2b3b/harness/witness/model.py#L193-L216)). Under `y-delay-vw12`, layer projections use BF16 scales while only `lm_head` uses power-of-two scales ([common.py#L182](https://github.com/sg-ai-safety-hub/zk-inference-prover/blob/eb95bfa887299d1637550228d42086c27cbb2b3b/harness/witness/common.py#L182), [#L232-L233](https://github.com/sg-ai-safety-hub/zk-inference-prover/blob/eb95bfa887299d1637550228d42086c27cbb2b3b/harness/witness/common.py#L232-L233); [model.py#L202](https://github.com/sg-ai-safety-hub/zk-inference-prover/blob/eb95bfa887299d1637550228d42086c27cbb2b3b/harness/witness/model.py#L202), [#L576-L581](https://github.com/sg-ai-safety-hub/zk-inference-prover/blob/eb95bfa887299d1637550228d42086c27cbb2b3b/harness/witness/model.py#L576-L581)). Because layer 0's `q_proj` is scaled by `hd^-1/2` prior to quantization ([model.py#L439](https://github.com/sg-ai-safety-hub/zk-inference-prover/blob/eb95bfa887299d1637550228d42086c27cbb2b3b/harness/witness/model.py#L439), [#L468-L470](https://github.com/sg-ai-safety-hub/zk-inference-prover/blob/eb95bfa887299d1637550228d42086c27cbb2b3b/harness/witness/model.py#L468-L470)), the perturbation targets another block-0 projection (`o_proj`, `k_proj`, `v_proj`, or MLP).

[`weight_change.py`](weight_change.py) inspects one output channel of a BF16 tensor in a safetensors file and finds the smallest BF16 step on a single weight that shifts its int8 code without changing the channel scale, leaving every other quantized weight untouched (`tests/test_sash_weight_change.py` tests this against hand-computed cases). `perturb` (RFC-0018 AD-5, CPU) applies this edit to the first qualifying row of `model.layers.0.self_attn.o_proj.weight`, writes W′ as a full copy of the model directory with those two bytes modified, and records the flat element index, before/after BF16 bytes, step count and int8 codes in `unit`, and before/after file SHA-256 digests. SASH has no standalone weight-digest binary (`digest_tool: null`). That `commit` on W′ yields distinct model roots follows from upstream's statement that a model root "is a function of the model" ([driver.sh#L147-L148](https://github.com/sg-ai-safety-hub/zk-inference-results/blob/11decec3c0b62c707618aab5deb82750b355d202/tools/drivers/lib/driver.sh#L147-L148)), which the C3 commit on W′ verifies directly.

### Scoring a reference reply (`score`, RFC-0018 AD-7)

`score` computes SASH's top token (FI-10) and top 256 token probabilities (FI-12) at every position of a reference reply produced by another engine. For each request, it invokes the same head-extraction command already run during `prove` ([`witness_and_plan`](entrypoint)), passing the combined prompt and reply IDs:

```
python -m harness.witness.extract --tokens 1024 --chunk 512 --layer 16 --spec y-delay-vw12 \
  --head --slim --diagonal-block --blocks 0,1 --ids <prompt + reply>.npy \
  --attn-ranges $ZK_OUT/attn_ranges.json --out <a fresh directory>
```

- `--ids` is a documented upstream flag: "token ids (.npy) to run instead of the corpus's first --tokens" ([extract.py L645-L647](https://github.com/sg-ai-safety-hub/zk-inference-prover/blob/4f41667297430a598165c4a8604258fe37d952ae/harness/witness/extract.py#L645-L647)). The adapter writes 1,024 int64 values directly in NumPy format without touching upstream's token cache.
- `--head` exports "the logits' order keys and the emitted tokens" ([L679-L681](https://github.com/sg-ai-safety-hub/zk-inference-prover/blob/4f41667297430a598165c4a8604258fe37d952ae/harness/witness/extract.py#L679-L681)): `tok_head.i32` (row-wise argmax, lowest index on ties) and `key_head.u16` (an order-preserving key for each bf16 logit, [L1187-L1195](https://github.com/sg-ai-safety-hub/zk-inference-prover/blob/4f41667297430a598165c4a8604258fe37d952ae/harness/witness/extract.py#L1187-L1195)). The adapter decodes each key back to bf16 (`sign ? 0x7FFF - mag : 0x8000 + mag`) and computes log-softmax in float64.
- Row `t` of a block predicts the token at position `t + 1` ([L1217-L1228](https://github.com/sg-ai-safety-hub/zk-inference-prover/blob/4f41667297430a598165c4a8604258fe37d952ae/harness/witness/extract.py#L1217-L1228)), so reply position 0 comes from row 511 of block 0, and positions 1 through 511 come from rows 0 through 510 of block 1. The adapter verifies its agreement count in block 1 against `emits_next_token` in the dump manifest and aborts on any discrepancy.
- `--attn-ranges` uses the exact attention calibration from the counted sessions' commitment (either supplied from the session commitment store after SHA-256 verification against `prover_files`, or regenerated via `commit` and verified to match the session digest).
- Any request rejected by an extractor assertion (no-wrap or fold checks, [L992](https://github.com/sg-ai-safety-hub/zk-inference-prover/blob/4f41667297430a598165c4a8604258fe37d952ae/harness/witness/extract.py#L992), [L1017](https://github.com/sg-ai-safety-hub/zk-inference-prover/blob/4f41667297430a598165c4a8604258fe37d952ae/harness/witness/extract.py#L1017)) is recorded as failed with that assertion line, while any other failure aborts `score`.

Provenance of this computation: the extractor computes the exact witnesses that would be fed to the prover for those token IDs, though no proof is generated during `score`. Upstream does not explicitly state at the pinned commit whether `--ids` is intended for non-greedy replies, whether extractor outputs match proved values bit-for-bit (the closest statement is "A witness and a spec are one object", [common.py L175](https://github.com/sg-ai-safety-hub/zk-inference-prover/blob/4f41667297430a598165c4a8604258fe37d952ae/harness/witness/common.py#L175)), or whether segment proofs would accept on non-greedy IDs with only grid token links failing (untested).

Level 1 measurement (Llama 3.1 8B, 15 prompts, 1 H200, `results/v1.0/teacher-forced/llama-3.1-8b/run-sash.json`, n = 1 run):

- Zero no-wrap or fold assertions fired across all 15 reference replies.
- All 16 head extractions (the system's own reply to prompt 0 plus the 15 reference replies) took 480 s total (30 s each including model load, measured, n = 1).
- On the system's own proved reply to prompt 0, `tok_head` matched the proved reply at all 512 positions.
- Across all 15 prompts, the first position where `tok_head` disagreed with the reference token equaled the proved reply's matched prefix length (FI-3's stored score), confirming agreement between teacher-forced extraction and proved greedy decoding on divergence points.

The scoring container is built from [`Dockerfile.score`](Dockerfile.score), layering this directory's `entrypoint` onto the pinned `system.yaml` image without modifying the `system.yaml` pin.

### Prompt side and reply side (RFC-0018 CO-10, proposed)

`prove` reports its `prove` phase in three parts as well as whole, summed over the session's replies. A part is named `<phase>__<part>`; CO-9's sum against the harness-timed prove call counts whole phases only, so `ids`, `witness`, `kernels_emit`, `kernels_build` and `prove` keep their meaning.

| Phase | Seconds | Upstream output |
|---|---|---|
| `prove__prompt` | the `chunk_secs` of every chunk row of the blocks before the reply block, their heads included: at 512 + 512, `B0L0` to `B0L31` and `B0head` | `compose-chunks` stdout, `result.chunks[]`: one row per segment with `ser_tag` (`B<b>L<k>` or `B<b>head`) and `chunk_secs` ([chunks.rs#L744-L746](https://github.com/sg-ai-safety-hub/zk-inference-prover/blob/4f41667297430a598165c4a8604258fe37d952ae/prover/src/chunks.rs#L744-L746)), which the adapter already writes to `/io/state/out/req<i>_slice_<lo>.json` |
| `prove__reply` | the same over the reply block, `B1L0` to `B1L31` and `B1head` | the same |
| `prove__rest` | `prove` less the two above | the adapter's own clock |

- **What a row's seconds are.** With `ZK_PIPELINE=1` one thread generates each segment's witness while another proves the segment before it. `chunk_secs` is the proving thread's time on one segment, from taking its generated witness to its files written ([chunks.rs#L641-L651](https://github.com/sg-ai-safety-hub/zk-inference-prover/blob/4f41667297430a598165c4a8604258fe37d952ae/prover/src/chunks.rs#L641-L651)). So the two sides hold the proving, and the rest holds what no row times: each process's start and plan read, the first witness of each process (nothing overlaps it), the time a proving thread waits for a witness, the `compose-chunks` summary, the plan's copy and the release.
- **Which side a head is on.** `B0head` is on the prompt side: its last row emits the reply's first token, which `boundary-grid` checks against `tok_in[0]` of `B1L0` across the block seam ([boundary.rs#L1148-L1156](https://github.com/sg-ai-safety-hub/zk-inference-prover/blob/4f41667297430a598165c4a8604258fe37d952ae/prover/src/boundary.rs#L1148-L1156)). So the prompt side holds the prompt's 512 positions and the choice of the reply's first token, as request A's 1-token reply does on the serving side.
- **When there are no parts.** The parts are reported only when every reply's rows name each segment of its plan exactly once with a number of seconds, and the two sides do not exceed that reply's `prove`. Otherwise no part is reported for the session, never one side alone or a sum over some replies, and a warning says which reply and why.
- **Measured.** On ten kept replies of 512 + 512 at the pin (two sessions on one H200, 2026-11-26; their rows are `tests/fixtures/gpu/chunk-rows.json`), the prompt side is 361.4 to 367.6 s a reply (mean 364.0 s) and the reply side 368.8 to 374.9 s (mean 372.2 s), together about 736 s of a `prove` phase of about 793 s a reply.
- **`ids` stays whole.** `gen_ids` prints its progress in whole seconds counted from after its model load: `prefilled 512/512 (Ts)` once the prompt is read, `decoded k/513 (Ts)` every 128 tokens and `wrote ... in Ts` at the end ([gen_ids.py#L62-L67](https://github.com/sg-ai-safety-hub/zk-inference-prover/blob/4f41667297430a598165c4a8604258fe37d952ae/harness/witness/gen_ids.py#L62-L67), [#L83-L84](https://github.com/sg-ai-safety-hub/zk-inference-prover/blob/4f41667297430a598165c4a8604258fe37d952ae/harness/witness/gen_ids.py#L83-L84), [#L101-L102](https://github.com/sg-ai-safety-hub/zk-inference-prover/blob/4f41667297430a598165c4a8604258fe37d952ae/harness/witness/gen_ids.py#L101-L102)). That is too coarse for the prefill, which no line times from its start, and the decode span between the two lines also holds the tokenizer's load ([#L69-L71](https://github.com/sg-ai-safety-hub/zk-inference-prover/blob/4f41667297430a598165c4a8604258fe37d952ae/harness/witness/gen_ids.py#L69-L71)). It also leaves out the model load, the prompt written into the token cache and `shift_ids`. So the adapter reports no `ids__prompt` or `ids__reply`. It logs these lines in `logs/prove.stderr` (`req-<i>: gen_ids: ...`) and nothing reads them. On the board, the generation on each side, and the side totals, are then null with that cause, and the proving sides still print.
- **Identity.** The change is in the adapter alone (no upstream change, no new argument to any upstream program). It changes `entrypoint`, so the image and its digest change. A session reuses only a setup made with the same image and adapter commit (`setups.py` `IDENTITY`), so a new image and a new setup run are needed before the next session.
