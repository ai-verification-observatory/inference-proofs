# FlashProve

Adapter for [`anthropics/FlashProve`](https://github.com/anthropics/FlashProve) pinned at commit `9e2bdd8ff5bf9c62f18263d7dac189b0400b260c` (v0.16.0, RFC-0005). This README covers the subcommand mapping (RFC-0005 §Adapter README requirements 1 to 4, 6, and 7) and the container image build (requirement 5). Every technical detail links to upstream at that commit, and any silent area is noted explicitly (AGENTS.md rule 9). All numbers cited on this page are grade `external`, tier `reported`, copied from upstream documentation at the pinned commit rather than measured by us; upstream figures for result tables live in [`external.yaml`](external.yaml).

## Subcommands and upstream calls

Each subcommand invokes a single upstream binary using the same flags passed by upstream's own scripts at the pinned commit. The adapter adds no undocumented flags; in negative-control jobs, `control_flags` are appended to `cp_prove` only. Every subprocess invocation is logged to `/io/commands.jsonl`. The binaries come from upstream's default build in `/src/prover/build/hc`.

| Step | Upstream call | Source |
|---|---|---|
| `info`, `setup` | None (binaries are compiled into the image) | |
| `commit` | `cp_commit -weights /models/UD-Q4_K_XL -config /io/state/commit/config -M 1 -ivk /io/state/commit/ivk -isk /io/state/commit/isk` | Commit command under "Reproduce the numbers" ([guide/performance.md#L76](https://github.com/anthropics/FlashProve/blob/9e2bdd8ff5bf9c62f18263d7dac189b0400b260c/guide/performance.md#L76)); [examples/maverick/run.sh#L1569-L1570](https://github.com/anthropics/FlashProve/blob/9e2bdd8ff5bf9c62f18263d7dac189b0400b260c/examples/maverick/run.sh#L1569-L1570) adds `-public-weights`, which we omit |
| `prove` | `cp_prove -isk /io/state/prove/isk -spool /io/state/prove/spool -batch B -in-step K -most-batches N -memory lean,tensor-rooms=8`, with `HOME` and `TMPDIR` pointing to fresh directories under `/io/state/prove` (`B` and `N` are the workload's batch size and batch count; `K = min(6, B)`) | [driver/measure_rate.py#L567-L571](https://github.com/anthropics/FlashProve/blob/9e2bdd8ff5bf9c62f18263d7dac189b0400b260c/driver/measure_rate.py#L567-L571), defaults [#L305-L308](https://github.com/anthropics/FlashProve/blob/9e2bdd8ff5bf9c62f18263d7dac189b0400b260c/driver/measure_rate.py#L305-L308), environment [#L685](https://github.com/anthropics/FlashProve/blob/9e2bdd8ff5bf9c62f18263d7dac189b0400b260c/driver/measure_rate.py#L685); option docs in [docs/service.md#L475-L487](https://github.com/anthropics/FlashProve/blob/9e2bdd8ff5bf9c62f18263d7dac189b0400b260c/docs/service.md#L475-L487) |
| `verify` | `cp_verify CONFIG IVK REQUEST TOKEN PROOF -id ID -next-token -j N`, where `N` is the container's available CPU count (capped at 256) | [driver/measure_rate.py#L697-L698](https://github.com/anthropics/FlashProve/blob/9e2bdd8ff5bf9c62f18263d7dac189b0400b260c/driver/measure_rate.py#L697-L698); CLI reference in [verifier/README.md#L88-L125](https://github.com/anthropics/FlashProve/blob/9e2bdd8ff5bf9c62f18263d7dac189b0400b260c/verifier/README.md#L88-L125) |

**`commit`.** First, the adapter checks the two fit outputs with published digests (`wsums.txt` next to the weights and `KL.bin`) against [examples/maverick/expected.txt](https://github.com/anthropics/FlashProve/blob/9e2bdd8ff5bf9c62f18263d7dac189b0400b260c/examples/maverick/expected.txt), mirroring the `fit` and `compare` stages of `run.sh`. It copies the three fit configuration files into `/io/state/commit/config` and runs `cp_commit`. A valid commit exits 0 with a final line starting with `cp_commit: done.` and containing `is complete and can be handed out`, and prints a single `commitment ID: <64 hex>` line ([docs/operators-duties.md#L497-L506](https://github.com/anthropics/FlashProve/blob/9e2bdd8ff5bf9c62f18263d7dac189b0400b260c/docs/operators-duties.md#L497-L506)). Any other result causes `commit` to fail with `cp_commit`'s exit code and last line. Omitting `-public-weights` lets `cp_commit` sample its own random seed so weight masking remains enabled, matching upstream's timed runs ([guide/performance.md#L6](https://github.com/anthropics/FlashProve/blob/9e2bdd8ff5bf9c62f18263d7dac189b0400b260c/guide/performance.md#L6); [examples/maverick/README.md#L52-L59](https://github.com/anthropics/FlashProve/blob/9e2bdd8ff5bf9c62f18263d7dac189b0400b260c/examples/maverick/README.md#L52-L59)).

**`prove`.** Before starting `cp_prove`, the adapter stages all requests into the spool's `in/` directory so every batch is full, matching `measure_rate.py` ([driver/README.md#L63-L71](https://github.com/anthropics/FlashProve/blob/9e2bdd8ff5bf9c62f18263d7dac189b0400b260c/driver/README.md#L63-L71)). Each request file encodes a window of `T` token IDs, the range `r` and `e`, and 32 random bytes, named `sha256("p258-spool-req-1" || bytes).req`, written to `in/.tmp/` and linked into `in/` ([docs/service.md#L94-L113](https://github.com/anthropics/FlashProve/blob/9e2bdd8ff5bf9c62f18263d7dac189b0400b260c/docs/service.md#L94-L113)). For Level 1, the window contains the prompt, the reply generated by the integer model, and zero padding up to `T`, with `r = P - 1` and `e = P + R - 1` so every reply token is covered (see §Level 1, "The request and the range"). For single-token v0.1 workloads, the window is the prompt with `r = T - 1` and `e = T`, proving the next token written by `cp_prove` as a 32-bit word in `<id>.y` ([docs/service.md#L84](https://github.com/anthropics/FlashProve/blob/9e2bdd8ff5bf9c62f18263d7dac189b0400b260c/docs/service.md#L84)). `cp_prove` pulls up to `-batch` queued requests at a time and moves a batch's outputs into `out/` once all are ready, marking each response complete when `<id>.proof` appears ([docs/service.md#L22-L30](https://github.com/anthropics/FlashProve/blob/9e2bdd8ff5bf9c62f18263d7dac189b0400b260c/docs/service.md#L22-L30), [#L250-L262](https://github.com/anthropics/FlashProve/blob/9e2bdd8ff5bf9c62f18263d7dac189b0400b260c/docs/service.md#L250-L262)). While `cp_prove` runs, the adapter polls `out/` every 50 ms; for each completed response it hard-links `<id>.y` and `<id>.proof` into `/io/proofs/.tmp-req-<i>/` as `response.y` and `response.proof`, then atomically renames the directory to `req-<i>` (RFC-0005 §Proof release protocol). `claimed_output` records the token word from `<id>.y` (or the full reply in Level 1). `prove` exits non-zero with `cp_prove`'s exit code and last line if `cp_prove` fails to exit 0 (`p258 end 0`, [docs/service.md#L334-L339](https://github.com/anthropics/FlashProve/blob/9e2bdd8ff5bf9c62f18263d7dac189b0400b260c/docs/service.md#L334-L339)), or if any request produces `<id>.failed` or receives no output.

**`verify`.** The adapter constructs the request file and token file itself without a nonce, acting as an external client ([docs/verifying.md](https://github.com/anthropics/FlashProve/blob/9e2bdd8ff5bf9c62f18263d7dac189b0400b260c/docs/verifying.md)). At Level 1, it writes the window containing `request` and `claimed_output` with `r = P - 1`, `e = P + R - 1`, and a 4-byte zero token file (`y` is ignored when `e < T`). For single-token v0.1 workloads, it writes `request` with `r = T - 1`, `e = T`, the claimed token in the token file, and passes `-next-token`. It passes only `response.proof` from the proof directory and never reads the claimed token from the proof folder. Configuration and public-key directories are reconstructed in `/tmp` from the harness's recorded `verifier_files`. Verification runs the C++ binary `cp_verify` rather than the Lean verifier (RFC-0005 Q4), matching [`claim.yaml`](claim.yaml) (configuration `exact-match-cp-verify`, unreviewed).

## Verdict mapping

Follows RFC-0005 §Verdict normalisation using the exit codes and final output lines documented in [verifier/docs/output.md#L247-L261](https://github.com/anthropics/FlashProve/blob/9e2bdd8ff5bf9c62f18263d7dac189b0400b260c/verifier/docs/output.md#L247-L261). The adapter captures the raw exit code and the last non-empty line of stdout (falling back to stderr if stdout is empty).

| cp_verify exit code and last line | verdict | `policy` |
|---|---|---|
| 0, `YES` | `accept` | `exact-match` |
| 0, `WITHIN LIMITS: clipped-gap C=... sh=...` | `accept` | `clipped-gap` |
| 1, `NO: <name>` | `reject` | |
| 1, `NO: internal-<...>` ("Treat it like exit code 5", [verifier/docs/output.md §Rejection names](https://github.com/anthropics/FlashProve/blob/9e2bdd8ff5bf9c62f18263d7dac189b0400b260c/verifier/docs/output.md#rejection-names)) | `no_verdict` | |
| 5, `NOT CHECKED: <name>` | `no_verdict` | |
| 2 (wrong call or unreadable file), 3 (`PART PASSED`), 4 (`PLAN ONLY`), 14 (`NOT-A-VERIFICATION`), 15 (no output) | `invalid_call` | |
| Any other exit code, signal termination, exit 0 with an unrecognized last line, or exit 1 whose last line is not `NO: <name>` | None (`verify` exits non-zero) | |

Note that the currently pinned image (`sha256:12611db7…` in `system.yaml`) was built from adapter commit `aa5f31f` prior to the 2026-11-15 mapping update, so in that image any exit 1 maps to `reject` regardless of its final line. No stored verdict is affected because no archived run contains `NO: internal-` or an exit 1 without `NO: `. Runs using the pinned image continue to use that earlier mapping until the image is rebuilt from this adapter and repinned with its new adapter commit (RFC-0014 B7).

Under the published configuration, the acceptance policy is exact match ([examples/maverick/README.md#L287-L289](https://github.com/anthropics/FlashProve/blob/9e2bdd8ff5bf9c62f18263d7dac189b0400b260c/examples/maverick/README.md#L287-L289)), so accepted proofs finish with `YES`. The adapter checks only this exit-code and last-line mapping rather than the rest of upstream's client checklist (such as the proof-of-work line and `result-v1` fields, [verifier/docs/output.md#L121-L131](https://github.com/anthropics/FlashProve/blob/9e2bdd8ff5bf9c62f18263d7dac189b0400b260c/verifier/docs/output.md#L121-L131)), though full raw output is preserved in the step log.

Because `isk/` contains subdirectories with identical filenames (`leaf/0/count.bin` and `anchor/count.bin`, [docs/operators-duties.md#L188-L198](https://github.com/anthropics/FlashProve/blob/9e2bdd8ff5bf9c62f18263d7dac189b0400b260c/docs/operators-duties.md#L188-L198)) while the harness stores commitment files flat by basename, the adapter archives `isk/` into a single tar file. `commit` deletes the original `isk/` after creating the tar, and `prove` unpacks the harness's read-only archive into a fresh `/io/state/prove/isk` directory with mode `0700` so `cp_prove` can lock it and append to `count.bin` ([examples/maverick/README.md#L219-L222](https://github.com/anthropics/FlashProve/blob/9e2bdd8ff5bf9c62f18263d7dac189b0400b260c/examples/maverick/README.md#L219-L222); [docs/service.md#L146-L159](https://github.com/anthropics/FlashProve/blob/9e2bdd8ff5bf9c62f18263d7dac189b0400b260c/docs/service.md#L146-L159)). The verifier never has access to `/io/state`. Upstream reports an average proof size of 18.78 MB ([guide/performance.md#L21](https://github.com/anthropics/FlashProve/blob/9e2bdd8ff5bf9c62f18263d7dac189b0400b260c/guide/performance.md#L21)); each proof directory holds `response.proof` and the 4-byte `response.y`.

## What `commit` needs that the image does not make

`cp_commit` and `cp_prove` expect a weights directory containing the five GGUF files alongside the fit artifacts `wsums.txt` and `fold.txt` (`eres 10`, `qkrows asis`), plus a config directory holding `policy.txt`, `KL.bin`, and `layout.txt` from `prover/examples/target_full_f2` ([examples/maverick/run.sh#L1451-L1500](https://github.com/anthropics/FlashProve/blob/9e2bdd8ff5bf9c62f18263d7dac189b0400b260c/examples/maverick/run.sh#L1451-L1500)).

**`setup`** executes upstream's `fit` stage offline into `/io/fit` in the exact order of `run.sh`:

1. Runs `scales/make_calibration_set.py` using the three upstream-specified inputs ([scales/README.md, "The calibration set"](https://github.com/anthropics/FlashProve/blob/9e2bdd8ff5bf9c62f18263d7dac189b0400b260c/scales/README.md#the-calibration-set)): the WikiText-2 raw training split and the Llama 2 and Llama 4 tokenizers. All three are downloaded at image build time and verified by upstream's SHA-256 digests. Because Meta's tokenizer repositories are gated, the image fetches byte-identical ungated copies (`TheBloke/Llama-2-7B-Chat-fp16` and `unsloth/Llama-4-Maverick-17B-128E-Instruct`, pinned in `inputs.lock`). The script independently verifies all three input hashes and the output calibration set hash.
2. Runs `bin/weight_sums --eres 10` to generate `wsums.txt` and checks its digest against `model/wsums.txt` in [examples/maverick/expected.txt](https://github.com/anthropics/FlashProve/blob/9e2bdd8ff5bf9c62f18263d7dac189b0400b260c/examples/maverick/expected.txt).
3. Writes `fold.txt` and `layout.txt` as `run.sh` does. Because `/models` is mounted read-only, the five GGUF weight files are reflink-cloned (`FICLONE`, falling back to a full copy when the filesystem does not support reflinks) into `/io/fit/weights` alongside `wsums.txt` and `fold.txt`; `cp_commit` rejects symlinks and multi-link hard links to weight files ([examples/maverick/README.md#L260-L263](https://github.com/anthropics/FlashProve/blob/9e2bdd8ff5bf9c62f18263d7dac189b0400b260c/examples/maverick/README.md#L260-L263)).
4. Runs `scales/calibrate.py --device cuda --eres 10` on the GPU to fit scales, followed by `scales/words_to_policy.py` to write `policy.txt` and `KL.bin`. `KL.bin` is checked against `config/KL.bin` in `expected.txt`; upstream notes that "The scales come from one float32 pass on the GPU, and its rounding can differ between GPU models, drivers and torch's CUDA libraries" ([examples/maverick/run.sh#L1500-L1501](https://github.com/anthropics/FlashProve/blob/9e2bdd8ff5bf9c62f18263d7dac189b0400b260c/examples/maverick/run.sh#L1500-L1501)). Any digest mismatch aborts `setup` before committing.

To support steps 1 and 4, the image includes Python 3.13 with upstream's hash-locked `requirements.txt` (torch 2.9.1 with CUDA 12.8 wheels). Upstream reports "5 to 6 minutes" for `bin/weight_sums` and 127 s for `scales/calibrate.py` ([examples/maverick/figures.txt](https://github.com/anthropics/FlashProve/blob/9e2bdd8ff5bf9c62f18263d7dac189b0400b260c/examples/maverick/figures.txt)). On filesystems without reflink support, copying the five weights adds 232 GB to `/io`.

## Machine needs

Upstream resource figures for the public 4-bit Maverick files on a single H100 80 GB (grade `external`, tier `reported`, FlashProve at the pinned commit):

- **Host and sandbox:** Requires an x86-64 CPU with SHA extensions and a container runtime permitting `madvise(MADV_WIPEONFORK)`; otherwise `cp_commit` and `cp_prove` exit immediately at startup ([prover/docs/build.md#L6](https://github.com/anthropics/FlashProve/blob/9e2bdd8ff5bf9c62f18263d7dac189b0400b260c/prover/docs/build.md#L6)). For instance, gVisor blocks this syscall (#68). `cp_verify` requires neither.
- **Host memory:** `run.sh` refuses to start `commit` with less than 330 GB free RAM or `prove` with less than 290 GB free ([examples/maverick/README.md#L68-L72](https://github.com/anthropics/FlashProve/blob/9e2bdd8ff5bf9c62f18263d7dac189b0400b260c/examples/maverick/README.md#L68-L72)). Peak RSS (excluding page cache) is 299.6 GB during commit and 269.7 GB during batch-24 proving ([guide/performance.md#L25](https://github.com/anthropics/FlashProve/blob/9e2bdd8ff5bf9c62f18263d7dac189b0400b260c/guide/performance.md#L25)). `cp_verify` peaked at 3.53 GB with 24 threads ([guide/performance.md#L23](https://github.com/anthropics/FlashProve/blob/9e2bdd8ff5bf9c62f18263d7dac189b0400b260c/guide/performance.md#L23)).
- **Disk:** 245 GB total on local storage (232.1 GB weights, 10 GB for `commit`, 1 GB for `prove`, [examples/maverick/README.md#L72-L73](https://github.com/anthropics/FlashProve/blob/9e2bdd8ff5bf9c62f18263d7dac189b0400b260c/examples/maverick/README.md#L72-L73)). This adapter also stores `isk.tar` and its unpacked directory under `/io/state` (2.15 GB each per upstream's size) plus ~19 MB per proof ([driver/README.md#L105](https://github.com/anthropics/FlashProve/blob/9e2bdd8ff5bf9c62f18263d7dac189b0400b260c/driver/README.md#L105)).
- **Runtime:** Committing takes ~39 minutes once per commitment ([guide/performance.md#L19](https://github.com/anthropics/FlashProve/blob/9e2bdd8ff5bf9c62f18263d7dac189b0400b260c/guide/performance.md#L19)), or 2,307.45 to 2,343.76 s in upstream's timed runs ([#L95](https://github.com/anthropics/FlashProve/blob/9e2bdd8ff5bf9c62f18263d7dac189b0400b260c/guide/performance.md#L95)). At batch 24 for five batches, `cp_prove` ran 1,208.4 to 1,236.4 s end-to-end ([#L86](https://github.com/anthropics/FlashProve/blob/9e2bdd8ff5bf9c62f18263d7dac189b0400b260c/guide/performance.md#L86)), including 68.1 to 79.0 s of startup ([#L19](https://github.com/anthropics/FlashProve/blob/9e2bdd8ff5bf9c62f18263d7dac189b0400b260c/guide/performance.md#L19)). At batch 1, upstream reports 58.796 ± 0.50 s per request (steady, n = 3, six batches per session, [#L10](https://github.com/anthropics/FlashProve/blob/9e2bdd8ff5bf9c62f18263d7dac189b0400b260c/guide/performance.md#L10)) without a total session time. `cp_verify` takes ~21 s single-threaded ([#L23](https://github.com/anthropics/FlashProve/blob/9e2bdd8ff5bf9c62f18263d7dac189b0400b260c/guide/performance.md#L23)). All of these fit comfortably inside the RFC-0005 default timeouts (`commit` 14,400 s, `prove` 43,200 s).

## CPU binding

Upstream recommends pinning `cp_commit` and `cp_prove` to CPUs on the GPU's NUMA node. Each binary automatically restricts its threads to CPUs within its allowed affinity mask and prints `# GPU … is on NUMA node …; this thread is pinned to … of its CPUs` (if that line is absent, no pinning occurred, [guide/performance.md#L95](https://github.com/anthropics/FlashProve/blob/9e2bdd8ff5bf9c62f18263d7dac189b0400b260c/guide/performance.md#L95)). Upstream's timed runs bound every process to 24 CPUs on the GPU's NUMA node ([#L93](https://github.com/anthropics/FlashProve/blob/9e2bdd8ff5bf9c62f18263d7dac189b0400b260c/guide/performance.md#L93)). The harness handles this via `--cpuset-cpus` and `--cpuset-mems` (RFC-0005 §Container invocation) targeting the GPU's NUMA node, so the adapter passes no pinning flags. Confirm that the pinning message appears in the `commit` and `prove` logs on the GPU host.

## Known deviations from upstream's measuring setup

- **Fresh commitment per run (`-M 1`).** Because a proving session consumes leaf-table entries permanently, upstream asks for a dedicated commitment per measurement ([driver/README.md#L103](https://github.com/anthropics/FlashProve/blob/9e2bdd8ff5bf9c62f18263d7dac189b0400b260c/driver/README.md#L103)) and reports figures for one leaf table ([guide/performance.md#L21](https://github.com/anthropics/FlashProve/blob/9e2bdd8ff5bf9c62f18263d7dac189b0400b260c/guide/performance.md#L21)).
- **Masking enabled (no `-public-weights`).** While the Maverick walkthrough script passes `-public-weights` ([examples/maverick/README.md#L52-L59](https://github.com/anthropics/FlashProve/blob/9e2bdd8ff5bf9c62f18263d7dac189b0400b260c/examples/maverick/README.md#L52-L59)), upstream's timed runs and "Reproduce the numbers" command omit it so masking stays on.
- **Prompts.** Uses the benchmark workload's 1,024-token windows (RFC-0003) instead of calibration windows or `measure_rate.py`'s prompts ([guide/performance.md#L93](https://github.com/anthropics/FlashProve/blob/9e2bdd8ff5bf9c62f18263d7dac189b0400b260c/guide/performance.md#L93)).
- **Batch count.** `fp-maverick-w1024-b1` runs five batches, whereas upstream's batch-1 timed runs used six ([guide/performance.md#L91](https://github.com/anthropics/FlashProve/blob/9e2bdd8ff5bf9c62f18263d7dac189b0400b260c/guide/performance.md#L91)).
- **Release timing.** Upstream timestamps a batch using the latest mtime of its proof files ([driver/README.md#L55](https://github.com/anthropics/FlashProve/blob/9e2bdd8ff5bf9c62f18263d7dac189b0400b260c/driver/README.md#L55)), whereas the harness records the adapter's atomic rename (up to one 50 ms polling interval later), which is why `steady_approximate: true` is set.
- **No response-tag check.** Unlike `measure_rate.py`, which validates each response tag ([docs/service.md#L293-L303](https://github.com/anthropics/FlashProve/blob/9e2bdd8ff5bf9c62f18263d7dac189b0400b260c/docs/service.md#L293-L303)), the adapter matches responses by request ID and delegates verification entirely to `cp_verify`.
- **Copying `isk/`.** The secret-key directory is archived and unpacked once per session via the harness commit record (see above). Upstream warns against copying `isk/` to bypass a rejection ([docs/service.md#L158-L159](https://github.com/anthropics/FlashProve/blob/9e2bdd8ff5bf9c62f18263d7dac189b0400b260c/docs/service.md#L158-L159)); here each unpacked copy is used only for the single session belonging to its fresh commitment.
- **Verification concurrency.** Runs sequentially after `cp_prove` exits on the verifier profile (`-j 8` on 8 CPUs, or `-j 1` for `verify.single_thread`), whereas `measure_rate.py` runs several `-j 4` verifications in parallel.

## Upstream's rejected proofs: not registered as system controls

Although RFC-0008 §System-specific controls mentions FlashProve's [examples/rejected-proofs](https://github.com/anthropics/FlashProve/tree/9e2bdd8ff5bf9c62f18263d7dac189b0400b260c/examples/rejected-proofs) as potential `fixture_proof` controls expecting `rejected` (issue #70), none are registered and this system has no `controls.yaml`. Every example fails RFC-0008 Q4 ("registered only if the harness can regenerate its commitment through the adapter's `commit` step; otherwise it is listed in the adapter README and not run as a control") and requires parameters that the adapter's `verify` job does not supply:

1. **No static altered proof files exist.** As upstream notes, "No altered files are stored here." Instead, `try_altered_copies.py` dynamically mutates files from `examples/accepted-proof` or `examples/accepted-proof-clipped-gap` one at a time and runs the verifier on each mutation ([README.md#L3](https://github.com/anthropics/FlashProve/blob/9e2bdd8ff5bf9c62f18263d7dac189b0400b260c/examples/rejected-proofs/README.md#L3)).
2. **The commitment is bundled with the example (INV-CTRL-6).** The script reads the ID from `ID.txt` ("For this demonstration only. In a real check the commitment ID comes from where the commitment is published, never from files that come with a proof", [try_altered_copies.py#L164-L166](https://github.com/anthropics/FlashProve/blob/9e2bdd8ff5bf9c62f18263d7dac189b0400b260c/examples/rejected-proofs/try_altered_copies.py#L164-L166)) along with the example's `config/` and `ivk/` ([#L248](https://github.com/anthropics/FlashProve/blob/9e2bdd8ff5bf9c62f18263d7dac189b0400b260c/examples/rejected-proofs/try_altered_copies.py#L248)). The underlying model is synthetic (8 layers, 4 routed experts, 512-token vocabulary, [accepted-proof/README.md#L54](https://github.com/anthropics/FlashProve/blob/9e2bdd8ff5bf9c62f18263d7dac189b0400b260c/examples/accepted-proof/README.md#L54)) with no published secret directory, and "`cp_commit` draws a fresh seed each time, so a run of your own gives another commitment ID, other files in `ivk/` and another proof" ([#L75](https://github.com/anthropics/FlashProve/blob/9e2bdd8ff5bf9c62f18263d7dac189b0400b260c/examples/accepted-proof/README.md#L75)). Because the harness cannot reproduce that commitment, verifying against a run's own commitment would reject on model mismatch rather than on the targeted tamper.
3. **Incompatible request ranges and policies.** Our `verify` builds requests with `r = P - 1, e = P + R - 1` (whole reply) or `r = T - 1, e = T` with `-next-token` (single token). Upstream's examples use `r = 60, e = 64` ([accepted-proof/README.md#L44](https://github.com/anthropics/FlashProve/blob/9e2bdd8ff5bf9c62f18263d7dac189b0400b260c/examples/accepted-proof/README.md#L44)) and `r = 15, e = 47` ([accepted-proof-clipped-gap/README.md#L46](https://github.com/anthropics/FlashProve/blob/9e2bdd8ff5bf9c62f18263d7dac189b0400b260c/examples/accepted-proof-clipped-gap/README.md#L46)), and "With any other request, the call ends in `NOT-A-VERIFICATION` at best" ([verifier/README.md#L122-L125](https://github.com/anthropics/FlashProve/blob/9e2bdd8ff5bf9c62f18263d7dac189b0400b260c/verifier/README.md#L122-L125)), returning exit code 14 (`invalid_call`). The clipped-gap set also requires `-policy` values parsed from `policy.txt` ([rejected-proofs/README.md#L50](https://github.com/anthropics/FlashProve/blob/9e2bdd8ff5bf9c62f18263d7dac189b0400b260c/examples/rejected-proofs/README.md#L50)), neither of which the job schema carries.

Upstream describes this suite as "a demonstration, not a test of soundness: a cheating prover would not flip bits in an honest proof" ([README.md#L56](https://github.com/anthropics/FlashProve/blob/9e2bdd8ff5bf9c62f18263d7dac189b0400b260c/examples/rejected-proofs/README.md#L56)). Its ten primary cases ([altered_copies.tsv#L22-L31](https://github.com/anthropics/FlashProve/blob/9e2bdd8ff5bf9c62f18263d7dac189b0400b260c/examples/rejected-proofs/altered_copies.tsv#L22-L31)) are listed below:

| Row (upstream's description) | File altered | Expected last line |
|---|---|---|
| one bit of the proof changed | `example.proof` | `NO: proof-refused` |
| the proof's last byte cut off | `example.proof` | `NO: proof-refused` |
| one byte added to the proof | `example.proof` | `NO: proof-refused` |
| one bit of ivk/key.bin changed | `ivk/key.bin` | `NO: key-refused` |
| one bit of ivk/leaf/0.bin changed | `ivk/leaf/0.bin` | `NO: entry-refused` |
| a prompt token changed | `example.req` | `NO: proof-refused` |
| a checked reply token changed | `example.req` | `NO: proof-refused` |
| another token after the request | `example.y` | `NO: reply-differs` |
| another scale in KL.bin | `config/KL.bin` | `NO: model-statement` |
| another commitment ID | the value after `-id` | `NO: model-statement` |

- [altered_copies_clipped_gap.tsv](https://github.com/anthropics/FlashProve/blob/9e2bdd8ff5bf9c62f18263d7dac189b0400b260c/examples/rejected-proofs/altered_copies_clipped_gap.tsv#L5-L14) repeats the same ten cases on the clipped-gap example, changing only the `example.y` row to "example.y is 1 where it must be 0", expecting `NO: statement-range` ([#L12](https://github.com/anthropics/FlashProve/blob/9e2bdd8ff5bf9c62f18263d7dac189b0400b260c/examples/rejected-proofs/altered_copies_clipped_gap.tsv#L12)).
- [every_kind_of_item.tsv](https://github.com/anthropics/FlashProve/blob/9e2bdd8ff5bf9c62f18263d7dac189b0400b260c/examples/rejected-proofs/every_kind_of_item.tsv) defines 79 byte-offset mutations "meant to cover each sort of item in the files (a tag, a root, an element of a message, an answer, a nonce, a salt, a digest and so on), not every field of every round", tied to specific byte positions "so they fit the stored files alone" ([README.md#L40](https://github.com/anthropics/FlashProve/blob/9e2bdd8ff5bf9c62f18263d7dac189b0400b260c/examples/rejected-proofs/README.md#L40)).

Many of these mutations overlap with our shared verifier-side controls (RFC-0008 §Shared controls), which operate on live run proofs and commitments: flipping a proof bit (C6), truncating the last byte (C5), altering a prompt token (C2), and altering the claimed output token (C1). Mutations to `ivk/`, `config/`, and `-id` target artifacts supplied from the harness commit record. Registering upstream's examples directly would require resolving RFC-0008 Q4 and Q5 and adding job fields for `r`, `e`, and policy parameters.

## Values for `system.yaml`

`system.yaml` configures the following values alongside the pushed image digest:

```yaml
deterministic_proofs: false
incremental_proofs: true
proofs:
  granularity: "request"
  tokens_covered: "window"
  steady_boundary: "first_proof"
  steady_approximate: true
  verify_reads:
    read: ["response.proof"]
    not_read:
      - part: "response.y"
        reason: "verify never reads it: cp_verify checks a token file the adapter writes from the job's claimed_output, which the harness takes from its own record (AGENTS.md rule 6); C1 changes that token"
forbidden_flags: ["-public-weights", "-keep-for-the-audit"]
```

- `proofs.granularity: request`: Each request yields one proof file, `<id>.proof` ([docs/service.md#L84-L86](https://github.com/anthropics/FlashProve/blob/9e2bdd8ff5bf9c62f18263d7dac189b0400b260c/docs/service.md#L84-L86)).
- `proofs.tokens_covered: window`: A proof certifies the next token following a 1,024-token window, and upstream throughput counts `T = 1,024` prompt tokens per request ([driver/README.md#L55](https://github.com/anthropics/FlashProve/blob/9e2bdd8ff5bf9c62f18263d7dac189b0400b260c/driver/README.md#L55); [guide/performance.md#L15](https://github.com/anthropics/FlashProve/blob/9e2bdd8ff5bf9c62f18263d7dac189b0400b260c/guide/performance.md#L15)).
- `incremental_proofs: true` and `steady_boundary: first_proof`: `cp_prove` releases each batch upon completion ([docs/service.md#L22-L30](https://github.com/anthropics/FlashProve/blob/9e2bdd8ff5bf9c62f18263d7dac189b0400b260c/docs/service.md#L22-L30)), and upstream defines steady rate as batch requests times `T` divided by the mean interval between successive releases ([driver/README.md#L55](https://github.com/anthropics/FlashProve/blob/9e2bdd8ff5bf9c62f18263d7dac189b0400b260c/driver/README.md#L55)).
- `steady_approximate: true`: RFC-0004 treats FlashProve's steady rate as approximate because of the 50 ms polling lag noted above.
- `deterministic_proofs: false`: Upstream does not guarantee identical proof bytes for identical inputs; proofs incorporate non-repeating random masks ([docs/operators-duties.md#L180](https://github.com/anthropics/FlashProve/blob/9e2bdd8ff5bf9c62f18263d7dac189b0400b260c/docs/operators-duties.md#L180)), and upstream notes that `-memory` "should not change any byte of a proof, but no test compares the bytes" ([docs/service.md#L482](https://github.com/anthropics/FlashProve/blob/9e2bdd8ff5bf9c62f18263d7dac189b0400b260c/docs/service.md#L482)).
- `forbidden_flags`: `-public-weights` disables weight hiding ("With this option the weights are not hidden", [docs/operators-duties.md#L200-L204](https://github.com/anthropics/FlashProve/blob/9e2bdd8ff5bf9c62f18263d7dac189b0400b260c/docs/operators-duties.md#L200-L204)), and `-keep-for-the-audit` retains files that together with the seed expose every mask ([#L198](https://github.com/anthropics/FlashProve/blob/9e2bdd8ff5bf9c62f18263d7dac189b0400b260c/docs/operators-duties.md#L198)). Upstream exposes no flag that weakens `cp_verify` acceptance (lowering `-bits` or omitting `-id` always fails, [verifier/README.md#L108-L133](https://github.com/anthropics/FlashProve/blob/9e2bdd8ff5bf9c62f18263d7dac189b0400b260c/verifier/README.md#L108-L133)).
- `proofs.verify_reads`: `verify` reads only `response.proof` and ignores `response.y`. It writes the token file passed to `cp_verify` from the job's `claimed_output` (taken from the harness record rather than proof files per AGENTS.md rule 6 and [RFC-0008 §Parts the verifier reads](../../rfcs/0008-negative-controls.md#parts-the-verifier-reads), matching how clients invoke `cp_verify` in [docs/verifying.md](https://github.com/anthropics/FlashProve/blob/9e2bdd8ff5bf9c62f18263d7dac189b0400b260c/docs/verifying.md)). Because mutating `response.y` never reaches `cp_verify`, C5, C6, and C8 target `response.proof` exclusively and record `response.y` in `parts_not_read`, while C1 tests tampered output tokens via `claimed_output`.
- `max_proof_parts` and `max_proof_bytes`: Not stated upstream; default caps apply (two parts, ~18.78 MB per proof).

- The CUDA Python packages are hash-locked in `cuda-requirements.txt` (`--require-hashes`), installed during the `fetch` stage (B2) into `/opt/cuda-13.2.86` rather than a home directory.

## Level 1

RFC-0018 fixes a single request format for Level 1: 512 prompt tokens, a 512-token greedy reply ignoring end tokens, and verification over every reply token. The Maverick workload `l1-maverick-p512-o512` runs 24 requests per batch across 5 batches per session (120 requests total), matching upstream's headline batch-24 configuration ([guide/performance.md#L8-L12](https://github.com/anthropics/FlashProve/blob/9e2bdd8ff5bf9c62f18263d7dac189b0400b260c/guide/performance.md#L8-L12); [docs/figures.tsv#L63](https://github.com/anthropics/FlashProve/blob/9e2bdd8ff5bf9c62f18263d7dac189b0400b260c/docs/figures.tsv#L63)). The analysis below comes from inspecting upstream at the pinned commit; nothing in this section had been executed on GPU when written.

### The request and the range

- Each window holds exactly `T` tokens (prompt, reply, then zero padding), where `T = 2^lt = 1,024` at full scale ([docs/verifying.md#L115-L117](https://github.com/anthropics/FlashProve/blob/9e2bdd8ff5bf9c62f18263d7dac189b0400b260c/docs/verifying.md#L115-L117)), determined from `lt 10` on line 34 of `prover/examples/target_full_f2/policy.txt`. The adapter reads `T` dynamically from the commitment's `policy.txt`.
- Upstream specifies: "To check a whole reply of R tokens (its end token included) after a prompt of P tokens, set r = P - 1 and e = P + R - 1" ([docs/verifying.md#L119-L123](https://github.com/anthropics/FlashProve/blob/9e2bdd8ff5bf9c62f18263d7dac189b0400b260c/docs/verifying.md#L119-L123)). Here `r = 511` and `e = 1,023`, covering positions 511 through 1,022 and certifying all 512 reply tokens at indices 512 through 1,023 (RFC-0018 AD-1).
- Because `P + R = 1,024 = T`, the window is completely filled with no padding needed, and because `e < T`, `y` is unused and the token file contains 0 ([docs/verifying.md#L125-L128](https://github.com/anthropics/FlashProve/blob/9e2bdd8ff5bf9c62f18263d7dac189b0400b260c/docs/verifying.md#L125-L128)). The adapter rejects `P + R > T` (the `e = T` one-past-window case is unused here) and pads shorter windows (`P + R < T`) with token 0, matching both upstream sides ([docs/verifying.md#L130-L132](https://github.com/anthropics/FlashProve/blob/9e2bdd8ff5bf9c62f18263d7dac189b0400b260c/docs/verifying.md#L130-L132); layout in [verifier/docs/output.md#L364-L368](https://github.com/anthropics/FlashProve/blob/9e2bdd8ff5bf9c62f18263d7dac189b0400b260c/verifier/docs/output.md#L364-L368)).
- `verify` builds the request file and 4-byte zero token file from `request` and `claimed_output` and invokes `cp_verify CONFIG IVK REQUEST TOKEN PROOF -id ID -j N` ([docs/verifying.md#L176](https://github.com/anthropics/FlashProve/blob/9e2bdd8ff5bf9c62f18263d7dac189b0400b260c/docs/verifying.md#L176)) without `-next-token` (passing `-next-token` on a range request triggers exit code 14, [verifier/docs/output.md#L314-L315](https://github.com/anthropics/FlashProve/blob/9e2bdd8ff5bf9c62f18263d7dac189b0400b260c/verifier/docs/output.md#L314-L315)). Accepted exact-match calls end with `YES` ([docs/verifying.md#L231-L234](https://github.com/anthropics/FlashProve/blob/9e2bdd8ff5bf9c62f18263d7dac189b0400b260c/docs/verifying.md#L231-L234)). Because C1 mutates a token inside `claimed_output`, which `verify` writes into the request file, altering the first, last, or any interior reply token reaches `cp_verify` directly.
- The adapter does not parse the `covered:` output line (`r=`, `e=`, `tokens=`) mentioned in point 5 of upstream's client acceptance checklist ([docs/verifying.md#L235-L239](https://github.com/anthropics/FlashProve/blob/9e2bdd8ff5bf9c62f18263d7dac189b0400b260c/docs/verifying.md#L235-L239)), though full stdout remains in the step log.

### The reply route (RFC-0018 AD-3)

Under exact match, a proof succeeds only if every covered token is the committed integer model's argmax ([integer_model/README.md#L166-L169](https://github.com/anthropics/FlashProve/blob/9e2bdd8ff5bf9c62f18263d7dac189b0400b260c/integrations/vllm/integer_model/README.md#L166-L169)), so replies must be generated by that model. Upstream ships `integrations/vllm/integer_model/` under Apache-2.0 ([LICENSE](https://github.com/anthropics/FlashProve/blob/9e2bdd8ff5bf9c62f18263d7dac189b0400b260c/integrations/vllm/integer_model/LICENSE); [pyproject.toml#L18-L19](https://github.com/anthropics/FlashProve/blob/9e2bdd8ff5bf9c62f18263d7dac189b0400b260c/integrations/vllm/integer_model/pyproject.toml#L18-L19)), with a NOTICE referencing `ggml` and `gguf-py` (MIT) and BLAKE2 reference code (CC0 1.0). Its vLLM dependency set lists 150 MIT/BSD/Apache-2.0/PSF packages, 12 other permissive packages, 3 MPL/LGPL packages, 24 NVIDIA proprietary packages, and 5 packages with no licence metadata ([vllm/LICENCES.tsv#L5](https://github.com/anthropics/FlashProve/blob/9e2bdd8ff5bf9c62f18263d7dac189b0400b260c/integrations/vllm/LICENCES.tsv#L5)).

Upstream documents two ways to execute the integer model: serving via a vLLM 0.29.0 plugin, or calling the Python API (`integer_model.load_from_folder(folder, "cuda")`, `new_sequence()`, `extend()`, [README.md#L12-L19](https://github.com/anthropics/FlashProve/blob/9e2bdd8ff5bf9c62f18263d7dac189b0400b260c/integrations/vllm/integer_model/README.md#L12-L19), [#L59-L68](https://github.com/anthropics/FlashProve/blob/9e2bdd8ff5bf9c62f18263d7dac189b0400b260c/integrations/vllm/integer_model/README.md#L59-L68)). Because upstream's "A request from the model's own reply" example uses the Python API directly ([#L112-L164](https://github.com/anthropics/FlashProve/blob/9e2bdd8ff5bf9c62f18263d7dac189b0400b260c/integrations/vllm/integer_model/README.md#L112-L164)), `prove` runs that Python API in a dedicated subprocess that exits before `cp_prove` launches:

1. **Float64 arithmetic check:** Runs `python -B -m pytest -p no:cacheprovider -rs tests/test_arithmetic_edges.py` with `INTEGER_MODEL_TEST_DEVICE=cuda` inside the package directory, as required before serving on a GPU: "Every test should pass, and none be skipped. If one fails or is skipped, do not serve from that GPU" ([OPERATING.md#L542-L559](https://github.com/anthropics/FlashProve/blob/9e2bdd8ff5bf9c62f18263d7dac189b0400b260c/integrations/vllm/integer_model/OPERATING.md#L542-L559)). Any non-zero exit or non-passing summary stops `prove`.
2. **Model folder setup:** Populates `/io/state/prove/integer-model` with `policy.txt`, `KL.bin`, and `integer_model.json` pointing to the five GGUF files and `/io/fit/weights` (`wsums.txt` and `fold.txt`), setting `"verify_sums": true` ([OPERATING.md#L59-L86](https://github.com/anthropics/FlashProve/blob/9e2bdd8ff5bf9c62f18263d7dac189b0400b260c/integrations/vllm/integer_model/OPERATING.md#L59-L86), [#L160-L162](https://github.com/anthropics/FlashProve/blob/9e2bdd8ff5bf9c62f18263d7dac189b0400b260c/integrations/vllm/integer_model/OPERATING.md#L160-L162)). Passes `sha256` to `load_from_folder` covering the five small files, using upstream's published digests from `examples/maverick/expected.txt` for `KL.bin` and `wsums.txt` ([integer_model/model.py#L648-L656](https://github.com/anthropics/FlashProve/blob/9e2bdd8ff5bf9c62f18263d7dac189b0400b260c/integrations/vllm/integer_model/integer_model/model.py#L648-L656)).
3. **Greedy generation:** For each prompt, calls `extend` once on the prompt and then once per generated token until 512 tokens are produced, ignoring end tokens (following README lines 124-135 on the real GGUF folder). The resulting replies populate both the proof request windows and `claimed_output`.

What upstream documentation states versus leaves unstated for this path:

- **Stated.** Single sequence at a time, single GPU, windows up to 1,024 tokens ([README.md#L18-L19](https://github.com/anthropics/FlashProve/blob/9e2bdd8ff5bf9c62f18263d7dac189b0400b260c/integrations/vllm/integer_model/README.md#L18-L19)). At full size: 238 GB free host RAM (mostly pinned), 36 GB peak GPU memory, 22 to 25 minutes startup when verifying every tensor, and 0.60 to 0.62 s per token after a 3-token prompt ([OPERATING.md#L32-L38](https://github.com/anthropics/FlashProve/blob/9e2bdd8ff5bf9c62f18263d7dac189b0400b260c/integrations/vllm/integer_model/OPERATING.md#L32-L38)). The loader raises `NotEnoughMemory` unless free host memory covers the weights plus 1/32 ([#L40-L43](https://github.com/anthropics/FlashProve/blob/9e2bdd8ff5bf9c62f18263d7dac189b0400b260c/integrations/vllm/integer_model/OPERATING.md#L40-L43)). Because `cp_prove` refuses to launch if more than 2 GiB of GPU memory is in use, upstream's single-GPU demo stops vLLM before proving (`--stop-vllm-to-prove`, [vllm/README.md#L90](https://github.com/anthropics/FlashProve/blob/9e2bdd8ff5bf9c62f18263d7dac189b0400b260c/integrations/vllm/README.md#L90)), noting that simultaneous serving and proving requires a second GPU and sufficient host RAM for both, which has never been tested at full size ([#L104](https://github.com/anthropics/FlashProve/blob/9e2bdd8ff5bf9c62f18263d7dac189b0400b260c/integrations/vllm/README.md#L104)). Running generation in a subprocess that exits prior to `cp_prove` satisfies this on one GPU.
- **Stated for non-release runs.** Upstream ran four full-size vLLM sessions on the public 4-bit weights (16 greedy replies each), proving and verifying all under exact match ([OPERATING.md#L583](https://github.com/anthropics/FlashProve/blob/9e2bdd8ff5bf9c62f18263d7dac189b0400b260c/integrations/vllm/integer_model/OPERATING.md#L583)); three stopped vLLM during proving with `--max-tokens 64` ([integrations/LIMITS.md#L117-L120](https://github.com/anthropics/FlashProve/blob/9e2bdd8ff5bf9c62f18263d7dac189b0400b260c/integrations/LIMITS.md#L117-L120)). Upstream clarifies that "None of them was made on the released programs, or with the scripts exactly as they are in this repository" ([#L110](https://github.com/anthropics/FlashProve/blob/9e2bdd8ff5bf9c62f18263d7dac189b0400b260c/integrations/LIMITS.md#L110)). The full-size example request uses 1,000 tokens generated on synthetic weights ([integrations/README.md#L56-L66](https://github.com/anthropics/FlashProve/blob/9e2bdd8ff5bf9c62f18263d7dac189b0400b260c/integrations/README.md#L56-L66)).
- **Not stated.** Calling the Python API directly at full size on real weights (upstream's full-size runs went through vLLM), generating 512-token replies on real weights, per-token decode latency after a 512-token prompt, or 512-token prefill time. Also note that finishing generation without `RangeConditionFailed` only verifies range conditions on evaluated positions, whereas `cp_prove` requires them across all `T` positions ([integer_model/model.py#L171-L175](https://github.com/anthropics/FlashProve/blob/9e2bdd8ff5bf9c62f18263d7dac189b0400b260c/integrations/vllm/integer_model/integer_model/model.py#L171-L175)). Because the final reply token is never fed back into `extend`, position 1,023 is checked only during `cp_prove`, which would emit `<id>.failed` and cause `prove` to exit non-zero.

**End tokens.** This route naturally obeys RFC-0018's EOS rule (keep greedily selected end tokens and continue generating). `extend` returns `first_argmax` across the full vocabulary `V` (lowest ID on ties) with no end-token masking ([integer_model/model.py#L297-L299](https://github.com/anthropics/FlashProve/blob/9e2bdd8ff5bf9c62f18263d7dac189b0400b260c/integrations/vllm/integer_model/integer_model/model.py#L297-L299); [arithmetic.py#L46-L54](https://github.com/anthropics/FlashProve/blob/9e2bdd8ff5bf9c62f18263d7dac189b0400b260c/integrations/vllm/integer_model/integer_model/arithmetic.py#L46-L54)); `model.py` has no concept of an end token, and the adapter loop unconditionally generates 512 tokens.

**No batching.** The package explicitly restricts inference to "greedy decoding, one sequence at a time, one GPU" ([README.md#L18-L19](https://github.com/anthropics/FlashProve/blob/9e2bdd8ff5bf9c62f18263d7dac189b0400b260c/integrations/vllm/integer_model/README.md#L18-L19)); the vLLM plugin rejects any `--max-num-seqs` other than 1 ([integer_model_vllm/model.py#L4](https://github.com/anthropics/FlashProve/blob/9e2bdd8ff5bf9c62f18263d7dac189b0400b260c/integrations/vllm/integer_model/integer_model_vllm/model.py#L4), [#L55](https://github.com/anthropics/FlashProve/blob/9e2bdd8ff5bf9c62f18263d7dac189b0400b260c/integrations/vllm/integer_model/integer_model_vllm/model.py#L55)), and `extend` accepts a single `Sequence` ([model.py#L222-L230](https://github.com/anthropics/FlashProve/blob/9e2bdd8ff5bf9c62f18263d7dac189b0400b260c/integrations/vllm/integer_model/integer_model/model.py#L222-L230)). The adapter therefore generates all 120 replies sequentially.

**Generation marks (RFC-0018 AD-4, CO-3).** `prove` atomically renames `/io/marks/.tmp-generation.start` to `generation.start` prior to the float64 check, and `.tmp-generation.end` to `generation.end` once the generation subprocess exits and before `cp_prove` begins. Between those two marks, the GPU is dedicated strictly to generating replies.

**Expected session time (estimate from upstream figures, grade `external`, not measured here).** Setup takes ~8 minutes plus copying 232 GB (5 to 6 min weight sums, 127 s calibration); commit takes 2,307 to 2,344 s; integer-model loading takes 22 to 25 min; sequential generation over `120 × 511` decode steps at 0.60 to 0.62 s takes 36,792 to 38,018 s (10.2 to 10.6 h), excluding unstated 512-token prefill and float64 check times; `cp_prove` adds 68 to 79 s startup plus ~1,210 to 1,240 s for five batches of 24 based on next-token runs (whole-reply proving at batch 24 ran at 108.67 vs 111.23 tokens/s, [guide/performance.md#L12-L17](https://github.com/anthropics/FlashProve/blob/9e2bdd8ff5bf9c62f18263d7dac189b0400b260c/guide/performance.md#L12-L17)). Total time is roughly 11.7 to 12.1 hours, ~87% spent in generation. Because the generation marks wrap loading and decoding, CO-3 attributes ~318 to 330 GPU-seconds per reply to generation on one GPU, compared to 7 to 10 GPU-seconds for proving (v0.1 H200 runs measured 7.06 to 7.20 GPU-s/reply for next-token proving). If 24-way batched generation existed at 0.60 to 0.62 s per step, generation would drop to ~26 minutes and a full session to ~2 hours, but upstream documents no batched integer-model route so the adapter does not attempt one.

Open RISK: upstream's exact-match whole-reply runs used different binaries/scripts and 64-token replies, leaving 512 + 512 on the released binaries untested (RFC-0018 RISK). Because the 0.60 to 0.62 s/token figure was measured after a 3-token prompt, the probe in `docs/runbooks/level-1.md` measures actual latency.

### Prompt side and reply side (RFC-0018 CO-10, proposed)

`prove` reports these phases, in this order. A part is named `<phase>__<part>`; CO-9's sum against the harness-timed prove call counts whole phases only.

| Phase | Seconds | Source |
|---|---|---|
| `float64_check` | the package's float64 check | the adapter's clock around `pytest` |
| `generate` | the generation process: its start, the load, every request's calls, its exit | the adapter's clock around the `-c` process |
| `generate__load` | `integer_model.load_from_folder` | the generation program's own clock, written to `/io/state/prove/generate-seconds.json` |
| `generate__prompt` | each request's prefill call, `extend(sequence, prompt)`, summed: 512 positions and the choice of the reply's first token | the same |
| `generate__reply` | each request's further calls, `extend(sequence, [token])` once a token, summed: 511 calls a request | the same |
| `spool` | the secret key extracted from `isk.tar` and the requests laid into `in/` | the adapter's clock |
| `cp_prove` | the `cp_prove` process | the adapter's clock |

- **What a call's time holds.** `extend` returns "an int64 tensor of n token ids on the CPU" ([model.py#L235-L236](https://github.com/anthropics/FlashProve/blob/9e2bdd8ff5bf9c62f18263d7dac189b0400b260c/integrations/vllm/integer_model/integer_model/model.py#L235-L236), the copy at [#L309](https://github.com/anthropics/FlashProve/blob/9e2bdd8ff5bf9c62f18263d7dac189b0400b260c/integrations/vllm/integer_model/integer_model/model.py#L309)), so the wall time of a call holds the GPU work it started. The program times its calls with `time.monotonic()` and changes no call, argument or output: the replies are the same bytes in `replies.jsonl`.
- **What the parts leave out.** The interpreter's start and the import of `integer_model` and torch, `new_sequence`, `free`, the writing of each reply and the process exit are in `generate` and in no part. The float64 check and the model folder are inside the generation marks (AD-4) and in no part either. On the board, the generation's rest (the marks less the prompt and reply parts) is apportioned by position (512 and 512), as is the whole proving, since `cp_prove` proves one window of 1,024 positions and prints no time per position.
- **`spool`.** Before this phase existed, the time between the generation's end and `cp_prove`'s start was in no phase. In the three stored v1.0 sessions of 120 replies it is below the 238 to 248 s from `generation.end` to the first released proof, under 1 % of their prove calls (28,340 to 28,890 s). In the stored session of one reply (2026-11-13) that bound is 95.8 s of a 1,746.2 s call, more than 1 %. The phase keeps the whole phases' sum within CO-9's 1 % without relying on such a bound.
- **When there are no parts.** If `generate-seconds.json` is unreadable, does not hold one value a request on each side, or its parts exceed `generate`, no part is reported and a warning says why; the replies and the proofs are kept.
- **The v1.0 records.** The four stored v1.0 sessions carry `adapter_phases: {}` because the harness of that release (commit `8512b94d`) wrote the field empty whatever the adapter reported. The harness has kept the reported phases since commit `09ccece0` (2026-11-26). So no stored FlashProve record holds phases, and the sides need a new session.
- **Identity.** The change is in the adapter alone. It changes `entrypoint`, so the image, its digest in `system.yaml` and the adapter commit a manifest records all change: the image must be rebuilt and re-pinned before a session reports these phases. Nothing is generated or proved differently, and `Dockerfile.score` stays layered on the pinned image.

### Scoring a reference reply (`score`, RFC-0018 AD-7)

`score` computes the integer model's greedy top choice (FI-10) and top 256 token probabilities (FI-12) at each position of a reference reply generated by another engine. `cp_prove` cannot supply these because it checks a single token or fixed window and "the programs have no option that prints an intermediate value" ([README.md L95-L97](https://github.com/anthropics/FlashProve/blob/9e2bdd8ff5bf9c62f18263d7dac189b0400b260c/integrations/vllm/integer_model/README.md#L95-L97)). The adapter therefore calls the same `integer_model` package used by `prove`, loading the verified fit folder (`setup` output with all tensors verified against `wsums.txt`) after running the float64 check:

```python
model.extend(sequence, prompt[:-1])
choices, gaps = model.extend(sequence, [prompt[-1], *reply[:-1]], gap_for=reply, record=record)
```

- This mirrors upstream's [`examples/score_reply.py`](https://github.com/anthropics/FlashProve/blob/9e2bdd8ff5bf9c62f18263d7dac189b0400b260c/integrations/vllm/integer_model/examples/score_reply.py#L126-L128), which "scores a reply that another engine served, in one forward pass" ([examples/README.md L31](https://github.com/anthropics/FlashProve/blob/9e2bdd8ff5bf9c62f18263d7dac189b0400b260c/integrations/vllm/integer_model/examples/README.md#L31)). `extend` returns "the argmax of the logits at the position of token_ids[i], with the lowest id on ties", and passing `gap_for` returns a gap that "is 0 exactly for the greedy choice" ([model.py, `extend`](https://github.com/anthropics/FlashProve/blob/9e2bdd8ff5bf9c62f18263d7dac189b0400b260c/integrations/vllm/integer_model/integer_model/model.py#L230-L242)). Since position `j` predicts token `j + 1`, the second call yields top tokens for all 512 reply positions. The adapter asserts that `gaps` is 0 if and only if the choice matches the reply token.
- Splitting the prompt across two `extend` calls has no effect because "The integers at a position depend only on the tokens up to it, not on how the tokens were divided into calls" ([model.py L232-L233](https://github.com/anthropics/FlashProve/blob/9e2bdd8ff5bf9c62f18263d7dac189b0400b260c/integrations/vllm/integer_model/integer_model/model.py#L232-L233)).
- **`record` is used for KL only.** Documented in `extend`'s docstring ("record(name, layer, tensor) receives named intermediate values ... after the layers x_last, aF, lam, first_choice", [model.py L252-L256](https://github.com/anthropics/FlashProve/blob/9e2bdd8ff5bf9c62f18263d7dac189b0400b260c/integrations/vllm/integer_model/integer_model/model.py#L252-L256)) and in `OPERATING.md` ("with `record=` every layer's arrays and the logits", [L309](https://github.com/anthropics/FlashProve/blob/9e2bdd8ff5bf9c62f18263d7dac189b0400b260c/integrations/vllm/integer_model/OPERATING.md#L309)), though omitted from the README's "Python API" section. The adapter retains only `lam`, converts logits via `lam / 2^s` (where `s` comes from the parameter file, described upstream as "the provider's statement: no equation ties it to the model", [parameter-file.md L219](https://github.com/anthropics/FlashProve/blob/9e2bdd8ff5bf9c62f18263d7dac189b0400b260c/verifier/docs/parameter-file.md#L219)), and computes log-softmax in float64. Top-token agreement does not depend on `record`.
- If `extend` raises `RangeConditionFailed` ("can raise RangeConditionFailed on an input on which the function is defined", [model.py L163-L167](https://github.com/anthropics/FlashProve/blob/9e2bdd8ff5bf9c62f18263d7dac189b0400b260c/integrations/vllm/integer_model/integer_model/model.py#L164-L167)), that request is recorded as failed with the exception message and never dropped.

Provenance of this computation: upstream states of `integer_model` that "By design, this is the function that the repository's prover proves" ([model.py L159-L160](https://github.com/anthropics/FlashProve/blob/9e2bdd8ff5bf9c62f18263d7dac189b0400b260c/integrations/vllm/integer_model/integer_model/model.py#L159-L160)), while noting that exact value-by-value equivalence with `cp_prove` at full size is not claimed ("What was compared with the prover is proof or no proof, and greedy choices", [OPERATING.md L593-L594](https://github.com/anthropics/FlashProve/blob/9e2bdd8ff5bf9c62f18263d7dac189b0400b260c/integrations/vllm/integer_model/OPERATING.md#L593-L594); value by value "nothing was compared at full size", [L585](https://github.com/anthropics/FlashProve/blob/9e2bdd8ff5bf9c62f18263d7dac189b0400b260c/integrations/vllm/integer_model/OPERATING.md#L585)). Our counted sessions establish that every reply produced by the package was accepted by `cp_prove` under exact match at those positions, whereas positions where the package diverges from the reference reply lack direct prover confirmation.

Level 1 measurement (Llama 4 Maverick, 360 prompts, 1 H200 bound on `h200x2`, `results/v1.0/teacher-forced/llama-4-maverick/run-flashprove.json`, n = 1 run):

- `extend` triggered zero `RangeConditionFailed` errors across all 360 reference replies.
- Scoring averaged 16.1 s per request (range 14.3 to 17.9 s, n = 361 including the system's own reply) with `record` and top-256 lists enabled. Total `score` time was 7,125 s (43 s float64 check, followed by full-tensor verified load and 361 requests); `setup` took 356 s. GPU memory was not logged.
- On the system's own proved reply for prompt 0, `integer_model` reproduced the proved reply at all 512 positions.
- Across all 360 prompts, the first position where `integer_model` disagreed with the reference token matched the exact matched prefix length of the proved reply (FI-3's stored score).

The scoring container is built from [`Dockerfile.score`](Dockerfile.score), layering this directory's `entrypoint` onto the pinned `system.yaml` image used by counted sessions without altering the `system.yaml` pin.

### The MODEL check's weight change, read at the pin

Level 1 defines the model perturbation as incrementing one Q4_K block scale in a block-0 dense attention tensor by one step. Each Q4_K block stores a float16 `h`, a float16 `h_min`, and eight 6-bit `(sc, mn)` pairs, with dequantized element values `v = RN32(RN32(RN32(h sc) c) - RN32(h_min mn))` ([docs/model.md#L377-L393](https://github.com/anthropics/FlashProve/blob/9e2bdd8ff5bf9c62f18263d7dac189b0400b260c/docs/model.md#L377-L393)). Committed integers are computed as `w = RNE(2^e pi)`, where `e` is set per tensor from its maximum `|pi|` ([#L441-L449](https://github.com/anthropics/FlashProve/blob/9e2bdd8ff5bf9c62f18263d7dac189b0400b260c/docs/model.md#L441-L449)). Incrementing a 6-bit `sc` shifts `v` by `RN32(h) * c` across that sub-block's 32 elements, altering `w` for any non-zero code `c` unless `2^e` times the shift rounds away (while `e` itself changes only if the tensor's maximum `|pi|` changes).

A CPU check can confirm that committed integers changed even though it cannot check commitment IDs (since `cp_commit` draws a fresh random seed every run, giving a new ID even on identical weights, [examples/accepted-proof/README.md#L75](https://github.com/anthropics/FlashProve/blob/9e2bdd8ff5bf9c62f18263d7dac189b0400b260c/examples/accepted-proof/README.md#L75)). `bin/weight_sums` runs on CPU and records each tensor's committed-integer SHA-256 in `wsums.txt` ([weight_sums/README.md#L1-L7](https://github.com/anthropics/FlashProve/blob/9e2bdd8ff5bf9c62f18263d7dac189b0400b260c/weight_sums/README.md#L1-L7)), so running it on W and W′ detects any committed integer change. `cp_commit` re-converts every tensor itself, exits with status 6 on any mismatch against `wsums.txt` ([#L169-L176](https://github.com/anthropics/FlashProve/blob/9e2bdd8ff5bf9c62f18263d7dac189b0400b260c/weight_sums/README.md#L169-L176)), and commits to the anchor root over those integers ([#L186-L188](https://github.com/anthropics/FlashProve/blob/9e2bdd8ff5bf9c62f18263d7dac189b0400b260c/weight_sums/README.md#L186-L188)).

**`perturb` (RFC-0018 AD-5, CPU).** Parses the GGUF v3 tensor tables across all five files ([docs/model.md#L352-L366](https://github.com/anthropics/FlashProve/blob/9e2bdd8ff5bf9c62f18263d7dac189b0400b260c/docs/model.md#L352-L366)), locates the first tensor among `blk.0.attn_q`, `attn_k`, `attn_v`, and `attn_output` encoded as Q4_K, and in the first block where stepping a scale moves an element (`h != 0` and some 4-bit code `!= 0`) increments the 6-bit `sc` of the first sub-block (`j < 4`, `sc < 63`) by 1 while preserving the byte's upper two bits ([docs/model.md#L377-L381](https://github.com/anthropics/FlashProve/blob/9e2bdd8ff5bf9c62f18263d7dac189b0400b260c/docs/model.md#L377-L381)). It copies all five files to `/io/perturbed/UD-Q4_K_XL/` with that single byte modified, then runs `bin/weight_sums --eres 10` on W′. `digest_w` records the published SHA-256 of W's `wsums.txt` (`examples/maverick/expected.txt`) and `digest_w_prime` records W′'s. If the digests match (no committed integer changed) or no block-0 attention tensor uses Q4_K, `perturb` exits non-zero (leaving MODEL `undecided`, RFC-0018 CH-2).

**W′ in control jobs (CH-2).** Only when a job specifies `control` with `"id": "P1"` or `"C3"` does the adapter permit `wsums.txt` or `KL.bin` to differ from the published digests (logging each difference in `warnings`); all other jobs still reject mismatches. For C3, `setup` runs `bin/weight_sums` and GPU calibration on W′ and `commit` commits to that fit. For P1, after `setup` and `commit` run on W, `prove` copies the five W′ files from `/models` over `/io/fit/weights` (the directory recorded by `cp_commit` and read by `cp_prove`, [weight_sums/README.md#L178-L180](https://github.com/anthropics/FlashProve/blob/9e2bdd8ff5bf9c62f18263d7dac189b0400b260c/weight_sums/README.md#L178-L180)), retains W's `wsums.txt` and `fold.txt`, and generates replies on W′ with `"verify_sums": false` (otherwise the loader would reject W′ before `cp_prove` starts). `cp_prove` then recomputes tree nodes from W′ and refuses to release proofs wherever they disagree with the commitment ([docs/model.md#L497-L504](https://github.com/anthropics/FlashProve/blob/9e2bdd8ff5bf9c62f18263d7dac189b0400b260c/docs/model.md#L497-L504)).
