# FlashProve

This page records the subcommand mapping (RFC-0005 §Adapter README requirements 1 to 4, 6 and 7) and the image build (requirement 5). Every fact links upstream at that commit; where upstream is silent, this page says so (AGENTS.md rule 9). Every figure on this page is grade external, tier reported, copied from upstream at the pin with its link; none was measured here. Upstream figures for the result tables are in [`external.yaml`](external.yaml).

## Subcommands and upstream calls

Each step runs one upstream program with the arguments that upstream's own scripts pass at the pin. The adapter adds no other argument; a control job's `control_flags` are appended to `cp_prove` only. Every process is appended to `/io/commands.jsonl`. The programs are the default build's, in `/src/prover/build/hc`.

| Step | Upstream call | Source |
|---|---|---|
| `info`, `setup` | none: the programs are built into the image | |
| `commit` | `cp_commit -weights /models/UD-Q4_K_XL -config /io/state/commit/config -M 1 -ivk /io/state/commit/ivk -isk /io/state/commit/isk` | the commit line under "Reproduce the numbers", [guide/performance.md#L76](https://github.com/anthropics/FlashProve/blob/9e2bdd8ff5bf9c62f18263d7dac189b0400b260c/guide/performance.md#L76); [examples/maverick/run.sh#L1569-L1570](https://github.com/anthropics/FlashProve/blob/9e2bdd8ff5bf9c62f18263d7dac189b0400b260c/examples/maverick/run.sh#L1569-L1570) passes the same plus `-public-weights`, which is not used here |

**commit.** The adapter first checks the two fit files whose digests upstream publishes, `wsums.txt` beside the weights and `KL.bin`, against [examples/maverick/expected.txt](https://github.com/anthropics/FlashProve/blob/9e2bdd8ff5bf9c62f18263d7dac189b0400b260c/examples/maverick/expected.txt), as run.sh's stages `fit` and `compare` do. It copies the fit's three configuration files into `/io/state/commit/config` and calls `cp_commit`. Success is exit code 0 and a last line that begins `cp_commit: done.` and says `is complete and can be handed out`; the commitment ID is the one line `commitment ID: <64 hex>` ([docs/operators-duties.md#L497-L506](https://github.com/anthropics/FlashProve/blob/9e2bdd8ff5bf9c62f18263d7dac189b0400b260c/docs/operators-duties.md#L497-L506)). Anything else makes `commit` exit non-zero with cp_commit's exit code and last line. Without `-public-weights` cp_commit draws the seed itself, so masking is on, as in upstream's timed runs ([guide/performance.md#L6](https://github.com/anthropics/FlashProve/blob/9e2bdd8ff5bf9c62f18263d7dac189b0400b260c/guide/performance.md#L6); [examples/maverick/README.md#L52-L59](https://github.com/anthropics/FlashProve/blob/9e2bdd8ff5bf9c62f18263d7dac189b0400b260c/examples/maverick/README.md#L52-L59)).

**prove.** The adapter lays every request into the spool's `in/` before `cp_prove` starts, so every batch is full, as `measure_rate.py` does ([driver/README.md#L63-L71](https://github.com/anthropics/FlashProve/blob/9e2bdd8ff5bf9c62f18263d7dac189b0400b260c/driver/README.md#L63-L71)). A request is the prompt's T token ids, then r = T - 1 and e = T, then 32 random bytes, under the name `sha256("p258-spool-req-1" || bytes).req`, written under `in/.tmp/` and linked into place ([docs/service.md#L94-L113](https://github.com/anthropics/FlashProve/blob/9e2bdd8ff5bf9c62f18263d7dac189b0400b260c/docs/service.md#L94-L113)). With e = T the proof covers the next token, which `cp_prove` writes as one 32-bit word in `<id>.y` ([docs/service.md#L84](https://github.com/anthropics/FlashProve/blob/9e2bdd8ff5bf9c62f18263d7dac189b0400b260c/docs/service.md#L84)). `cp_prove` takes the oldest queued requests, up to `-batch` of them, and releases a batch's responses into `out/` once all are staged; a response is complete once `<id>.proof` exists ([docs/service.md#L22-L30](https://github.com/anthropics/FlashProve/blob/9e2bdd8ff5bf9c62f18263d7dac189b0400b260c/docs/service.md#L22-L30), [#L250-L262](https://github.com/anthropics/FlashProve/blob/9e2bdd8ff5bf9c62f18263d7dac189b0400b260c/docs/service.md#L250-L262)). The adapter looks at `out/` every 50 ms while `cp_prove` runs. For each complete response it hard-links `<id>.y` and `<id>.proof` into `/io/proofs/.tmp-req-<i>/` as `response.y` and `response.proof`, then renames the directory to `req-<i>` (RFC-0005 §Proof release protocol). `claimed_output` is the word in `<id>.y`. `prove` exits non-zero, with cp_prove's exit code and last line, if `cp_prove` does not end with exit code 0 (`p258 end 0`, [docs/service.md#L334-L339](https://github.com/anthropics/FlashProve/blob/9e2bdd8ff5bf9c62f18263d7dac189b0400b260c/docs/service.md#L334-L339)), or if any request ends `<id>.failed` or gets no response.

**verify.** The adapter writes the request file (the job's `request`, then r = T - 1 and e = T, no nonce) and the token file (the one token of `claimed_output`) itself, as a client does ([docs/verifying.md](https://github.com/anthropics/FlashProve/blob/9e2bdd8ff5bf9c62f18263d7dac189b0400b260c/docs/verifying.md)), and passes the proof's `response.proof`. It never takes the token from the proof directory. The configuration and public key directories are rebuilt in `/tmp` from the harness's copies of `verifier_files`. `verify` calls the C++ verifier `cp_verify`, not the Lean verifier (RFC-0005 Q4); the claim card, [`claim.yaml`](claim.yaml) (configuration `exact-match-cp-verify`, unreviewed), names the same configuration.

## Verdict mapping

RFC-0005 §Verdict normalisation, over the exit codes and last lines of [verifier/docs/output.md#L247-L261](https://github.com/anthropics/FlashProve/blob/9e2bdd8ff5bf9c62f18263d7dac189b0400b260c/verifier/docs/output.md#L247-L261). The adapter keeps the raw exit code and the last non-empty line of standard output (of standard error when standard output is empty).

| cp_verify exit code and last line | verdict | `policy` |
|---|---|---|
| 0, `YES` | `accept` | `exact-match` |
| 0, `WITHIN LIMITS: clipped-gap C=... sh=...` | `accept` | `clipped-gap` |
| 1, `NO: <name>` | `reject` | |
| 5, `NOT CHECKED: <name>` | `no_verdict` | |
| 2 (wrong call or unreadable file), 3 (`PART PASSED`), 4 (`PLAN ONLY`), 14 (`NOT-A-VERIFICATION`), 15 (no output) | `invalid_call` | |
| any other exit code, a signal, or 0 with another last line | none: `verify` exits non-zero | |

Under the published configuration the policy is exact match ([examples/maverick/README.md#L287-L289](https://github.com/anthropics/FlashProve/blob/9e2bdd8ff5bf9c62f18263d7dac189b0400b260c/examples/maverick/README.md#L287-L289)), so an accepted proof here ends `YES`. The adapter applies this map only, not the rest of upstream's acceptance rule (the proof-of-work line and the `result-v1` fields, [verifier/docs/output.md#L121-L131](https://github.com/anthropics/FlashProve/blob/9e2bdd8ff5bf9c62f18263d7dac189b0400b260c/verifier/docs/output.md#L121-L131)); the raw output stays in the step's log.

## What `commit` needs that the image does not make

`cp_commit` and `cp_prove` read the model from the weights directory: the five GGUF files and, beside them, the fit's `wsums.txt` and `fold.txt` (`eres 10`, `qkrows asis`). `cp_commit` also takes a configuration directory with the fit's `policy.txt` and `KL.bin` and the `layout.txt` of `prover/examples/target_full_f2` ([examples/maverick/run.sh#L1451-L1500](https://github.com/anthropics/FlashProve/blob/9e2bdd8ff5bf9c62f18263d7dac189b0400b260c/examples/maverick/run.sh#L1451-L1500)).

**setup** runs upstream's stage `fit` into `/io/fit`, with no network, in the order run.sh runs it:

1. `scales/make_calibration_set.py` makes the calibration set from the three files upstream names ([scales/README.md, "The calibration set"](https://github.com/anthropics/FlashProve/blob/9e2bdd8ff5bf9c62f18263d7dac189b0400b260c/scales/README.md#the-calibration-set)): WikiText-2's raw training split and the Llama 2 and Llama 4 tokenizers. The image holds them, fetched at build time by the sha256 upstream lists. Meta's two tokenizer repositories are gated, so the image takes them from ungated copies whose bytes have that same sha256 (`TheBloke/Llama-2-7B-Chat-fp16` and `unsloth/Llama-4-Maverick-17B-128E-Instruct`, revisions in `inputs.lock`). The script checks the three sums itself and the set's own sum.
2. `bin/weight_sums --eres 10` writes `wsums.txt`, compared with `model/wsums.txt` in [examples/maverick/expected.txt](https://github.com/anthropics/FlashProve/blob/9e2bdd8ff5bf9c62f18263d7dac189b0400b260c/examples/maverick/expected.txt).
3. `fold.txt` and `layout.txt` as run.sh writes them. `/models` is read only, so the five weight files are cloned (FICLONE, or copied where the file system cannot clone) into `/io/fit/weights` beside `wsums.txt` and `fold.txt`. cp_commit refuses a link, or a second hard link, to a weight file ([examples/maverick/README.md#L260-L263](https://github.com/anthropics/FlashProve/blob/9e2bdd8ff5bf9c62f18263d7dac189b0400b260c/examples/maverick/README.md#L260-L263)).
4. `scales/calibrate.py --device cuda --eres 10` fits the scales on the GPU, and `scales/words_to_policy.py` writes `policy.txt` and `KL.bin`. `KL.bin` is compared with `config/KL.bin` in expected.txt: "The scales come from one float32 pass on the GPU, and its rounding can differ between GPU models, drivers and torch's CUDA libraries" ([examples/maverick/run.sh#L1500-L1501](https://github.com/anthropics/FlashProve/blob/9e2bdd8ff5bf9c62f18263d7dac189b0400b260c/examples/maverick/run.sh#L1500-L1501)). A different digest stops `setup`, and no commitment is made from it.

The image has Python 3.13 with upstream's hash-locked `requirements.txt` (torch 2.9.1, CUDA 12.8 wheels) for steps 1 and 4. Upstream gives "5 to 6 minutes" for `bin/weight_sums` and 127 s for `scales/calibrate.py` ([examples/maverick/figures.txt](https://github.com/anthropics/FlashProve/blob/9e2bdd8ff5bf9c62f18263d7dac189b0400b260c/examples/maverick/figures.txt)); the clone adds the weight files' 232 GB to the job's `/io` where the file system cannot share blocks.

## Machine needs

Upstream's figures, for the public 4-bit files on one H100 80 GB (external, reported, FlashProve at the pin):

- **Host and sandbox:** an x86-64 CPU with the SHA extensions, and a sandbox that lets `madvise(MADV_WIPEONFORK)` through; elsewhere `cp_commit` and `cp_prove` stop at their start ([prover/docs/build.md#L6](https://github.com/anthropics/FlashProve/blob/9e2bdd8ff5bf9c62f18263d7dac189b0400b260c/prover/docs/build.md#L6)). gVisor refused the call (#68). `cp_verify` needs neither.
- **Host memory:** run.sh does not start `commit` below 330 GB available, nor `prove` below 290 GB ([examples/maverick/README.md#L68-L72](https://github.com/anthropics/FlashProve/blob/9e2bdd8ff5bf9c62f18263d7dac189b0400b260c/examples/maverick/README.md#L68-L72)). Peaks, file cache not counted: committing 299.6 GB, serving at 24 per batch 269.7 GB in its container ([guide/performance.md#L25](https://github.com/anthropics/FlashProve/blob/9e2bdd8ff5bf9c62f18263d7dac189b0400b260c/guide/performance.md#L25)). `cp_verify` used up to 3.53 GB in its largest process, with 24 threads ([guide/performance.md#L23](https://github.com/anthropics/FlashProve/blob/9e2bdd8ff5bf9c62f18263d7dac189b0400b260c/guide/performance.md#L23)).
- **Disk:** 245 GB in all: 232.1 GB of weight files, 10 GB for `commit` and 1 GB for `prove`, on a local disk ([examples/maverick/README.md#L72-L73](https://github.com/anthropics/FlashProve/blob/9e2bdd8ff5bf9c62f18263d7dac189b0400b260c/examples/maverick/README.md#L72-L73)). The adapter adds the tar copy of the secret key directory and its unpacked copy in `/io/state` (2.15 GB each, by upstream's size of that directory), and about 19 MB per proof ([driver/README.md#L105](https://github.com/anthropics/FlashProve/blob/9e2bdd8ff5bf9c62f18263d7dac189b0400b260c/driver/README.md#L105)).
- **Time:** committing takes about 39 minutes, once per commitment ([guide/performance.md#L19](https://github.com/anthropics/FlashProve/blob/9e2bdd8ff5bf9c62f18263d7dac189b0400b260c/guide/performance.md#L19)), 2,307.45 to 2,343.76 s in the timed runs ([#L95](https://github.com/anthropics/FlashProve/blob/9e2bdd8ff5bf9c62f18263d7dac189b0400b260c/guide/performance.md#L95)). At 24 per batch and five batches, `cp_prove` ran 1,208.4 to 1,236.4 s from its start to its end ([#L86](https://github.com/anthropics/FlashProve/blob/9e2bdd8ff5bf9c62f18263d7dac189b0400b260c/guide/performance.md#L86)), with a start-up of 68.1 to 79.0 s ([#L19](https://github.com/anthropics/FlashProve/blob/9e2bdd8ff5bf9c62f18263d7dac189b0400b260c/guide/performance.md#L19)). At 1 per batch upstream reports 58.796 ± 0.50 s per request (steady, n = 3, six batches a session, [#L10](https://github.com/anthropics/FlashProve/blob/9e2bdd8ff5bf9c62f18263d7dac189b0400b260c/guide/performance.md#L10)) and no session time. `cp_verify` takes about 21 s on one thread ([#L23](https://github.com/anthropics/FlashProve/blob/9e2bdd8ff5bf9c62f18263d7dac189b0400b260c/guide/performance.md#L23)). The RFC-0005 default timeouts (`commit` 14,400 s, `prove` 43,200 s) are above these.

## CPU binding

Upstream advises keeping `cp_commit` and `cp_prove` on CPUs of the GPU's NUMA node. Each pins its threads only to CPUs it may already use, and then prints `# GPU … is on NUMA node …; this thread is pinned to … of its CPUs`; without that line it pinned nothing ([guide/performance.md#L95](https://github.com/anthropics/FlashProve/blob/9e2bdd8ff5bf9c62f18263d7dac189b0400b260c/guide/performance.md#L95)). The timed runs bound every program to 24 CPUs on the GPU's NUMA node ([#L93](https://github.com/anthropics/FlashProve/blob/9e2bdd8ff5bf9c62f18263d7dac189b0400b260c/guide/performance.md#L93)). The harness provides this through the container's `--cpuset-cpus` and `--cpuset-mems` (RFC-0005 §Container invocation), which must name CPUs and the memory node of the GPU's NUMA node; the adapter passes no binding option. Whether the pinning line appears is read in the `commit` and `prove` logs on the GPU host.

## Known deviations from upstream's measuring setup

- **A fresh commitment per run, `-M 1`.** A session uses up its batches of a leaf table for good, and upstream asks for a commitment made for the measurement ([driver/README.md#L103](https://github.com/anthropics/FlashProve/blob/9e2bdd8ff5bf9c62f18263d7dac189b0400b260c/driver/README.md#L103)); its figures are for one leaf table ([guide/performance.md#L21](https://github.com/anthropics/FlashProve/blob/9e2bdd8ff5bf9c62f18263d7dac189b0400b260c/guide/performance.md#L21)).
- **No `-public-weights`.** The Maverick example uses it ([examples/maverick/README.md#L52-L59](https://github.com/anthropics/FlashProve/blob/9e2bdd8ff5bf9c62f18263d7dac189b0400b260c/examples/maverick/README.md#L52-L59)); the timed runs had masking on, and the commit line under "Reproduce the numbers" omits it.
- **Requests.** The workload's 1,024-token windows (RFC-0003), not the calibration set's windows or measure_rate.py's drawn ones ([guide/performance.md#L93](https://github.com/anthropics/FlashProve/blob/9e2bdd8ff5bf9c62f18263d7dac189b0400b260c/guide/performance.md#L93)).
- **Batches.** `fp-maverick-w1024-b1` runs five batches; upstream's timed runs at 1 per batch had six ([guide/performance.md#L91](https://github.com/anthropics/FlashProve/blob/9e2bdd8ff5bf9c62f18263d7dac189b0400b260c/guide/performance.md#L91)).
- **Release time.** Upstream times a batch by the latest change time of its proof files ([driver/README.md#L55](https://github.com/anthropics/FlashProve/blob/9e2bdd8ff5bf9c62f18263d7dac189b0400b260c/driver/README.md#L55)); the harness times the adapter's rename, at most one 50 ms look later, hence `steady_approximate: true`.
- **No tag check.** `measure_rate.py` checks each response's tag ([docs/service.md#L293-L303](https://github.com/anthropics/FlashProve/blob/9e2bdd8ff5bf9c62f18263d7dac189b0400b260c/docs/service.md#L293-L303)); the adapter reads each response by its request ID and lets `cp_verify` judge it.
- **The secret key directory is copied** through the harness's record (above). Upstream says not to copy one to get past a rejection ([docs/service.md#L158-L159](https://github.com/anthropics/FlashProve/blob/9e2bdd8ff5bf9c62f18263d7dac189b0400b260c/docs/service.md#L158-L159)); here each copy serves the one session of a commitment made for it.
- **Verification** runs on the verifier profile (8 CPUs, so `-j 8`; 1 CPU for `verify.single_thread`), one call at a time, after `cp_prove` has ended; `measure_rate.py` checks with `-j 4`, several calls side by side.

## Upstream's rejected proofs: not registered as system controls

RFC-0008 §System-specific controls names FlashProve's [examples/rejected-proofs](https://github.com/anthropics/FlashProve/tree/9e2bdd8ff5bf9c62f18263d7dac189b0400b260c/examples/rejected-proofs) as `fixture_proof` controls with expected outcome `rejected` (issue #70). None is registered: there is no `controls.yaml` for this system. Each example fails the RFC-0008 Q4 rule ("registered only if the harness can regenerate its commitment through the adapter's `commit` step; otherwise it is listed in the adapter README and not run as a control"), and none can go through the adapter's `verify` without a parameter the job does not carry. The reasons, from upstream at the pin:

1. **No proof is stored.** "No altered files are stored here." A script, `try_altered_copies.py`, alters the files of `examples/accepted-proof` or `examples/accepted-proof-clipped-gap` one at a time and runs the verifier on each altered set ([README.md#L3](https://github.com/anthropics/FlashProve/blob/9e2bdd8ff5bf9c62f18263d7dac189b0400b260c/examples/rejected-proofs/README.md#L3)). There is no upstream file to verify as is.
2. **The commitment comes with the example (INV-CTRL-6).** The script takes the ID from the example's `ID.txt` ("For this demonstration only. In a real check the commitment ID comes from where the commitment is published, never from files that come with a proof", [try_altered_copies.py#L164-L166](https://github.com/anthropics/FlashProve/blob/9e2bdd8ff5bf9c62f18263d7dac189b0400b260c/examples/rejected-proofs/try_altered_copies.py#L164-L166)) and the example's own `config/` and `ivk/` ([#L248](https://github.com/anthropics/FlashProve/blob/9e2bdd8ff5bf9c62f18263d7dac189b0400b260c/examples/rejected-proofs/try_altered_copies.py#L248)). The model is synthetic (8 layers, 4 routed experts, a vocabulary of 512, [accepted-proof/README.md#L54](https://github.com/anthropics/FlashProve/blob/9e2bdd8ff5bf9c62f18263d7dac189b0400b260c/examples/accepted-proof/README.md#L54)), not the workload's Maverick, and its secret directory is not published; "`cp_commit` draws a fresh seed each time, so a run of your own gives another commitment ID, other files in `ivk/` and another proof" ([#L75](https://github.com/anthropics/FlashProve/blob/9e2bdd8ff5bf9c62f18263d7dac189b0400b260c/examples/accepted-proof/README.md#L75)). The harness cannot make that commitment, and with the run's own commitment every altered set would fail on the model, not on the alteration the row names.
3. **The request is not one the adapter writes.** `verify` writes r = T - 1, e = T and passes `-next-token` (above). The clipped-gap set also needs `-policy` with values the script reads from the example's `policy.txt` ([rejected-proofs/README.md#L50](https://github.com/anthropics/FlashProve/blob/9e2bdd8ff5bf9c62f18263d7dac189b0400b260c/examples/rejected-proofs/README.md#L50)). ## Values for `system.yaml`

`system.yaml` declares these values, with the image the images workflow pushed:

```yaml
deterministic_proofs: false
incremental_proofs: true
proofs:
  granularity: "request"
  tokens_covered: "window"
  steady_boundary: "first_proof"
  steady_approximate: true
  verify_reads:
    read: ["response.proof"]
    not_read:
      - part: "response.y"
        reason: "verify never reads it: cp_verify checks a token file the adapter writes from the job's claimed_output, which the harness takes from its own record (AGENTS.md rule 6); C1 changes that token"
forbidden_flags: ["-public-weights", "-keep-for-the-audit"]
```

- `proofs.granularity: request`. Each request gets one proof file, `<id>.proof` ([docs/service.md#L84-L86](https://github.com/anthropics/FlashProve/blob/9e2bdd8ff5bf9c62f18263d7dac189b0400b260c/docs/service.md#L84-L86)).
- `proofs.tokens_covered: window`. A proof checks the next token after a 1,024-token window, and upstream's rate counts each request's T = 1,024 prompt tokens ([driver/README.md#L55](https://github.com/anthropics/FlashProve/blob/9e2bdd8ff5bf9c62f18263d7dac189b0400b260c/driver/README.md#L55); [guide/performance.md#L15](https://github.com/anthropics/FlashProve/blob/9e2bdd8ff5bf9c62f18263d7dac189b0400b260c/guide/performance.md#L15)).
- `incremental_proofs: true` and `steady_boundary: first_proof`. `cp_prove` releases each batch's responses when the batch is done, so a session has one release per batch ([docs/service.md#L22-L30](https://github.com/anthropics/FlashProve/blob/9e2bdd8ff5bf9c62f18263d7dac189b0400b260c/docs/service.md#L22-L30)); upstream's steady rate is a batch's requests times T over the mean interval between successive releases ([driver/README.md#L55](https://github.com/anthropics/FlashProve/blob/9e2bdd8ff5bf9c62f18263d7dac189b0400b260c/driver/README.md#L55)).
- `steady_approximate: true`. RFC-0004 maps FlashProve's steady rate onto `prove.steady` as approximate, and the release times differ as listed above.
- `deterministic_proofs: false`. Upstream does not state byte-identical proofs for identical inputs: proofs are masked with values from a random source that must not repeat ([docs/operators-duties.md#L180](https://github.com/anthropics/FlashProve/blob/9e2bdd8ff5bf9c62f18263d7dac189b0400b260c/docs/operators-duties.md#L180)), and of `-memory` it says that it "should not change any byte of a proof, but no test compares the bytes" ([docs/service.md#L482](https://github.com/anthropics/FlashProve/blob/9e2bdd8ff5bf9c62f18263d7dac189b0400b260c/docs/service.md#L482)).
- `forbidden_flags`. `-public-weights` gives up weight hiding ("With this option the weights are not hidden", [docs/operators-duties.md#L200-L204](https://github.com/anthropics/FlashProve/blob/9e2bdd8ff5bf9c62f18263d7dac189b0400b260c/docs/operators-duties.md#L200-L204)); `-keep-for-the-audit` keeps files that, with the seed, reveal every mask ([#L198](https://github.com/anthropics/FlashProve/blob/9e2bdd8ff5bf9c62f18263d7dac189b0400b260c/docs/operators-duties.md#L198)). Upstream names no option that loosens what `cp_verify` accepts: a call with a lower `-bits` or without `-id` is never accepted ([verifier/README.md#L108-L133](https://github.com/anthropics/FlashProve/blob/9e2bdd8ff5bf9c62f18263d7dac189b0400b260c/verifier/README.md#L108-L133)).
- `proofs.verify_reads`: `verify` reads `response.proof` and never reads `response.y`. It writes the token file `cp_verify` checks from the job's `claimed_output`, which the harness takes from its own record, never from files sent with a proof (AGENTS.md rule 6, [RFC-0008 §Parts the verifier reads](../../rfcs/0008-negative-controls.md#parts-the-verifier-reads)), as a client writes its own token file ([docs/verifying.md](https://github.com/anthropics/FlashProve/blob/9e2bdd8ff5bf9c62f18263d7dac189b0400b260c/docs/verifying.md)); `response.y` is the prover's copy of that token (§Subcommands and upstream calls, `prove`). A mutated `response.y` therefore never reaches `cp_verify`, so C5, C6 and C8 choose `response.proof` only and `controls.json` lists `response.y` with this reason. The attack a changed token would make is C1, which changes the claimed output token.
- `max_proof_parts` and `max_proof_bytes`: not stated upstream; the defaults apply (two parts, about 18.78 MB a proof).

## Level 1

RFC-0018 sets one request for the level: 512 prompt tokens, a 512-token greedy reply with end tokens ignored, every reply token checked. The workload is `l1-maverick-p512-o512`: 24 requests a batch, five batches a session, 120 requests. Batch 24 is upstream's headline timed run ([guide/performance.md#L8-L12](https://github.com/anthropics/FlashProve/blob/9e2bdd8ff5bf9c62f18263d7dac189b0400b260c/guide/performance.md#L8-L12); [docs/figures.tsv#L63](https://github.com/anthropics/FlashProve/blob/9e2bdd8ff5bf9c62f18263d7dac189b0400b260c/docs/figures.tsv#L63)). Everything below was read at the pin; nothing in this section has run on a GPU.

### The request and the range

- The window holds exactly T tokens: prompt, reply, then filler; T = 2^`lt`, 1,024 at full size ([docs/verifying.md#L115-L117](https://github.com/anthropics/FlashProve/blob/9e2bdd8ff5bf9c62f18263d7dac189b0400b260c/docs/verifying.md#L115-L117)); the fit's parameter file comes from `prover/examples/target_full_f2/policy.txt`, whose line 34 is `lt 10`. The adapter reads T from the commitment's `policy.txt`.
- "To check a whole reply of R tokens (its end token included) after a prompt of P tokens, set r = P - 1 and e = P + R - 1" ([docs/verifying.md#L119-L123](https://github.com/anthropics/FlashProve/blob/9e2bdd8ff5bf9c62f18263d7dac189b0400b260c/docs/verifying.md#L119-L123)). Here r = 511 and e = 1,023: positions 511 to 1,022, each about the token after it, so reply tokens 512 to 1,023, all 512 of them (RFC-0018 AD-1).
- P + R = 1,024 = T, so the window is full and no filler is written. e < T, so y is unused and the token file holds 0 ([docs/verifying.md#L125-L128](https://github.com/anthropics/FlashProve/blob/9e2bdd8ff5bf9c62f18263d7dac189b0400b260c/docs/verifying.md#L125-L128)). The one-past-the-window case (P + R = T + 1, e = T, the last token as y) is not needed; the adapter refuses any P + R > T. Where P + R < T the adapter pads with token 0, as both of upstream's sides do ([docs/verifying.md#L130-L132](https://github.com/anthropics/FlashProve/blob/9e2bdd8ff5bf9c62f18263d7dac189b0400b260c/docs/verifying.md#L130-L132); the word layout: [verifier/docs/output.md#L364-L368](https://github.com/anthropics/FlashProve/blob/9e2bdd8ff5bf9c62f18263d7dac189b0400b260c/verifier/docs/output.md#L364-L368)).
- `verify` writes that request file and a token file of four zero bytes from the job's `request` and `claimed_output` and calls `cp_verify CONFIG IVK REQUEST TOKEN PROOF -id ID -j N` ([docs/verifying.md#L176](https://github.com/anthropics/FlashProve/blob/9e2bdd8ff5bf9c62f18263d7dac189b0400b260c/docs/verifying.md#L176)), without `-next-token`: with a request that does not ask only about y that option ends the call in exit code 14 ([verifier/docs/output.md#L314-L315](https://github.com/anthropics/FlashProve/blob/9e2bdd8ff5bf9c62f18263d7dac189b0400b260c/verifier/docs/output.md#L314-L315)). The verdict map is the one above; an accepted exact-match call ends `YES` ([docs/verifying.md#L231-L234](https://github.com/anthropics/FlashProve/blob/9e2bdd8ff5bf9c62f18263d7dac189b0400b260c/docs/verifying.md#L231-L234)). C1 changes a token of `claimed_output`, which goes into the request file the verifier reads, so a changed first, last or interior reply token reaches `cp_verify`.
- The adapter does not read the `covered:` line that point 5 of upstream's acceptance rule asks a client to compare (`r=`, `e=`, `tokens=`, [docs/verifying.md#L235-L239](https://github.com/anthropics/FlashProve/blob/9e2bdd8ff5bf9c62f18263d7dac189b0400b260c/docs/verifying.md#L235-L239)); the raw output stays in the step's log.

### The reply route (RFC-0018 AD-3)

Under exact match a proof is made only if every covered token is the committed integer model's first choice ([integer_model/README.md#L166-L169](https://github.com/anthropics/FlashProve/blob/9e2bdd8ff5bf9c62f18263d7dac189b0400b260c/integrations/vllm/integer_model/README.md#L166-L169)), so the reply must be that model's own. Upstream ships the package that computes it, `integrations/vllm/integer_model/`, licence Apache-2.0 ([LICENSE](https://github.com/anthropics/FlashProve/blob/9e2bdd8ff5bf9c62f18263d7dac189b0400b260c/integrations/vllm/integer_model/LICENSE); [pyproject.toml#L18-L19](https://github.com/anthropics/FlashProve/blob/9e2bdd8ff5bf9c62f18263d7dac189b0400b260c/integrations/vllm/integer_model/pyproject.toml#L18-L19)); its NOTICE carries ggml and gguf-py (MIT) and the BLAKE2 reference code (CC0 1.0). The vLLM set it installs lists, by its own count, 150 packages under MIT, BSD, Apache-2.0 or PSF, 12 other permissive, 3 MPL or LGPL, 24 NVIDIA proprietary and 5 with no licence named in their metadata ([vllm/LICENCES.tsv#L5](https://github.com/anthropics/FlashProve/blob/9e2bdd8ff5bf9c62f18263d7dac189b0400b260c/integrations/vllm/LICENCES.tsv#L5)).

The package documents two ways to run the integer model: serving it through vLLM 0.29.0 with its plug-in, and a Python API, `integer_model.load_from_folder(folder, "cuda")`, `new_sequence()`, `extend()` ([README.md#L12-L19](https://github.com/anthropics/FlashProve/blob/9e2bdd8ff5bf9c62f18263d7dac189b0400b260c/integrations/vllm/integer_model/README.md#L12-L19), [#L59-L68](https://github.com/anthropics/FlashProve/blob/9e2bdd8ff5bf9c62f18263d7dac189b0400b260c/integrations/vllm/integer_model/README.md#L59-L68)). Its section "A request from the model's own reply" uses the Python API to make a request file from the model's own greedy reply ([#L112-L164](https://github.com/anthropics/FlashProve/blob/9e2bdd8ff5bf9c62f18263d7dac189b0400b260c/integrations/vllm/integer_model/README.md#L112-L164)), which is this adapter's task, so `prove` uses it, in one process that ends before `cp_prove` starts:

1. **The float64 check**, as upstream asks before the GPU serves the integer model: `python -B -m pytest -p no:cacheprovider -rs tests/test_arithmetic_edges.py` in the package's directory with `INTEGER_MODEL_TEST_DEVICE=cuda`. "Every test should pass, and none be skipped. If one fails or is skipped, do not serve from that GPU" ([OPERATING.md#L542-L559](https://github.com/anthropics/FlashProve/blob/9e2bdd8ff5bf9c62f18263d7dac189b0400b260c/integrations/vllm/integer_model/OPERATING.md#L542-L559)). Exit code other than 0, or a summary line with anything but passed tests, stops `prove`.
2. **The model folder** `/io/state/prove/integer-model`: the fit's `policy.txt` and `KL.bin`, and `integer_model.json` naming the five GGUF files and the set-up folder that holds `wsums.txt` and `fold.txt` (the same `/io/fit/weights` that `cp_commit` read), with `"verify_sums": true` ([OPERATING.md#L59-L86](https://github.com/anthropics/FlashProve/blob/9e2bdd8ff5bf9c62f18263d7dac189b0400b260c/integrations/vllm/integer_model/OPERATING.md#L59-L86), [#L160-L162](https://github.com/anthropics/FlashProve/blob/9e2bdd8ff5bf9c62f18263d7dac189b0400b260c/integrations/vllm/integer_model/OPERATING.md#L160-L162)). `load_from_folder` gets the option `sha256` with the digests of the five small files; those of `KL.bin` and `wsums.txt` are upstream's published ones from `examples/maverick/expected.txt` ([integer_model/model.py#L648-L656](https://github.com/anthropics/FlashProve/blob/9e2bdd8ff5bf9c62f18263d7dac189b0400b260c/integrations/vllm/integer_model/integer_model/model.py#L648-L656)).
3. **The replies**: for each prompt, one `extend` call on the prompt, then one per further token, each the greedy choice, until 512 tokens; no end token stops the loop. The program is the README's lines 124-135 with the GGUF folder in place of the synthetic one. The replies become the requests' reply tokens and the proofs' `claimed_output`.

What upstream states for this route, and what it does not:

- **Stated.** One sequence at a time, one GPU, windows up to 1,024 tokens ([README.md#L18-L19](https://github.com/anthropics/FlashProve/blob/9e2bdd8ff5bf9c62f18263d7dac189b0400b260c/integrations/vllm/integer_model/README.md#L18-L19)). At full size: 238 GB of free host memory, most of it pinned; 36 GB of GPU memory at the peak; start-up 22 to 25 minutes with every tensor verified; 0.60 to 0.62 s for each token after a 3-token prompt ([OPERATING.md#L32-L38](https://github.com/anthropics/FlashProve/blob/9e2bdd8ff5bf9c62f18263d7dac189b0400b260c/integrations/vllm/integer_model/OPERATING.md#L32-L38)). The loader raises `NotEnoughMemory` unless free host memory holds the weights plus 1/32 ([#L40-L43](https://github.com/anthropics/FlashProve/blob/9e2bdd8ff5bf9c62f18263d7dac189b0400b260c/integrations/vllm/integer_model/OPERATING.md#L40-L43)). `cp_prove` does not start on a GPU with more than 2 GiB in use, and the demo stops vLLM to prove on one GPU (`--stop-vllm-to-prove`, [vllm/README.md#L90](https://github.com/anthropics/FlashProve/blob/9e2bdd8ff5bf9c62f18263d7dac189b0400b260c/integrations/vllm/README.md#L90)); serving and proving at once needs a second GPU and host memory for both, never run at full size ([#L104](https://github.com/anthropics/FlashProve/blob/9e2bdd8ff5bf9c62f18263d7dac189b0400b260c/integrations/vllm/README.md#L104)). Hence generation runs first, in a process that exits, and `cp_prove` after it, on the same GPU.
- **Stated, for runs not on these programs.** At full size on the public 4-bit files, vLLM served 16 greedy replies from the package in each of four runs, each proved under exact match and checked ([OPERATING.md#L583](https://github.com/anthropics/FlashProve/blob/9e2bdd8ff5bf9c62f18263d7dac189b0400b260c/integrations/vllm/integer_model/OPERATING.md#L583)); three of them ran with vLLM stopped while `cp_prove` ran and `--max-tokens 64` ([integrations/LIMITS.md#L117-L120](https://github.com/anthropics/FlashProve/blob/9e2bdd8ff5bf9c62f18263d7dac189b0400b260c/integrations/LIMITS.md#L117-L120)). "None of them was made on the released programs, or with the scripts exactly as they are in this repository" ([#L110](https://github.com/anthropics/FlashProve/blob/9e2bdd8ff5bf9c62f18263d7dac189b0400b260c/integrations/LIMITS.md#L110)). The full-size example's request holds 1,000 tokens that the integer model chose itself, on synthetic weights ([integrations/README.md#L56-L66](https://github.com/anthropics/FlashProve/blob/9e2bdd8ff5bf9c62f18263d7dac189b0400b260c/integrations/README.md#L56-L66)).
- **Not stated.** The Python API at full size on real weights (upstream's full-size replies went through vLLM); replies of 512 tokens on real weights; the decoding time per token after a 512-token prompt; a prefill time for 512 tokens. A reply made without `RangeConditionFailed` meets the range conditions only at the positions evaluated, and a proof needs them at all T positions ([integer_model/model.py#L171-L175](https://github.com/anthropics/FlashProve/blob/9e2bdd8ff5bf9c62f18263d7dac189b0400b260c/integrations/vllm/integer_model/integer_model/model.py#L171-L175)); the reply's last token is never fed to the model, so position 1,023 is checked only by `cp_prove`, which then answers `<id>.failed` and `prove` exits non-zero.

**End tokens.** RFC-0018's rule (an end token chosen greedily stays in the reply and generation goes on) holds on this route. `extend` returns, at each position, `first_argmax` of the logits over the whole vocabulary V, the lowest id on ties, with no end token masked ([integer_model/model.py#L297-L299](https://github.com/anthropics/FlashProve/blob/9e2bdd8ff5bf9c62f18263d7dac189b0400b260c/integrations/vllm/integer_model/integer_model/model.py#L297-L299); [arithmetic.py#L46-L54](https://github.com/anthropics/FlashProve/blob/9e2bdd8ff5bf9c62f18263d7dac189b0400b260c/integrations/vllm/integer_model/integer_model/arithmetic.py#L46-L54)); `model.py` names no end token. The adapter's loop asks for exactly 512 tokens and stops at nothing else.

**No batching.** The package states one sequence at a time: "greedy decoding, one sequence at a time, one GPU" ([README.md#L18-L19](https://github.com/anthropics/FlashProve/blob/9e2bdd8ff5bf9c62f18263d7dac189b0400b260c/integrations/vllm/integer_model/README.md#L18-L19)); the plug-in refuses any `--max-num-seqs` but 1 ([integer_model_vllm/model.py#L4](https://github.com/anthropics/FlashProve/blob/9e2bdd8ff5bf9c62f18263d7dac189b0400b260c/integrations/vllm/integer_model/integer_model_vllm/model.py#L4), [#L55](https://github.com/anthropics/FlashProve/blob/9e2bdd8ff5bf9c62f18263d7dac189b0400b260c/integrations/vllm/integer_model/integer_model_vllm/model.py#L55)); `extend` takes one `Sequence` ([model.py#L222-L230](https://github.com/anthropics/FlashProve/blob/9e2bdd8ff5bf9c62f18263d7dac189b0400b260c/integrations/vllm/integer_model/integer_model/model.py#L222-L230)). So the adapter generates the 120 replies one after another.

**Generation marks (RFC-0018 AD-4, CO-3).** `prove` renames `/io/marks/.tmp-generation.start` to `generation.start` before the float64 check and `.tmp-generation.end` to `generation.end` after the generating process has exited, before `cp_prove` starts. Between the two marks the GPU does nothing but the replies.

**Expected session time, an estimate from upstream's figures (grade external, not measured here).** Setup about 8 minutes plus the copy of 232 GB (weight sums 5 to 6 min, calibration 127 s); commit 2,307 to 2,344 s; the integer model's load 22 to 25 min; generation 120 x 511 decoding steps at 0.60 to 0.62 s, 36,792 to 38,018 s (10.2 to 10.6 h), with the 512-token prefill and the float64 check not stated; `cp_prove` start-up 68 to 79 s and five batches of 24, about 1,210 to 1,240 s by the next-token runs (whole replies at 24 per batch ran at 108.67 against 111.23 tokens/s, [guide/performance.md#L12-L17](https://github.com/anthropics/FlashProve/blob/9e2bdd8ff5bf9c62f18263d7dac189b0400b260c/guide/performance.md#L12-L17)). In all about 11.7 to 12.1 h, generation about 87 % of it. The marks enclose the load and the generation, so under CO-3 they add about 318 to 330 GPU-seconds per reply to m on one GPU, against 7 to 10 for proving (v0.1's H200 runs read 7.06 to 7.20 at one token checked). With 24 replies a step, if one step took the same 0.60 to 0.62 s, generation would be about 26 min and the session about 2 h; upstream documents no such way, so the adapter does not do it.

RISK, open: upstream's own exact-match whole-reply runs used other programs and scripts, and 64-token replies; 512 + 512 on the released programs is untested anywhere (RFC-0018 RISK). The 0.60 to 0.62 s per token is after a 3-token prompt; the probe of `docs/runbooks/level-1.md` measures the real time.

### Scoring a reference reply (`score`, RFC-0018 AD-7)

`score` gives the integer model's greedy choice at every position of a reply another engine wrote (FI-10), and its 256 most probable tokens there (FI-12). `cp_prove` cannot give them: it states one token, after a full window, and "the programs have no option that prints an intermediate value" ([README.md L95-L97](https://github.com/anthropics/FlashProve/blob/9e2bdd8ff5bf9c62f18263d7dac189b0400b260c/integrations/vllm/integer_model/README.md#L95-L97)). The adapter calls the package `prove` writes the replies with, on the same folder (`setup`'s fit, every tensor checked against `wsums.txt`) and after the same float64 check:

```python
model.extend(sequence, prompt[:-1])
choices, gaps = model.extend(sequence, [prompt[-1], *reply[:-1]], gap_for=reply, record=record)
```

- This is the call of upstream's [`examples/score_reply.py`](https://github.com/anthropics/FlashProve/blob/9e2bdd8ff5bf9c62f18263d7dac189b0400b260c/integrations/vllm/integer_model/examples/score_reply.py#L126-L128), which "scores a reply that another engine served, in one forward pass" ([examples/README.md L31](https://github.com/anthropics/FlashProve/blob/9e2bdd8ff5bf9c62f18263d7dac189b0400b260c/integrations/vllm/integer_model/examples/README.md#L31)). `extend` returns "the argmax of the logits at the position of token_ids[i], with the lowest id on ties", and with `gap_for` a gap that "is 0 exactly for the greedy choice" ([model.py, `extend`](https://github.com/anthropics/FlashProve/blob/9e2bdd8ff5bf9c62f18263d7dac189b0400b260c/integrations/vllm/integer_model/integer_model/model.py#L230-L242)). Position j scores token j + 1, so the choices of the second call are the top tokens at the reply's 512 positions. The adapter checks that the gaps are 0 exactly where the choice is the reply's token.
- "The integers at a position depend only on the tokens up to it, not on how the tokens were divided into calls" ([model.py L232-L233](https://github.com/anthropics/FlashProve/blob/9e2bdd8ff5bf9c62f18263d7dac189b0400b260c/integrations/vllm/integer_model/integer_model/model.py#L232-L233)), so feeding the prompt first changes nothing.
- **`record` is used for KL only.** `extend`'s docstring describes it ("record(name, layer, tensor) receives named intermediate values ... after the layers x_last, aF, lam, first_choice", [model.py L252-L256](https://github.com/anthropics/FlashProve/blob/9e2bdd8ff5bf9c62f18263d7dac189b0400b260c/integrations/vllm/integer_model/integer_model/model.py#L252-L256)) and `OPERATING.md` names it ("with `record=` every layer's arrays and the logits", [L309](https://github.com/anthropics/FlashProve/blob/9e2bdd8ff5bf9c62f18263d7dac189b0400b260c/integrations/vllm/integer_model/OPERATING.md#L309)); the README's "Python API" section does not show it. The adapter keeps `lam` only. A logit is `lam / 2^s` with `s` from the parameter file, which upstream calls "the provider's statement: no equation ties it to the model" ([parameter-file.md L219](https://github.com/anthropics/FlashProve/blob/9e2bdd8ff5bf9c62f18263d7dac189b0400b260c/verifier/docs/parameter-file.md#L219)); the log-softmax is taken in float64. Top-token agreement does not use `record`.
- A request on which `extend` raises `RangeConditionFailed` is recorded as failed with that message; it is never dropped. `extend` "can raise RangeConditionFailed on an input on which the function is defined" ([model.py L163-L167](https://github.com/anthropics/FlashProve/blob/9e2bdd8ff5bf9c62f18263d7dac189b0400b260c/integrations/vllm/integer_model/integer_model/model.py#L164-L167)).

Whose computation this is: the publisher's package, of which it says "By design, this is the function that the repository's prover proves" ([model.py L159-L160](https://github.com/anthropics/FlashProve/blob/9e2bdd8ff5bf9c62f18263d7dac189b0400b260c/integrations/vllm/integer_model/integer_model/model.py#L159-L160)). Not stated at the pin: that the package equals `cp_prove` value by value at full size. "What was compared with the prover is proof or no proof, and greedy choices" ([OPERATING.md L593-L594](https://github.com/anthropics/FlashProve/blob/9e2bdd8ff5bf9c62f18263d7dac189b0400b260c/integrations/vllm/integer_model/OPERATING.md#L593-L594)), and value by value "nothing was compared at full size" ([L585](https://github.com/anthropics/FlashProve/blob/9e2bdd8ff5bf9c62f18263d7dac189b0400b260c/integrations/vllm/integer_model/OPERATING.md#L585)). The counted sessions add this much: every reply the package wrote was proved by `cp_prove` under exact match, at those positions. A position where the package's choice differs from the reference token has no such confirmation.

Measured on Level 1 (Llama 4 Maverick, the 360 prompts, 1 H200 bound on `h200x2`, `results/v1.0/teacher-forced/llama-4-maverick/run-flashprove.json`, n = 1 run):

- `extend` raised `RangeConditionFailed` on none of the 360 reference replies.
- A request took 16.1 s (mean; 14.3 to 17.9 s, n = 361 with the system's own reply), with `record` and the lists. The `score` call took 7,125 s: 43 s for the float64 check, then the load with every tensor checked and the 361 requests. `setup` took 356 s. GPU memory was not recorded.
- On the system's own proved reply to prompt 0, the package's choices were that reply at all 512 positions.
- On each of the 360 prompts, the first position where the package's choice differs from the reference token is the matched prefix of the proved reply (FI-3's stored score).

The scoring image is [`Dockerfile.score`](Dockerfile.score): `system.yaml`'s image, the one the counted sessions ran, plus this directory's `entrypoint`. The `system.yaml` pin does not change.

### The MODEL check's weight change, read at the pin

The level's change is one Q4_K block scale of one dense attention tensor of block 0, raised by one step. A Q4_K block holds a float16 `h`, a float16 `h_min` and eight 6-bit pairs (sc, mn); element value v = RN32(RN32(RN32(h sc) c) - RN32(h_min mn)) ([docs/model.md#L377-L393](https://github.com/anthropics/FlashProve/blob/9e2bdd8ff5bf9c62f18263d7dac189b0400b260c/docs/model.md#L377-L393)). The committed integer is w = RNE(2^e pi), with e fixed per tensor from its largest |pi| ([#L441-L449](https://github.com/anthropics/FlashProve/blob/9e2bdd8ff5bf9c62f18263d7dac189b0400b260c/docs/model.md#L441-L449)). A step of one 6-bit `sc` moves v by RN32(h) times the code c for the 32 elements of that sub-block, so w changes for any element whose code is not 0 unless 2^e times that move rounds away, and e itself moves only if the tensor's largest |pi| does.

A CPU check can show the committed integers change, not the commitment ID: `cp_commit` draws a fresh seed each time, so every commitment has another ID even on the same files ([examples/accepted-proof/README.md#L75](https://github.com/anthropics/FlashProve/blob/9e2bdd8ff5bf9c62f18263d7dac189b0400b260c/examples/accepted-proof/README.md#L75)). `bin/weight_sums` runs on a CPU and writes each committed tensor's SHA-256 of its integers to `wsums.txt` ([weight_sums/README.md#L1-L7](https://github.com/anthropics/FlashProve/blob/9e2bdd8ff5bf9c62f18263d7dac189b0400b260c/weight_sums/README.md#L1-L7)); run on W and on W′, the changed tensor's line differs exactly when its integers do. `cp_commit` converts every tensor itself and exits with status 6 when a hash differs from `wsums.txt` ([#L169-L176](https://github.com/anthropics/FlashProve/blob/9e2bdd8ff5bf9c62f18263d7dac189b0400b260c/weight_sums/README.md#L169-L176)), and the commitment covers the anchor's root over the committed integers ([#L186-L188](https://github.com/anthropics/FlashProve/blob/9e2bdd8ff5bf9c62f18263d7dac189b0400b260c/weight_sums/README.md#L186-L188)). **`perturb` (RFC-0018 AD-5, CPU).** It reads the GGUF tensor tables of the five files (version 3, [docs/model.md#L352-L366](https://github.com/anthropics/FlashProve/blob/9e2bdd8ff5bf9c62f18263d7dac189b0400b260c/docs/model.md#L352-L366)), takes the first of `blk.0.attn_q`, `attn_k`, `attn_v`, `attn_output` stored as Q4_K, and in its first block whose scale step moves an element (h not 0, a 4-bit code not 0) raises the 6-bit scale `sc` of the first sub-block j < 4 below 63 by one, keeping the byte's top two bits ([docs/model.md#L377-L381](https://github.com/anthropics/FlashProve/blob/9e2bdd8ff5bf9c62f18263d7dac189b0400b260c/docs/model.md#L377-L381)). W′ is the five files copied to `/io/perturbed/UD-Q4_K_XL/` with that one byte changed. It then runs `bin/weight_sums --eres 10` on W′; the record's `digest_w` is the published sha256 of W's `wsums.txt` (`examples/maverick/expected.txt`) and `digest_w_prime` that of W′'s. Equal digests mean no committed integer moved, and `perturb` exits non-zero (MODEL `undecided`, RFC-0018 CH-2). Which attention tensors of block 0 are Q4_K in the UD-Q4_K_XL files was not read here; `perturb` exits non-zero if none is.

**W′ in control jobs (CH-2).** Only in a job whose `control` is `{"id": "P1" | "C3", ...}` does the adapter accept a `wsums.txt` or `KL.bin` other than the published ones, each recorded in `warnings`; in any other job, a control job included, it refuses as before. C3: `setup` on W′ runs upstream's own `bin/weight_sums` and calibration on W′, and `commit` commits to that fit, so `cp_commit` sees W′'s own sums. P1: after `setup` and `commit` on W, `prove` copies the five files from `/models` (W′) over `/io/fit/weights`, the directory `cp_commit` recorded and `cp_prove` reads ([weight_sums/README.md#L178-L180](https://github.com/anthropics/FlashProve/blob/9e2bdd8ff5bf9c62f18263d7dac189b0400b260c/weight_sums/README.md#L178-L180)), keeps W's `wsums.txt` and `fold.txt`, and generates the replies with W′ and `"verify_sums": false` (with W's sums the loader would refuse W′ before `cp_prove` runs). `cp_prove` then rebuilds the commitment's tree nodes from W′ and releases nothing where they differ ([docs/model.md#L497-L504](https://github.com/anthropics/FlashProve/blob/9e2bdd8ff5bf9c62f18263d7dac189b0400b260c/docs/model.md#L497-L504)).
