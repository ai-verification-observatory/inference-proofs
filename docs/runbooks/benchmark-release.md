# Benchmark release

Checklist for a benchmark release (`v<release>`), from [docs/spec/09-release-and-versioning.md §Release checklists](../spec/09-release-and-versioning.md#release-checklists). Each step names the RFC section that defines it. Do every step in order; a step that fails stops the release.

1. The RFCs the release uses are Accepted, and their commit is named in `release.yaml` ([RFC-0001 §RFC lifecycle](../../rfcs/0001-process-and-governance.md#rfc-lifecycle), [RFC-0001 §Release approval](../../rfcs/0001-process-and-governance.md#release-approval), [RFC-0009 §Release record](../../rfcs/0009-results-and-publication.md#release-record)).
2. The reference file is merged with the price, its date and pinned driver, CUDA and runtime versions ([RFC-0006 §Reference file](../../rfcs/0006-reference-hardware-and-cost.md#reference-file), [RFC-0006 §Cost basis](../../rfcs/0006-reference-hardware-and-cost.md#cost-basis)).
3. All runs are merged. Every run is eligible, or listed as ineligible with its reason ([RFC-0007 §Eligibility](../../rfcs/0007-evidence-tiers-and-reproduction.md#eligibility), [RFC-0014 §Eligibility](../../rfcs/0014-provenance-and-integrity.md#eligibility)).
4. System maintainers have reviewed the claim cards (`reviewed_by` non-empty), and the release lists them by digest ([RFC-0002 §Claim class](../../rfcs/0002-claim-card.md#claim-class), [RFC-0009 §Release record](../../rfcs/0009-results-and-publication.md#release-record)).
5. Peer reviews and reproductions are merged, failed reproductions included ([RFC-0007 §Peer review before release](../../rfcs/0007-evidence-tiers-and-reproduction.md#peer-review-before-release), [RFC-0007 §Failed reproductions](../../rfcs/0007-evidence-tiers-and-reproduction.md#failed-reproductions)).
6. One archived proof per configuration is uploaded, with its `uri` and digest ([RFC-0014 §Proof digests and archive](../../rfcs/0014-provenance-and-integrity.md#proof-digests-and-archive)).
7. The candidate site and draft `index.json` are built. A review window of at least 14 days is opened, and system maintainers are notified ([RFC-0009 §Review window](../../rfcs/0009-results-and-publication.md#review-window)).
8. Replies are merged (optional for each team). The report is drafted from [reports/TEMPLATE.md](../../reports/TEMPLATE.md) and reviewed by every listed team ([RFC-0009 §Right of reply](../../rfcs/0009-results-and-publication.md#right-of-reply), [RFC-0009 §Reports](../../rfcs/0009-results-and-publication.md#reports)).
9. The window is closed, `iproofs release freeze` is run, `index.json` is merged, and the tag `v<release>` is placed on that commit ([RFC-0009 §Freeze algorithm](../../rfcs/0009-results-and-publication.md#freeze-algorithm), [RFC-0007 §Effective tier at release freeze](../../rfcs/0007-evidence-tiers-and-reproduction.md#effective-tier-at-release-freeze)).
10. The site is published from the tagged commit. The sponsors and conflicts pages are checked against `release.yaml` and [MAINTAINERS.md](../../MAINTAINERS.md) ([RFC-0009 §Site](../../rfcs/0009-results-and-publication.md#site), [RFC-0001 §Conflicts of interest](../../rfcs/0001-process-and-governance.md#conflicts-of-interest)).
