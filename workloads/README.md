# Workloads

One file per workload, `workloads/<id>.yaml`, valid against `schema/workload/1.schema.json` ([RFC-0003 §Workload file](../rfcs/0003-workloads.md#workload-file)). Weights are never stored here; a workload pins them by source, revision and per-file hash.

`iproofs.workloads.load_workload` validates the file against its schema, then checks the rules a schema cannot express. Each violation is a `config` error naming the field:

- the file name matches `id`, and `version` matches the requested version when one is given;
- INV-WL-4: `prompts.count == shape.batch_size * shape.batches_per_session` and `prompts.length_rule.prompt_tokens == shape.prompt_tokens`;
- `shape.context_window >= shape.prompt_tokens + shape.output_tokens - 1`;
- `model.tokenizer_file` is one of `model.files[].path`, or, when `model.tokenizer_source` names a second pinned repository for the tokenizer file alone, that source's `file.path`;
- every id in `systems` has a `systems/<id>/system.yaml`;
- a `precision.weight_bits` with basis `file_size` lists files of `model.files` and types no `bits`: the loader computes them as the files' bytes × 8 / `model.parameters.total` ([RFC-0003 §Weight bits](../rfcs/0003-workloads.md#weight-bits)).

The schema itself enforces the closed-division rule (`claim_class` present exactly when `division` is `closed`), greedy decoding and full 40-hex model revisions. The runner checks a closed workload's class against the job's claim card (Closed workloads, below).

A system joins a workload's `systems` list when its `system.yaml` lands; the loader requires one for every id listed. A job runs only when the system's own `system.yaml` `workloads` lists the workload too.

Each workload carries `precision.weight_bits`, the bits per weight of the precision as proved, with its source (RFC-0003 §Weight bits): 8 for the SASH workloads and the closed `l31-8b-c1024`, as SASH's own quantizer states its weight matmuls (the files are BF16, quantized at load time); 4.5 for the Maverick workloads, Unsloth's figure for `UD-Q4_K_XL` in its column headed "MoE Bits", a nominal width since the files mix block types (RFC-0003 Q5). Both statements cover part of the active weights (weight matmuls; the expert layers), so both are recorded `covers: part`, and RFC-0004 does not sort by their D-SPAB-S until Q5 is resolved. RFC-0004 D-SPAB-S divides prover time by active parameters times these bits. The runner copies both numbers into each run's `inputs`, so a correction of `bits`, which is a new workload version, never changes a stored run (WB-4).

## Closed workloads

A closed workload is a common workload with one fixed `claim_class`: only a system whose claim card has that exact class runs in it, and its rows compare directly ([RFC-0003 §Divisions](../rfcs/0003-workloads.md#divisions)). The runner checks the class when it resolves a job, against the card the job's manifest records (`claims/default.yaml`, else `claim.yaml`; a v0.1 job names no configuration): a card of another class, or a proving system with no such card, is a `config` error before any container starts (`iproofs.runner.check_card_class`). A reference system has no card (RFC-0015) and is not checked.

[`l31-8b-c1024`](l31-8b-c1024.yaml) is the shared Llama 3.1 8B workload (owner decision, 2026-11-08; [RFC-0003 §Closed workloads](../rfcs/0003-workloads.md#closed-workloads)). It is a candidate: its rows enter a release once two systems with its class run it through their adapters with no upstream change (RFC-0003 Q7, default). `iproofs release freeze` enforces the count: a release holding completed runs of the workload from fewer than two proving systems whose cards have its class stops with a `config` error (`iproofs.release.closed_workload_failures`). Its choices, each a default recorded as an open question in RFC-0003:

- **Model.** The files of `sash-l31-8b-c1024`: the same repository, revision, file list and `model.digest` (`sha256:368b6c2838f66f92d67f24276a2314c7c2014b059a33c33ea35d793740377ee7`), so a model fetched for SASH's native workload serves this one. RFC-0003 §Model fetch and hash rule allows it: the digest names the files, not the workload.
- **Precision: W8A8.** The one system with an adapter for this model proves W8A8 (`sash-l31-8b-c1024`). No other system read states W8A8 for it (table below). A system that proves another precision runs this model in the open division.
- **Shape: 1,024 prompt + 64 continuation positions, batch 1, one batch per session, phase `both`, greedy.** The shape of `sash-l31-8b-c1024`, the shorter of SASH's two native shapes (the other is 4,096 + 512). Upstream SASH records no run at this shape: its geometry there is "not stated" ([`systems/sash/README.md`](../systems/sash/README.md#the-two-v01-shapes)). No other system played a part in the choice: FlashProve's 1,024-token window is the whole context of a request on Llama 4 Maverick ("A request contains a window of T tokens", [`docs/limits.md` L213](https://github.com/anthropics/FlashProve/blob/9e2bdd8ff5bf9c62f18263d7dac189b0400b260c/docs/limits.md?plain=1#L213); "one full-size model shape: that of Llama 4 Maverick, with a window of 1,024 tokens", [L2479-L2480](https://github.com/anthropics/FlashProve/blob/9e2bdd8ff5bf9c62f18263d7dac189b0400b260c/docs/limits.md?plain=1#L2479-L2480)), while this shape's context is 1,088 tokens, on another model, and FlashProve's card has another class.
- **Claim class: `greedy-continuation/exact-match/committed-weights`**, SASH's card class ([`systems/sash/claim.yaml`](../systems/sash/claim.yaml)). FlashProve's card class is `next-token/exact-match/committed-weights`, so FlashProve on this model would run in the open division.
- **Prompts.** The shared corpus and `corpus-window/1`, one prompt per job. The tokenizer file is the one SASH's native workload pins, so `iproofs prompts build l31-8b-c1024 --seed S` gives the digest `sash-l31-8b-c1024` gives for the same seed.

`systems` lists `sash`, `ref-serve` and `ref-recompute`. No system's `system.yaml` lists the workload yet, so no job of it runs: SASH's adapter names its workloads in its `info` output (`systems/sash/entrypoint`, `WORKLOADS`), so listing this one means a new adapter image, and the reference systems each need a `workloads` entry with their precision substitution (RFC-0015 PM-0).

## Checking a prompt set

`iproofs prompts build WORKLOAD --seed SEED [--out prompts.jsonl]` rebuilds the prompt set a job with that seed used, without running a prover: it fetches and verifies the corpus, loads the workload's tokenizer file (from the verified model cache, or fetched alone and checked against its listed sha256), runs `corpus-window/1`, writes `prompts.jsonl` and prints `{workload, seed, count, digest, tokenizers_version}` as JSON. The digest equals the manifest's `workload.prompt_set_digest` for a run that recorded that seed. Real tokenizer files need the `[prompts]` extra (`uv sync --extra prompts`); a different `tokenizers` version can tokenize differently, which shows as a different digest (RFC-0003 §Failure modes).
