    FlashProve

    What one proof establishes

    1. Weights hidden. Does the checker learn nothing about the weights?

      Partly

      Hidden by design, but one bit per request leaks.

    2. Model bound. Is each checked token tied to the committed weights?

      Partly

      Under exact match each checked token is meant to be the top choice; for the programs that step is not shown.

    3. Whole output checked. Does one check cover every output token of a request?

      No

      Covers the positions the client names; completeness of the reply not shown.

      statedPartly; C1 accepted in run 2026-11-25-flashprove-fp-maverick-w1024-b24-prover-h100-1

    4. Formally verified. Is the security argument for this configuration checked by a proof assistant?

      No

      Nothing is proved of cp_verify, the verifier this setup runs; that rests on tests.

    5. Security level. Is a soundness level stated for this configuration, and proven?

      Not stated

      No level is claimed for cp_verify; its printed bits are its own accounting, not a theorem.

    6. No trusted party. Does a check hold without trusting a chip maker, a setup ceremony or an honest party?

      Partly

      You must grant its public files were fixed before the hash.

    hidden
    The weights: “by design, beyond a declared list, every published value that depends on the weights is masked or published only as a salted hash. Zero knowledge, Lean's form of weight hiding, is proved in Lean for the protocol, at full size and at the exact-match policy, with fresh random masks. The honest prover in these theorems is a Lean definition, not the CUDA prover.” Of the programs: “we expect, rather than know, that the programs hide the weights at the default setting, in honest runs, if the provider keeps its duties (this does not reach any real model's weights, or the parameter file and scales fitted to them)”.
    not hidden
    The declared list, “At least eleven things are visible”: each reply, whether a request was served or failed, time, the architecture and every size, settings fitted to the weights, that cp_commit's checks passed, that a batch failed or the service stopped, how much a provider has served and when, who shared a batch and how many, lengths, places in the batch and nonces, masked sums of the weights. “The list says what is visible by design, not that everything else is hidden.” In Lean's theorem, one bit per request (served or refused) is revealed, “and it depends on the weights”.

    binding
    statement
    “The commitment ID is a hash, in 64 hex digits, of the configuration, the Merkle root and shape of the first weight table, a masked encoding of the weights, and the out-of-domain (OOD) seeds and answers. [...] the ID covers them by design, but the soundness theorem on verify is stated at given public files and does not itself say that one ID cannot verify under two sets of them. The ID does not cover the leaf files or the key file's proofs, which cp_verify checks on reading.”
