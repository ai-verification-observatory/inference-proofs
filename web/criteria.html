    Criteria

    Not stated is No. The sources read say nothing that meets the Yes, Partly or No rule, or they have not been read yet. A guarantee nobody states is one nobody can rely on: the glyph draws it as No, and its reason says it is not stated.

    • Weights hidden
    • Model bound
    • Whole output checked
    • Formally verified
    • Security level
    • No trusted party

    Weights hidden

    Does the checker learn nothing about the weights?

    Yes
    The weights stay hidden from the checker in the default use, naming no leak beyond public settings.
    Partly
    They are hidden with a stated limit: a named leak, hiding shown for one policy or setting only, hiding optional per circuit, or hiding behind a commitment without the formal zero-knowledge property.
    No
    The checker sees the weights, or hiding is off or not provided.

    Hiding the weights from the host operator (an enclave) is not this property.

    Model bound

    Is each checked token tied to the committed weights?

    Yes
    A passing check ties each checked token to the committed weights exactly, in the configuration run.
    Partly
    Tied with a stated limit: under one of several policies only, within a tolerance or bound, or shown only in empirical tests.
    No
    Outputs are not tied to any weights, or nothing is checked.

    Which real, named model the commitment is: FlashProve and SASH both say that stays outside their proof; it does not change the state.

    Whole output checked

    Does one check cover every output token of a request?

    Yes
    One check, or one joined set of checks, covers the prompt and every output token of a request.
    Partly
    One check covers a stated part: the positions the client names, one segment, or one disputed step.
    No
    No output token is checked, or nothing is checked.
    Not stated
    A proved run whose output tokens the documentation does not name.

    Which requests get a check (sampling, proving after the fact) is a deployment choice, not what one check covers. The text before tokenizing and after detokenizing, which FlashProve and SASH both put outside their proof, does not change the state.

    Formally verified

    Is the security argument for this configuration checked by a proof assistant?

    Yes
    The soundness of the configuration run is proved in a proof assistant (Lean, Coq, Isabelle or similar).
    Partly
    Machine-checked for a stated part only: one component, or a weaker statement than the one the system makes.
    No
    The argument is not machine-checked, a machine check is planned only, or its soundness evidence is review or tests and nothing else; or for a reference (production serving), which has no security argument by definition.

    A proof that the code itself is correct: no row claims it. A statement made only for another configuration of the same system, another verifier for one, sets nothing here.

    Security level

    Is a soundness level stated for this configuration, and proven?

    Yes
    The documentation states a numeric soundness bound for the configuration run and says it is proven, by hand or by machine, under named assumptions.
    Partly
    A numeric level is stated but called conjectured, or stated only in code or configuration, or for part of the system. A level stated without saying it is proven or conjectured is Partly. rule RFC-0016 Q10 ↗
    No
    The settings give no meaningful soundness, for example a test-only setting; or for a reference (production serving), which has no soundness level by definition.

    The level itself: the state shows only whether one is stated and proven. A level stated only for another configuration of the same system sets nothing here.

    No trusted party

    Does a check hold without trusting a chip maker, a setup ceremony or an honest party?

    Yes
    The check rests on cryptography alone or needs no trusted setup, and names no chip maker, setup or other party to trust.
    Partly
    The documentation states a trusted input or condition that its proved statement does not cover: a setup file, public files the user must grant were fixed before the hash, or one honest party among several.
    No
    The check verifies a hardware attestation against a chip maker's keys or certificate chain, or the provider is trusted. Running in a trusted execution environment, said alone, is not such a statement.

    Trust every row shares does not change the state: the checker's own computer, compiler and verifier build, and where the commitment or the weights come from (see Model bound).
