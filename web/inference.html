    Inference, for cryptographers

    What a language model computes when it answers, how it is served, and why the computation is awkward to prove.

    You know what a circuit is. A language model's forward pass is one, with three inconvenient features: it is large, many of its gates are not field operations, and its inputs are not field elements. This page describes the computation as a prover meets it, and the facts about serving that decide what a proof is compared with.

    The computation

    A model reads tokens, which are integers, and for each position produces a score for every token of its vocabulary. The next token of a reply is chosen from those scores. To produce a reply, the model appends the chosen token to its input and runs again.

    For a prover the operations fall into three kinds.

    • Products with the weights. A vector of activations times a matrix the operator has committed to. These are most of the arithmetic, and the page on proving a forward pass shows why they are the cheap part.
    • Products of two computed values. Attention multiplies activations by activations: queries by keys, then scores by values. Neither side is fixed by the commitment: both are computed during the pass.
    • Everything else. Normalisation divides by a square root. Softmax takes exponentials and divides. Activation functions are fixed curves. Greedy decoding takes the largest of the vocabulary's scores, tens of thousands of them or more. The embedding is a table lookup. None of these is an addition or a multiplication.

    Its size

    A forward pass uses every weight it reads about once per token, in one multiplication and one addition. So the work per token is about two operations per weight. For a model of 8 billion weights that is 1.6 × 10^10 operations per token, and a request of 1,024 tokens comes to about 1.6 × 10^13.

    Two refinements matter on this site's ladder. A mixture-of-experts model reads only some of its weights for each token: the largest model here holds 400 billion and reads about 17 billion per token. The commitment still covers all of them. And attention adds work that grows with the square of the length of the context, since every position looks at every earlier one.

    The witness is large too. Every intermediate value of every layer at every position is part of it: thousands of numbers per position per layer, before any encoding.

    Its arithmetic

    Publishers release weights as floating point numbers of 8 to 32 bits, and serving engines compute in floating point on GPUs. Floating point addition is not associative: summing the same numbers in another order can change the last bits of the result. The order depends on the hardware, the library, and how many requests were batched together. Two honest runs of the same model on the same prompt can therefore differ in a low bit, then in which of two near-equal scores is larger, then in a token. After one different token the rest of the reply usually differs. One study found that “changing system configuration, such as evaluation batch size, GPU count, and GPU version, can introduce significant differences in the generated responses”, and reports them under greedy decoding too.

    Most of this is not randomness. With the GPU model, the software versions, the parallelism and the batch sizes all fixed, and no kernel that adds in an order set by thread timing, the same bits come out, and recent work reproduces serving engines' outputs bit for bit on that basis. It found true run-to-run differences only in some integer-quantized kernels. But a verifier rarely holds all of those facts, and in the setting of a proof it does not hold the weights.

    So the reply of this model to this prompt is not a mathematical object until the arithmetic is fixed exactly. A proof needs it to be one. Provers fix it by working on a quantized copy of the model (quantization) whose arithmetic and rounding rules are specified exactly, so that every run gives the same bits. Three consequences follow, and each has a rule on this site.

    • The statement is about the copy. An accepted proof says the quantized model gives the reply. It says nothing by itself about the publisher's floating point model. The Fidelity check tests whether the copy's replies stay closer to the original's than those of copies damaged on purpose.
    • The reply must come from the copy. A reply generated by a serving engine in floating point will, sooner or later, differ in a token from what the proof can show. Under exact match, the reply has to be generated with the prover's own arithmetic.
    • Decoding is greedy. With greedy decoding the reply is a function of the model and the prompt. Random decoding (sampling, in ML usage) would add randomness to the statement, which someone would have to commit to and limit.

    How it is served

    A proof is compared with the cost of an ordinary reply, so it matters how ordinary replies are made. A serving engine processes the prompt once, keeping each layer's keys and values in a cache, then produces the reply one token at a time against that cache. It runs many requests together on one GPU, and its throughput rises with the number of concurrent requests until the GPU is saturated.

    The cost of one served reply therefore depends on the load. A lone request on an idle GPU is expensive, and a request among hundreds is cheap. This benchmark takes the serving baseline at full load: it raises the concurrency step by step until the rate stops rising.

    The cost of a served reply at full load is the number every proving cost is divided by.

    What a statement has to pin down

    A claim that this model produced this reply hides several choices, and a proof is only as precise as its statement makes them.

    ChoiceWhy it cannot be left open
    Which representation of the weights is committedA commitment to 4-bit codes and a commitment to the original floats fix different models
    Which arithmeticRounding rules decide the last bits, and the last bits decide tokens
    Tokens, not textThe model computes on token ids. Turning text into ids is outside the statement unless it says otherwise
    The decoding ruleGreedy, with a fixed rule for ties, or random with what randomness
    Where a reply endsWhether an end token stops the reply. Here it does not, so every reply has 512 tokens
    Which positions are checkedOne next token, or every token of the reply

    The statement, the page before this one, reads two systems' statements for four of these. The other two, tokens and the end of a reply, are settled by this benchmark's request.

    Why this is awkward to prove

    • Scale. About 1.6 × 10^13 operations for one request on a model of 8 billion weights. Any constant cost per operation is multiplied by it.
    • The non-arithmetic share. Every activation, normalisation and comparison needs a lookup argument or a range check, per value, per layer, per token.
    • Precision. Exactness forces fixed point, and fixed point forces a rescaling after every product.
    • Sequence. A reply is produced one token at a time, each depending on the last. Checking it can be done in one parallel pass. Producing it cannot.
    • Memory. The witness has to be held, encoded and committed, on top of the model itself.
