    The six checks

    How a check works

    Every runnable system pinned to a public commit receives the exact same request: 512 prompt tokens, 512 reply tokens, greedy, every reply token checked. Generation never stops early on an end-of-sequence token. A system passes on a model when all six checks pass.

    None of our checks try to forge a proof. Soundness and weight secrecy are not tested by our harness; instead, the glyph grades what each publisher states and proves.

    Three checks alter one input that the verifier must reject, and the other three test honest runs. A trivial system whose proof is just a keyed hash of the commitment, prompt, and reply computed from the weights would pass all six checks and appear on the ladder as Passed. However, it would receive no ranking position: ranking requires a recorded publisher statement (or our reading of one) that an accepted proof guarantees the committed model's own greedy reply.

    CheckPasses whenFails when

    Run check

    The publisher's prover ran as published at the pinned commit for 3 cold-start sessions, producing an accepted proof for every reply.

    passes
    The model's prompts are divided into 3 slots, and each slot has a complete cold-start session whose prove call exits 0 with an accepted proof for every request. The container is built from the pinned public commit as published, with no weakening flags.
    fails
    A slot accumulates 5 incomplete runs, the system's own code records a refusal caused by its inputs, or a counted session passes a weakening flag.
    cap
    Any session that hits the spending cap (120 USD on Llama 4 Maverick, 40 USD on other models) is stopped and recorded as incomplete.
    counted
    Each slot counts its earliest complete session by start time, never cherry-picked for speed. If a session missed Verify without weights only because a GPU was visible and was never re-verified, the slot passes to the next complete session from the same image and adapter commit that meets the check.

    Model check

    When we alter one weight, no proof built with the changed weights is accepted against the original commitment.

    passes
    Proving with one modified weight against the original commitment produces no accepted proof in 3 of 3 trials of the same change (a prover stop counts only when the publisher documents at the pinned commit that it signals mismatched weights). Checking an honest proof against the modified weights' commitment is rejected in 3 of 3 trials.
    fails
    A tampered trial was accepted, and running the system's own command outside our adapter accepted the same modified input.

    Prompt check

    When we alter one prompt token, the verifier rejects the proof.

    passes
    Changing one prompt token at a seeded position (fresh in each trial) causes the verifier to reject the proof in 3 of 3 trials.
    fails
    A tampered trial was accepted, and running the system's own command outside our adapter accepted the same modified input.

    Reply check

    Every proof covers all 512 reply tokens, and altering the first, last, or an interior reply token causes the verifier to reject the proof.

    passes
    Every accepted proof covers all 512 reply tokens. Changing the first token, the last token, or a seeded interior token (fresh per trial) causes the verifier to reject the proof in 3 of 3 trials at each position.
    fails
    A proof covered fewer than 512 reply tokens, or a tampered trial was accepted and reproduced with the system's own command outside our adapter.

    Verify without weights check

    The verifier reached every verdict with no model weights on disk and no GPU visible.

    passes
    Every counted verdict comes from a verify call with no GPU visible, no model files on disk, and a file-open trace confirming none were opened. A verdict from a GPU host still counts once the same proof is re-verified and accepted inside the same image on a host with no GPU.
    fails
    The file-open trace records a model file, or a verify call required one.

    Fidelity check

    Proved replies match more leading tokens of the original model than the pass bar (a deliberately damaged copy) does, tested at p < 0.05.

    passes
    The replies proved in counted sessions score above the pass bar in a paired one-sided sign-flip test at p < 0.05.
    fails
    The pass bar scores above the system's replies under the same paired test. If neither side is shown higher, the check remains not decided.
    score
    Each reply is scored by how many consecutive leading tokens match the original model's reply to the same prompt (0 to 512). The original is a Hub copy of the publisher's release at its release precision, pinned on each system page: 16‑bit for Llama 4 Maverick 17B-128E Instruct and Llama 3.1 8B Instruct, 32‑bit for GPT-2.
    bar
    The bar is the highest-scoring damaged control that every honest control still outperforms. Honest controls are the original rerun plus 8-bit and 4-bit quantizations (Q8_0 and Q4_K_M); damaged controls are listed on each system page. If no damaged control qualifies, the model has no bar and Fidelity stays not decided for every row.

    Checks not decided

    An undecided check is not a failure. When a row has no failed checks but at least one undecided check, its standing shows Not passed yet. System pages may also display verifier trials run outside the counted suite next to the relevant check, without affecting any check state.
    system limit
    The system cannot run what this check requires (publisher's quote linked), so the row cannot pass.
    not run
    Not run yet.
    not resolved
    The test ran, but its result does not yet count.
    not reproduced
    A verifier accepted a tampered input in our adapter, and we have not yet reproduced it with the system's own command.

    Figures

    Cost vs serving

    multiple
    Steady proving cost m divided by serving baseline b on the same model. GPU time counts only the H200 GPUs allocated to the job.
    m
    Mean GPU-seconds per proved reply (including generation) across 3 sessions. Proofs released within 1 s of the previous one form a release group. m measures the time from the end of the first group to the end of the last group divided by the replies released after the first group. If a system generates replies in a separate phase, m adds that phase's GPU-seconds divided by all session replies.
    b
    GPU-seconds per reply when serving the same request without a proof. The model publisher's release (FP8 on Llama 4 Maverick) runs on the pinned engine at full load using the fewest NVIDIA H200 GPUs that fit it. Full load is the lowest concurrency (doubling from 1 to 1,024) that reaches 95 % of peak throughput; if that happens only at 1,024, the model is not saturated and has no b.
    whole sessions
    A row has a steady m when every one of its 3 sessions has at least 3 release groups after the first and each group's per-reply time stays within 5 % of their median. Otherwise it has no steady multiple and reports whole-session GPU-seconds per reply divided by b, labelled “whole sessions of N replies”.
    parts
    When a system runs reply generation in its own phase, the figure splits into two parts, each divided by b: generation, and the remainder (proving for m, or commit and proving for whole sessions). Because not every system times them separately, the split appears only under Cost on the system page and never affects ranking.

    Tokens per second

    The request's 512 reply tokens divided by the GPU-seconds required for one reply on a single GPU, reported in tokens/s per GPU with the GPU model named. The proved rate covers whole sessions (matching Cost vs serving), and the served rate covers unproved serving at full load on the same GPU type. Dividing the served rate by the proved rate equals Cost vs serving.
    Because both rates depend on GPU hardware, neither is used for ranking (OR-3 ranks by the steady multiple m).
    Prefill (prompt processing) and decode (reply generation) are not timed separately in the stored records.

    Cost per reply

    steady
    Steady GPU time m converted to USD at the release's hourly H200 price.
    session
    Mean GPU-seconds per reply across 3 sessions (from the start of commit to the final proof, including generation), converted to USD at the same hourly price.

    Verify time per reply

    Total wall time of all verify calls in a session divided by the session's replies, averaged across 3 sessions. Re-verification runs never replace the session's own verify timing.

    Proof size per reply

    Total stored bytes of all proof files in a session divided by the session's replies (a proof covering multiple replies is counted once), averaged across 3 sessions in MB (1 MB = 1,000,000 bytes).

    Fidelity figure

    The percentage of reply positions where the system's top token matches the original model's reply token when fed the prompt followed by that reply token by token. Averaged across prompts (counting declined prompts as 0), with the model's standard 8-bit and 4-bit copies (Q8_0 and Q4_K_M) shown alongside.
    100 % means picking the original's exact token at every position. This metric compares top choices rather than full distributions (KL divergence compares distributions).
    Computed by the system's own scoring code on the reference reply rather than by the proved computation. It sets no check or petal grade.
    Why top-token agreement: greedy decoding chooses the top token at each step, so this measures how often the proved model makes the same choice as the original across all 512 positions, not just up to the first mismatch.
    Whenever a proved reply starts identically to the original's, both models saw the same prefix, so the proof fixes which token the proved model chose up to and including the first difference. The system's scoring code must pick that exact token at every such position (the count appears on the system page); otherwise we display the Fidelity check state instead of the percentage.

    KL to the original weights

    Mean KL divergence per scored token (in nats) between the committed weights file and the original model over 64 texts of 512 tokens, computed by llama.cpp on the committed file rather than the proved computation. Displayed for context; gates nothing.
    not measured
    Shown with the reason whenever llama.cpp cannot run the original model (such as Llama 4 Maverick's 16-bit weights) or cannot load the committed file and the adapter provides no distributions of its own.

    Order

    ranked
    Only systems that pass all six checks on a model are ranked.
    unranked
    A passing system is ranked only if its publisher states at the pinned commit (or we read its quotes as stating, marked with links) that an accepted proof means the reply is the committed model's greedy output for the prompt, and the level file records a numeric security level stated there for at least one verifier it ships. Otherwise the row is listed as Passed, not ranked with the reason. Level 1 sets no minimum bit floor.
    above
    One system ranks ahead of another when both have a steady multiple, its mean is at least 10 % lower, and its highest session m falls strictly below the other's lowest. Any system with a steady multiple ranks ahead of one without; two systems without one compare the same way using whole-session cost per reply.
    position
    A system's position is 1 plus the number of systems ranked strictly ahead of it, so tied systems share a position. It counts among the systems run on its own model only.
    below
    Ranked systems appear first, followed by passed unranked systems, then systems that have not passed, sorted alphabetically within each group. Systems that have not passed still show their checks and figures without a position.
    largest model with a passed row
    The largest model by total parameters that has at least one passing system whose publisher states that an accepted proof represents the model's own reply.
    glyph
    The glyph never changes a system's ranking.
    models
    Systems are never ranked across models.

    Glyph

    The glyph shows how close a system comes to an ideal prover across five separate properties, never summed into a single score. Four petals are graded from the publisher's documentation at the pinned commit, while Fidelity comes from our own fidelity run (and stays undecided whenever the Fidelity check does). A failed check flips any contradicted petal to Failed, an undecided check lowers nothing, and a passed check raises none. Whenever a rule is ambiguous, the lower grade applies.

    Met Mostly met Partly met Not met Failed Not stated Not decided

    Each system page shows what every petal still needs for Met and who must act, computed directly from these rules.

    Integrity

    soundness

    Could a provider get a reply accepted that the committed model did not actually compute? Integrity grades the soundness bound stated by the publisher and whether it covers the exact setup we run. It protects the customer. Met requires a proved error bound of at most 2^-128 (128 bits) covering what we run.
    protects
    the customer
    question
    The soundness bound stated by the publisher on a false reply being accepted, whether it is proved, and whether it covers the exact setup we run.
    Met
    A proved soundness bound covering what we run, with every exponent at least 128.
    Mostly met
    A proved bound covering what we run with every exponent at least 100, or a Met-level bound that depends on our reading.
    Partly met
    Any other stated bound above Not met: conjectured, not shown to cover what we run, or a proved bound with an exponent between 80 and 99.
    Not met
    The bound holds only against a weaker adversary, has an exponent below 80, or is unproved with an exponent below 100.
    Not stated
    The documentation read at the pinned commit gives no soundness bound with exponents.
    Failed
    Our Model, Prompt, or Reply check failed.
    Not decided
    We have not yet read the publisher's documentation at the commit we run.
    covers what we run
    The bound applies to our benchmark settings against any cheating prover, covers a full reply (or one proof per reply), and holds when each reply is verified individually. Records show its preconditions hold for our files, and the verifier program we run is proved or stated to match the bound. An unrecorded batch size is treated as uncovered.
    exponent
    In 2^-t or q/2^t, the exponent is t, where a larger exponent means a smaller forgery probability. When a bound sums multiple terms, every term must clear the threshold. We read exponents verbatim as stated by the publisher without inventing our own bit counts or fixing a query budget q. A bound stated per segment or layer is read per part as stated; not covering a full reply counts as a coverage gap without lowering the grade further.
    Integrity grades soundness only, not completeness (which the Run check tests). Failing our Model, Prompt, or Reply checks flips this petal to Failed, though passing them never measures the soundness bound.

    Confidentiality

    zero knowledge of the weights

    Does checking a proof leak the model's weights? Confidentiality grades what the publisher states and proves about weight hiding. It protects the provider. Met requires zero knowledge proved for the exact setup we run.
    protects
    the provider
    question
    What the publisher states and proves about proofs keeping the model's weight values secret.
    Met
    A zero-knowledge theorem proved for the exact configuration and batch size we run, stated for the actual programs we run, paired with a published list of visible values containing nothing that depends on the weights.
    Mostly met
    A zero-knowledge theorem is proved, but at least one requirement for Met is missing.
    Partly met
    The publisher states that proofs hide the weights, without a zero-knowledge theorem.
    Not met
    The verifier receives the weights, or the publisher states that proofs do not hide them.
    Not stated
    The documentation read says nothing about hiding the weights.
    Failed
    Our Verify without weights check failed.
    Not decided
    We have not yet read the publisher's documentation at the commit we run.
    Confidentiality does not grade hiding the model architecture, because every Level 1 model has open weights (a closed-weights level would grade it). Failing Verify without weights flips this petal to Failed, though passing it cannot measure what a proof reveals.

    Fidelity

    quantization error, in matched leading tokens

    Does the proved model behave like the publisher's original release? Because provers usually run a quantized copy with fewer bits per number, Fidelity compares the proved replies against the original using standard 8-bit and 4-bit copies as yardsticks. It protects the customer. Met requires scoring closer to a rerun of the original than to the 8-bit copy.
    protects
    the customer
    question
    How closely the proved replies match the publisher's original release, measured against standard 8-bit and 4-bit quantized copies.
    Met
    Replies score significantly above the midpoint between a rerun of the original and the 8-bit copy, in a fidelity run sending one request at a time.
    Mostly met
    Replies score significantly above the midpoint between the 8-bit and 4-bit copies.
    Partly met
    • The Fidelity check passed, but replies are not shown above the midpoint between the 8-bit and 4-bit copies.
    • Or no claim card exists, or its decoding policy accepts tokens other than the model's top token.
    • Or a reference copy needed for a midpoint did not run, failed, or was scored on a different number of replies.
    Failed
    The Fidelity check failed: the pass bar (a damaged copy) scores above the system's replies.
    Not decided
    The Fidelity check is not decided, or no fidelity record is stored.
    halfway
    The arithmetic midpoint of two reference copies' unrounded mean scores.
    one request at a time
    Every part of the model's fidelity run executes one request at a time in llama.cpp (slots = 1). When pinned llama.cpp cannot run the original model, the original and its rerun execute in vLLM in a single batched call, which does not count as one-at-a-time (the rerun sends prompts in reverse order so its batches differ from the first pass).
    shown above
    Our paired sign-flip test gives p < 0.05 comparing the system's scores against the midpoint.
    measure
    This petal is graded on matched leading tokens, the same metric used by the Fidelity check. The headline Fidelity figure reports top-token agreement and sets no grade.

    Formally verified

    machine-checked soundness proof

    Has a proof assistant checked the mathematical proof that false replies are rejected, and does that proof reach the actual verifier binary we run? It protects the customer. Met requires a machine-checked proof covering the verifier we run.
    protects
    the customer
    question
    How far a machine-checked soundness proof reaches: part of the protocol, an abstraction of it, the protocol with the model, or the actual verifier binary we run.
    Met
    Rebuilt by us: the proof covers the actual verifier binary we run from raw input bytes to verdict, lists its trusted base, and leaves no input-reading code outside the proof.
    Mostly met
    Rebuilt by us: the proof covers the protocol including the model's computation, or covers the verifier binary with a gap in its trusted base or input-reading code.
    Partly met
    Rebuilt by us: the proof covers an abstraction of the protocol (the protocol without the model, or the model without the protocol) or only part of the protocol. Theorems whose conclusion is not about the model, or builds relying on non-standard axioms, also stop here.
    Not met
    The publisher states that nothing is machine-checked.
    Not stated
    The documentation read names no machine-checked proof.
    Failed
    Our rebuild of the named theorem failed or reported undeclared axioms, or our Model, Prompt, or Reply check failed on a system claiming Met.
    Not decided
    A machine-checked proof is claimed, but our rebuild is not recorded yet or stopped before reaching a verdict, or we have not yet read the documentation at the pinned commit.
    build
    Every grade above Not met requires a recorded rebuild of the named theorem at the pinned commit using the publisher's pinned toolchain. We run the publisher's own verification command unpatched and log its output. We do not audit the theorem's formal semantics; we grade its reach from the publisher's quotes shown with the petal.
    above Partly met
    Grades above Partly met require a theorem whose conclusion refers to a formal definition of the model, rebuilt using only the proof assistant's standard axioms (in Lean: propext, Classical.choice, and Quot.sound, with no sorry). Each system page notes that no outside expert has reviewed the theorem statement.
    the code
    Only the verifier binary we actually execute counts as the code. A verified reference verifier that we do not run counts at the protocol level.
    protocol or code
    A proof about a formal model of the algorithm verifies the protocol rather than the implementation. Level 1 distinguishes the full protocol (including the model's computation) from an abstraction (omitting either the model or the protocol). Only a proof covering the actual verifier binary verifies the code.
    scope card
    Printed under a system's petals for context without affecting any grade, since this petal covers soundness alone. Because soundness belongs to the verifier and zero knowledge to the prover, opposite-party cells read 'does not apply'.
    Formally verified does not grade prover code, which affects completeness and zero knowledge (shown separately on the scope card without setting a grade). Publisher caveats outside the five graded criteria (reach, conclusion, input-reading code, axioms, and our rebuild) are displayed without lowering the grade. Two rule questions remain open: whether grades above Partly met should require showing the verifier accepts honest proofs on our files, and whether trials of alternate verifiers should affect grades (currently they do not).

    Trust assumptions

    trusted setup or party

    Does checking a proof rely on trusting anyone beyond mathematics, such as whoever ran a one-time setup or controls a hardware signing key? It protects the customer. Met requires the publisher to state that verification rests on cryptography alone.
    protects
    the customer
    question
    What verification depends on beyond cryptography: a setup secret, a fixed group of parties, or a hardware vendor's or other trusted key.
    Met
    The publisher explicitly states that soundness rests on cryptography alone and no setup produced a secret. Proofs must also be publicly verifiable unless the publisher is silent on who can check them.
    Mostly met
    An open setup ceremony with a public transcript that holds if at least one participant was honest, or Met-level facts established only via our reading.
    Partly met
    Relies on one honest party within a fixed group, a live challenger within a time window, or proofs only a designated verifier can check.
    Not met
    Relies on a single-party trusted setup, a hardware vendor's key, or another trusted key.
    Not stated
    The documentation read says nothing about what soundness depends on.
    Not decided
    We have not yet read the publisher's documentation at the commit we run.
    This petal does not grade which real model a commitment represents, nor whether soundness is proved or conjectured (Integrity covers that). Preconditions requiring public files to be fixed before hashing are also tracked under Integrity.

    Why a petal is low or not decided

    not stated
    Not statedNot stated (drawn as an outline): the publisher's documentation at the pinned commit says nothing about this property. Because users cannot rely on an unstated guarantee, we grade silence at the bottom rather than leaving it undecided.
    below Partly met, as the publisher states it
    Not metNot met or Failed (drawn filled, name struck): the publisher explicitly states that the property does not hold, or what it states falls below Partly met.
    a check failed, or the proof build failed
    FailedNot met or Failed (drawn filled, name struck): one of our entry checks failed, or our rebuild of the publisher's machine-checked proof failed or reported undeclared axioms.
    not read yet
    Not decidedNot decided (drawn hollow): our properties record is missing, uses an older schema, or was read at a different commit than the one we ran (or the row has no recorded commit). We never mark unread documentation as silent.
    Fidelity check not decided or not recorded
    Not decidedNot decided (drawn hollow), Fidelity only: the Fidelity check is not decided, or the row has no recorded fidelity scores.
    waits on our finished build of the publisher's machine-checked proof
    Not decidedNot decided (drawn hollow), Formally verified only: the publisher claims a machine-checked proof, but we have no completed rebuild of the named theorem at the pinned commit using the publisher's pinned toolchain (or the recorded build timed out or was killed before finishing). If the publisher pins no toolchain, no build can match.

    Our reading

    At least one fact behind this grade comes from our interpretation of multiple passages rather than a single explicit sentence from the publisher. The petal flags that it relies on our reading, links the supporting quotes, and caps the grade at Mostly met for every system equally. We never infer claims simply from the name of a cryptographic construction.

    Systems not run

    Systems without a row on the ladder are listed below with a single reason: the first criterion below that applies in their documentation, checked in order. Each entry cites and links the specific fact behind its classification.

    Another kind of check

    Does not produce a cryptographic proof of inference; instead uses hardware attestation, re-execution, a dispute game, or an activation fingerprint.
    opML
    Uses optimistic fault proofs: “the challenge game and single step verification”. (new tab)
    Private ML SDK
    Verifies via a hardware signature over the SHA-256 hashes of the HTTP request and response bodies rather than generating a cryptographic proof. (new tab)
    Tinfoil
    Relies on hardware enclave attestation as described in its architecture docs rather than generating a cryptographic proof (checked 2026-11-08). (new tab)
    TOPLOC
    Uses activation fingerprints rather than a proof: its validator “Validates against predefined error thresholds”. (new tab)
    Verde (with RepOps)
    Uses refereed re-execution: “we design Verde, a dispute arbitration protocol”. (new tab)

    A different statement

    Proves a different claim from Level 1's requirement that the reply is the committed model's greedy output for a prompt given to the verifier.
    VerInf
    It “certifies an observed output stream against a committed integer model”, “proving similarity rather than exact reproduction”. (new tab)
    zkGPT
    Omits token generation from the proof (Appendix A): “we omit proving the final linear projection and the token generation procedure” (archived copy from 2025-09-02). (new tab)

    No public verifier

    No public repository to pin, or no standalone public program that verifies a stored proof against an externally supplied commitment (including provers and verifiers that only run together, or verifiers that read the commitment from inside the proof file).
    Attestable prover
    No public repository: the blog post describes “a standalone CPU verifier” without linking to source code (checked 2026-11-15). (new tab)
    DeepProve
    deep-prove-cli verify takes only the proof file and verifies against a verifier key embedded inside that file, with no documented way to derive the key from model weights alone (checked at 9d1a53e2). (new tab)
    JOLT Atlas
    Its single binary (the prove example) “proves and verifies any model in the zoo”, with no standalone verifier at 329b21ef for checking a stored proof. (new tab)
    NanoZK
    No public code: the paper does not link to a repository (checked 2026-11-15). (new tab)
    zkLLM
    Interactive prototype without a standalone verifier: “the prover and verifier works are implemented side-by-side for each component”. (new tab)
    zkPyTorch
    No public code: neither the paper nor polyhedra.network links to a repository (checked 2026-11-08). (new tab)

    Licence

    No licence file at the repository root, or a licence granting no use rights. Licences permitting internal testing and evaluation cover our own runs, though they do not permit redistributing the software.
    EZKL
    No licence file at the root of the repository at e196b111. (new tab)
    JSTprove
    Its licence: “NO USE RIGHTS ARE GRANTED BY THIS LICENSE.” (new tab)

    No configuration at the request

    No documented configuration proves a reply to Level 1's request on any Level 1 model.
    LuminAIR
    The README demonstrates general computational graph proofs and lists no language-model configuration (checked at 9026bd3d). (new tab)
    Remainder (Community Edition)
    A general-purpose GKR prover; its README lists no language-model circuit or configuration (checked at 5687fe7f). (new tab)
    ZKML
    Demonstrates single forward-pass proofs without autoregressive reply generation; its only language-model example is a distilled GPT-2 (checked at 43789582). (new tab)
    ZKTorch
    Proves model execution without specifying autoregressive token generation or a Level 1 model configuration (checked at 63b9c689). (new tab)

    Not yet run
