    Checks

    The reason for each rule on this page: How we compare.

    Terms

    proof
    The files a system writes for one reply. Its verifier is a program that accepts or refuses them. Each publisher states what an accepted proof shows, for example that each reply token is the committed model's top choice, and under which assumptions. A sound verifier accepts a reply that statement does not cover only with the probability its security level bounds.
    commitment
    The value a system's commit step produces: it fixes the weights a later proof refers to. The verifier is given the value from our record of that step, never from files sent with a proof.
    request
    512 prompt tokens, 512 reply tokens, greedy, every reply token checked. The same request for every system on every model.
    ladder
    The models, largest first, each an open-weights release named by its publisher. A system has a row on each model it was run on.

    Unforgeable

    green
    A soundness level of 128 bits or more, proven for the verifier code the system runs.
    amber
    A level that is conjectured, below 128 bits, stated per part only, or proven for the protocol but not for the code run.
    red
    No level stated, or our Model, Prompt or Reply check failed.

    Weights hidden

    green
    Zero knowledge proven for the program run, with no leak beyond public sizes.
    amber
    Hidden with leaks the publisher lists, or proven for the protocol but not for the program run.
    red
    The checker receives the weights, hiding is off or not stated, or our No weight file check failed.

    Faithful model

    green
    The replies are not shown below a second run of the publisher's original weights.
    amber
    The replies score above the model's bar, and the second run of the original weights scores above them.
    red
    Our Fidelity check failed.

    Any model

    green
    The system passed on every model of the level.
    amber
    It passed on more than one model, not all.
    red
    It passed on one model or none.

    Only the verifier trusted

    green
    Soundness rests on cryptographic assumptions alone (for example a random oracle): no setup ceremony, hardware maker's key or third party. Public files fixed before the hash do not count: every non-interactive proof has them.
    amber
    One honest party among several, or a setup the publisher says anyone can reproduce.
    red
    A trusted setup, hardware attestation or a trusted key, or not stated.

    A hollow petal is not decided yet: a measured petal with no result, its cause beside it. A petal read from the publisher's documents is red where they are silent.

    The six checks

    A system passes on a model when it holds all six checks there. A failed check turns its petals red; a held check never turns a petal green.

    These checks run each system's own prover and verifier. None attempts a forged proof: soundness and weight secrecy are not tested.

    Run

    held
    Each of the 3 session slots holds a complete session, built from the public pin, unpatched, with no weakening flag.
    failed
    A slot has 5 incomplete runs, the system's own code refuses the request, or a counted session used a weakening flag.
    evidence
    every session's run record

    Model

    held
    A proof made after one weight was changed is not accepted, and an honest proof checked against the changed weights' commitment is refused, in 3 of 3 trials each.
    failed
    Any trial is accepted: the verifier accepts a proof for weights other than the committed ones.
    evidence
    the controls record

    Prompt

    held
    A proof checked with one prompt token changed is refused, in 3 of 3 trials.
    failed
    Any trial is accepted: the verifier accepts a proof for a prompt other than the one proved.
    evidence
    the controls record

    Reply

    held
    Every accepted proof covers all 512 reply tokens, and a changed reply token is refused at the first, the last and one seeded interior position, in 3 of 3 trials each.
    failed
    A proof covers fewer reply tokens, or any trial is accepted: the verifier accepts a reply with a token changed.
    evidence
    the run records and the controls record

    No weight file

    held
    Every counted verdict came from a check run with no GPU visible, on a filesystem holding no model file, under a file-open trace that names no model file.
    failed
    The trace names a model file, or a check needed one.
    evidence
    the file-open trace of every check

    Fidelity

    held
    The system's replies score above the model's bar: the damaged copy of the model that every honest copy scores above, scored by the leading tokens each reply shares with the reply of the publisher's original weights.
    failed
    The bar scores above the system's replies: they match the replies of the publisher's original weights for fewer leading tokens than those of a copy damaged on purpose.
    evidence
    the model's fidelity record

    Undecided

    system limit
    the system cannot do what the test needs; the publisher's sentence is quoted
    not run
    the test has not been run
    not resolved
    the test ran and decided nothing
    not reproduced
    failed in our adapter, not yet reproduced outside it

    Figures

    Multiple of serving

    proving
    m, GPU-seconds per further proved reply. In one session, proofs released within 1 s of the previous release form a group. m is the GPU time from the first group's last release to the session's last release, over the replies of the later groups, generating the replies included. The mean of 3 sessions, each from a cold start.
    serving
    b, GPU-seconds per reply of plain serving: the publisher's own release, served by the pinned engine on the fewest H200 that hold it, at full load. Full load is the lowest concurrency that reaches 95 % of the highest rate, on a ladder up to 1,024 concurrent requests.
    multiple
    m over b, on one model. Both halves are GPU-seconds of the same GPU at one price, so the multiple is the same in dollars.
    cold
    A system whose sessions release too few groups, or uneven ones, has no m. It prints its session cost per reply over b, labelled as cold sessions.

    Cost per reply

    steady
    m in USD, at the release's price of one H200 GPU-hour.
    session
    Where a system has no multiple: the GPU time from the start of commit to the release of the last proof, over the session's replies, in USD.

    Check time per reply

    check
    The time the system's verifier takes on a session's proofs, over the session's replies.

    KL to the reference

    kl
    The mean KL divergence per scored token, in nats, of the file the system commits from the reference: the publisher's original weights, 16-bit for Llama 4 Maverick 17B-128E Instruct and Llama 3.1 8B Instruct, 32-bit for GPT-2.
    computed by
    llama.cpp, on the committed file, not on the proved computation. It is printed and decides no check.
    none
    Not measured where llama.cpp cannot load the committed file.

    Order

    ranked
    Only a system that passed on a model, and only on that model.
    above
    A system is placed above another when its multiple is at least 10 % lower and its highest session m is below the other's lowest. A system with a multiple is placed above one without. Two without compare the same way on session cost per reply.
    position
    1 plus the number of systems placed above. The count of systems run on the model is printed beside it.
    unranked
    A system that passed is ranked only when its publisher states a security level at the pinned commit. The level is printed as stated: our tests cannot tell 60 bits from 128.
    glyph
    The glyph never moves a position.
    models
    Nothing is compared across models: they differ in what serving costs and in how proving scales.
