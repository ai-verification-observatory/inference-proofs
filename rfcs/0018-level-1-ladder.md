# RFC-0018: Level 1: the ladder, six checks, cost and fidelity

- Authors: 0xchqrles
- Created: 2026-11-10
- Requires: RFC-0002, RFC-0003, RFC-0004, RFC-0005, RFC-0006, RFC-0008, RFC-0009, RFC-0010, RFC-0012, RFC-0014, RFC-0015, RFC-0016, RFC-0017

Write "None." where a section has no content. Normative text uses MUST, SHOULD and MAY as defined in RFC 2119.

## Summary

This RFC defines Level 1, the first frozen benchmark specification, together with the public site it publishes. The site presents a leaderboard structured as a ladder with one rung per open-weights model, ordered from largest to smallest. On each rung, every system we can run unpatched receives one fixed request (512 prompt tokens and a 512-token greedy reply, with every reply token verified), six benchmark-run checks, and a single headline figure: how many times more expensive a proved reply is than serving the same request without a proof. Systems that pass all six checks are ranked by that cost multiple within their rung; nothing is divided or ranked across rungs. The frontier is the largest model on which at least one system has passed, marked directly on the ladder.

For everything published under Level 1, this specification replaces the six documentation properties of RFC-0016, the cross-model comparisons of v0.1, the per-token headline of RFC-0004, and Part B of RFC-0017, while keeping the measurement core intact (the adapter contract, runner, external timing, provenance, and schemas). The frozen definition lives in `levels/L1.yaml` (schema `level/1`), and this RFC specifies what every field means and how every published state and figure derives from stored records. Wherever this RFC conflicts with an earlier RFC on a Level 1 release, this RFC takes precedence.

## Motivation

- At their pinned commits, no two runnable systems support the same model. FlashProve accepts only Llama 4 Maverick's dimensions ("only models of width 5120 and head width 128 are supported", `prover/weights_blocks/gguf_source.cuh` L29 to L30 at `9e2bdd8`), while SASH proves dense Llama architectures (all its recorded runs target Llama 3.1 8B). Sorting them in one table compares models rather than provers, which v0.1 did.
- FlashProve's v0.1 headline figure was inaccurate. Because FlashProve releases proofs in batches of 24 roughly 171 s apart, RFC-0004 INV-SCOPE-5 counted 119 requests where only 96 were produced. Recomputed from release timestamps, the four H200 runs actually measure 7.060, 7.082, 7.128, and 7.195 GPU-seconds per request rather than 5.746 (`results/v0.1/flashprove/*-fp-maverick-w1024-b24-prover-h200-hosted-*/run.json`).
- In v0.1, the two systems ran incompatible request shapes: FlashProve checked a single reply token after a 1,024-token window, whereas SASH proved 64 reply tokens. RFC-0017 made the request the unit of comparison, but a shared request definition was still missing.
- RFC-0016's glyph reported publisher documentation, yet readers naturally interpret green cells as empirical test results. Four of its six properties had no test behind them, and no Model bound control ran in v0.1.
- Without a fidelity gate, a prover could aggressively quantize a model to make proving cheap while drifting far from the publisher's weights. Nothing in v0.1 measured that gap.
- Readers asked for a clear leaderboard: labs should have a clean target at the top of each rung, and policy readers should see within a minute which systems pass, on which models, and at what cost.

## Goals

- Present one clear page that ranks what can be fairly compared and states everything else as plain fact.
- Back every check state with a test we executed, and compute every glyph petal purely from stored records (our runs plus verbatim facts copied from publisher documentation at the pin).
- Use one fixed request across the entire level so the cost multiple means the same thing on every rung.
- Define a cost metric that cannot be gamed by cherry-picking window lengths, batch sizes, or serving baselines.
- Enforce a fidelity gate that blocks heavily degraded copies while reporting KL divergence alongside it.
- Freeze the level file before the first counted run so no constant or prompt is selected after seeing results.

## Non-Goals

- Empirically testing cryptographic soundness or weight secrecy. No check attempts to forge a proof, and the site states this clearly.
- Recomputing publishers' stated security levels. Stated levels are printed verbatim (recomputation is reserved for the Level 2 draft below), and Integrity compares written bound exponents directly without deriving a bits figure (Q9).
- Writing, modifying, or formally auditing a publisher's machine-checked proof, or reviewing what its theorem means. Level 1 runs the publisher's own documented proof-checking command unpatched and logs the outcome; the claimed scope is taken from the publisher's documentation and printed alongside the petal (MC-5, amended 2026-11-15 and 2026-11-16).
- Supporting closed-weights models, lab-submitted runs, third-party reruns, or sealed provers in Level 1.
- Ranking across rungs or dividing one rung's cost by another's.
- Writing final disclosure wording (About page and operator disclosures), which the owner finalizes before launch.

## Proposed Design

### Terms

- **Level.** A frozen benchmark specification fixing rungs, request shape, checks, ranking rules, and constants in `levels/L<k>.yaml`. Changing rules requires a new level file (§Levels).
- **Release.** A dated snapshot of results published under a single level (RFC-0009). Level 1 releases use `v1.<n>`.
- **Rung.** One open-weights model identified by its publisher's original release, paired with its serving baseline, fidelity reference, and one workload per system run on it.
- **Request.** 512 prompt tokens followed by a 512-token greedy reply, with every reply token verified (task `p512-o512`, RFC-0017). End-of-sequence tokens do not halt generation: if an EOS token is the greedy argmax, it is emitted as part of the reply and generation continues (matching vLLM's `ignore_eos`). Any reference or control engine that would normally suppress EOS MUST be configured to preserve this behaviour (FI-1).
- **Request A** (proposed 2026-11-27, CO-10, awaiting the owner's decision). A rung's diagnostic request: the level's 512-token prompts with a 1-token greedy reply, served on the ladder only. It is not the request: it ranks nothing and no session runs it.
- **Session.** One cold-start run executing `setup`, `commit`, and `prove` across `N` requests, where `N` is the rung's `requests_per_session`. A session is complete when `prove` exits 0 and releases an accepted proof (or joined proof set, RFC-0017 INV-REQ-2) for every request.
- **Slot.** Each rung defines three session slots. Slot `k` proves prompts `[(k-1)·N, k·N)` from the rung's prompt stream. Failed sessions retry in the same slot on the same prompts.
- **Row.** One proving system evaluated on one rung.
- **Check.** One of six benchmark-run tests, each ending as `held`, `failed`, or `undecided` (with a cause), displayed on the site as "passed", "failed", and "not decided" (amended 2026-11-16, Q37).
- **Passed.** All six checks are `held`. A row's standing displays as "Passed", "Passed, not ranked: <reason>", "Not passed: <Check> check failed" when any check failed, or "Not passed yet: <Check> check not decided" when every non-passing check is undecided (amended 2026-11-16, Q37).
- **Multiple.** Steady GPU-seconds per further proved reply divided by the serving baseline's GPU-seconds per reply at full load (§Cost). For every release after v1.0 the site prints two multiples of a further reply, proving and total (CO-9, Q55).
- **One-time work.** Work that depends only on the system's pin, the model and the request shape, never on a request, and whose result every later reply reuses: the `commit` call, and a setup run a session reuses (CO-9). Printed apart, never divided by N.
- **Frontier.** The largest rung (by total parameter count) containing at least one passed row.

### The level file

`levels/L1.yaml` uses schema `level/1` (`schema/level/1.schema.json`), authored in YAML and validated by gate G2. Each field defines a constant referenced by rules below:

| Field | Meaning |
|---|---|
| `id`, `name`, `frozen` | `L1`; public display name "Level 1"; freeze date, or null while in draft |
| `request` | prompt and reply token counts, decoding rule, `ignore_eos: true`, `every_reply_token_checked: true` |
| `prompts` | generator `beacon-window/1`, corpus digest, beacon chain and round (§Prompts) |
| `rungs[]` | rung ID, model name and publisher, total parameters, per-system workloads, serving record, fidelity reference and controls, `requests_per_session` |
| `sessions` | slot count (3), attempt cap per slot (at most 5 runs per slot), per-session USD spending cap |
| `steady` | release group gap (1 s), minimum later groups (3), group variance tolerance (0.05) |
| `baseline` | concurrency ladder, plateau tolerance (0.05), warm-up and timed batch counts per concurrency, ladder prompt count |
| `order` | ranking margin (0.10) |
| `fidelity` | scoring metric, test type, alpha, resample count, seed rule |
| `kl` | text count and token length, evaluation tool |
| `systems` | per-system entries: stated security level (words and source) for ranking, Model check weight perturbation (CH-2), and `limits` naming any check impossible by design with publisher quote and source (CH-5) |
| `price` | price basis key from `reference/<release>.yaml` |

Draft level files (`frozen: null`) support probes and development runs. Every counted run in a Level 1 release records the frozen level file's digest in its manifest, and `iproofs release freeze` rejects any release whose runs reference a different digest.

### Prompts

- PR-1. Generator `beacon-window/1` extends `corpus-window/1` (RFC-0003) by seeding it from a public randomness beacon: the first 8 bytes (big-endian) of the beacon round's 32-byte hex `randomness`. Sampling is otherwise identical, calling `random.Random(seed).random()` once per prompt to extract 512-token windows from the corpus using the rung's tokenizer.
- PR-2. The beacon uses drand's `quicknet` chain (one round every 3 s), selecting the first round produced after the commit timestamp that freezes the level file so prompts cannot be known when constants are chosen. `iproofs level beacon` computes that round from the commit timestamp, queries two public relays, verifies that both answers match and satisfy `randomness == sha256(signature)`, and writes `levels/L1-beacon.json` (round, randomness, signature, relays, and fetch date). `level check --frozen` rejects any other stored round, while draft probes may pick any past round. The harness does not verify the BLS signature directly, though anyone can verify it with the drand client. Amendment of 2026-11-15: because a git commit timestamp comes from the committer's own clock rather than a third party, "nobody chooses the round" applies strictly to a single freeze, and refreezing draws new prompts. Level 1 was frozen three times on 2026-11-11 at 11:13:02, 12:54:50, and 14:03:50 UTC (commits `6f89f42`, `a082b2c`, and `0032bcc`) to perform the initial freeze and update constants (adding a GPT-2 rung, then adjusting the serving ladder), taking fresh rounds `33864073`, `33866109`, and `33867489`, each emitted 1 s after its commit time (GitHub's event log, checked 2026-11-15, shows each commit pushed 2 s after its commit time). All counted runs use the third round and the third freeze's digest.
- PR-3. Each rung draws one contiguous stream in fixed order: first its `3·N` session prompts, then `kl.texts` KL windows of `kl.tokens` tokens, and finally `baseline.prompts` (4,096) prompts for the serving ladder.

### Sessions and what is recorded

- SE-1. Each session is a cold-start job: fresh container, fetched and verified weights, `setup`, `commit`, and one `prove` invocation given all `N` slot requests at once, ending on its own.
- SE-2. The harness records wall-clock time for every call, release timestamps for every proof via the release watcher (RFC-0011), and which GPUs the system binds. Machine-seconds count GPU-seconds of bound GPUs only (RFC-0006 R1); any extra GPUs on the rented host are listed on the system page without being billed to the figure.
- SE-3. Three complete sessions count per row, one per slot, choosing the earliest complete run by start time in each slot. Incomplete sessions are archived with exit codes and trailing logs (AGENTS.md rule 5), excluded from metrics and all checks except RUN (§Checks), and listed on the system page. Each slot allows at most five attempts; five incomplete runs in a slot fail RUN.
- SE-3a. If a counted session misses VERIFY WITHOUT WEIGHTS solely because a GPU was visible to verify calls on the job's host (with all traces written and no model file opened) and its proof bytes were not retained for re-verification (CH-4a), the slot passes to the earliest subsequent complete session at the exact same pin (image and adapter commit) whose verdicts satisfy CH-4. The replaced session is excluded from metrics and checks and listed on the system page with that reason. Sessions are never replaced because of timing figures, and replacement strictly selects the first qualifying session by start time. Discovery (2026-11-13): SASH's verifier loads the CUDA driver and NVML, which open GPU device nodes on GPU hosts even without an allocated GPU, whereas it verifies cleanly with no GPU on a CPU verifier host.
- SE-3b (amended 2026-11-15). A run counts as a session, control run (CH-1b), or replacement (SE-3a) only if RFC-0014 classifies it as eligible for the release (belonging to the release, valid `manifest/1`, `self_test.passed` true, matching the release's claim card digest, and clean harness and adapter trees). Before `release.yaml` exists, the active card digest is checked against the repository's current card for that system and configuration so an edited card invalidates prior runs. Ineligible runs enter no figures or checks, do not count toward the five-attempt cap of SE-3 (the fault belongs to the host or working tree, not the prover), remain archived in `results/` (APP-1), and appear on the system page with their reason codes (`ineligible_sessions` in the board file). Discovery (2026-11-15): SASH's `2026-11-13-sash-l1-l31-8b-p512-o512-prover-h200-hosted-2`, which had replaced slot 2's first session under SE-3a, ran on a host that failed its self-test (`ST-SAMPLER`, `ST-JITTER`); slot 2 therefore reverted to its first session (which verified with a GPU visible), leaving VERIFY WITHOUT WEIGHTS `undecided` until an eligible replacement runs.
- SE-4. Any session reaching the rung's spending cap (`rungs[].cap_usd`, defaulting to `sessions.cap_usd`) stops and records as incomplete with cause `cap`. The cap is a uniform level constant for every system on a rung.
- SE-5. A deliberate refusal ends the slot immediately. If the system's own code rejects the request based on its inputs (an intentional refusal quoted from the trailing logs, not an adapter bug, host fault, timeout, OOM, or spending cap), RUN fails without retrying because fixed prompts and greedy replies would trigger the exact same refusal. Reviewers record this in `results/<release>/<system>/refusals/slot-<k>.json` (`refusal/1`) citing the run, refusal message, upstream source line, and upstream commit (`upstream.commit`, owner decision 2026-11-11). RUN consults a refusal record only when its `upstream.commit` matches the row's active sessions; refusal records from earlier pins stay archived in `results/` without affecting newer pins (amended 2026-11-15: restored SASH slot 1's refusal at upstream `eb95bfa`, which had been removed on 2026-11-11 when moving to `4f41667`, while slot 1 sessions at `4f41667` completed cleanly).

### Cost

All cost figures are measured in GPU-seconds of bound H200 GPUs, with USD conversions computed from the release's price basis (RFC-0006 C7). Because provers and baselines use the same GPU type and price, the multiple is invariant to unit choice. Under the 2026-11-16 amendment (Q39), USD amounts print exclusively in the Cost block of system pages (depth 3) and in rules on the Checks page (depth 4), never on the ladder, Scale page, system-page band or Figures row, share cards, alt text, page descriptions, or search entries.

- CO-1. **Session cost per reply.** For a single session, total GPU-seconds from the start of `commit` to the release of the `N`-th proof divided by `N`, capturing generation wherever it happens. The row reports both the mean across the three counted sessions and each individual session's value.
- CO-2. **Release groups.** Proofs released within `steady.group_gap_s` (1 s) of the preceding release form one group `g` with count `n_g` and timestamp `t_g` (its last release).
- CO-3. **Steady seconds per further reply, `m`.** For a session with release groups `1..G`, `m = (t_G − t_1) × gpus / (n_2 + ... + n_G)`, counting every GPU-second spent on replies released after the first group. When an adapter generates all replies in a separate pre-proving phase (as FlashProve does because `cp_prove` refuses a GPU held by another process), the adapter emits start and end marks (AD-4) timed by the release watcher, and `m` adds that phase's GPU-seconds divided by `N` so generation is always included. Steady state is valid when `G − 1 ≥ steady.min_later_groups` (3) and every later group's per-reply time `(t_g − t_{g−1}) / n_g` lies within `steady.tolerance` (5 %) of the median of those per-reply times; otherwise the session lacks a steady state with cause `too few groups` or `uneven groups`. A row has a steady state only when all three counted sessions do, with row `m` equal to their mean.
- CO-4. **Baseline.** Each rung's serving record (RFC-0015 SRV-6) runs the publisher's release via the pinned engine on the fewest H200 GPUs that fit it. Across `baseline.ladder` concurrencies (`1, 2, 4, ..., 1,024`), the baseline runs one warm-up batch followed by `baseline.timed_batches` (3) timed batches of `c` distinct prompts drawn from `baseline.prompts` (PR-3), submitting each batch whole under the level's decoding rules with a per-batch cache salt to defeat prefix caching across batches. Rate `r_c` is replies per GPU-second across timed batches. Full load is the lowest `c` satisfying `r_c ≥ (1 − baseline.plateau) × max r`. If that occurs at the top rung of the ladder, throughput was still climbing beyond `baseline.plateau` and the rung has no baseline ("not saturated") until the ladder extends further. Because the initial Maverick run jumped 32 % from `c = 128` to `256` against a KV cache fitting roughly 593 requests, the ladder runs up to 1,024 (the engine's default batch cap) across `baseline.prompts = 4,096` distinct prompts. Baseline GPU-seconds per reply equal `1 / r` at full load; its concurrency, rate, and full ladder appear on the rung/system page. Reply token IDs are archived alongside `run.json` by digest outside git (RFC-0013 SIZE-1) since the baseline uses only release timestamps.
- CO-5 (amended 2026-11-13). **Multiple.** `m` divided by the baseline's GPU-seconds per reply, with both numerator and denominator reported. Rows lacking a steady state have no steady multiple and instead report session cost per reply divided by baseline GPU-seconds per reply, labelled "whole sessions of N replies" (renamed from "cold sessions of N replies" on 2026-11-13 to clarify that timing begins at `commit` under CO-1 and excludes weight loading). That scope label appears under the figure on the system page and in hover titles, while the ladder, Scale page, and share cards print the figure alone (SI-8). Amendment of 2026-11-15 (Q29): wherever a row has whole-session figures, the site displays the whole-sessions multiple across the ladder, Scale page, system-page band, and share cards so two rows on the same rung never display mismatched scopes (amended 2026-11-16, Q39: USD cost appears under Cost only, while the ladder and band show the rate pair under CO-8). Steady `m` still drives ranking (OR-3) and appears under Cost as the steady multiple, leaving positions, states, and stored figures untouched. Amendment of 2026-11-26 (Q55): for every release after v1.0 the site prints CO-9's two multiples of a further reply in place of the whole-sessions multiple, on the ladder, the Overview page, the band and share cards; the whole-sessions figures stay computed and stored, and stand under Cost at depth 3.
- CO-7. **Generation and proving.** When an adapter separates reply generation into its own phase (AD-4), `m` splits into a generation part (phase GPU-seconds divided by `N`) and a proving part (`m` minus generation), each also divided by the baseline. Ranking uses `m` alone; systems without a separate phase have no split. Amendment of 2026-11-13 (Q15): session cost per reply (CO-1) splits identically into generation (`phase GPU-seconds / N`) and commit-and-proving (`session cost − generation`, spanning `commit`, the non-generation portion of `prove`, and inter-call gaps), averaged across the `n` counted sessions. Amendment of 2026-11-15: system pages also break session cost per reply down by timed call with ranges (`commit` call GPU-seconds over `N`, generation phase if present, and the remainder), plus generation GPU-seconds per reply token beside the generating engine. Amendment of 2026-11-17 (Q47, owner decision): because not every system separates generation from proving, the two parts print only under Cost on system pages beneath the two rates (CO-8), with units, shared block scope and `n`, and title labels (without ranges, matching the multiple), and no longer appear on the ladder, Scale page, band, share cards, alt text, descriptions, or search entries. Computation and storage remain unchanged. Amendment of 2026-11-26 (Q55): for every release after v1.0, the two parts that print are CO-9's parts of a further reply, and the proving one prints on the surface as its multiple beside the total (reversing Q47 for those releases); CO-7's session parts stay computed and stored.
- CO-8 (adopted 2026-11-16, Q37; amended 2026-11-23, Q54). **Reply tokens per GPU-second.** Defined as `output_tokens` divided by the row's mean session GPU-seconds per reply (CO-1, whole sessions), with range given by `output_tokens` over the highest and lowest session values across `n` counted sessions. Labels: unit `token/gpu_s` (printed "reply tokens/GPU-s"), scope `whole_wall`, grade `derived`, tier `reported`, derivation `D-L1-REPLY-TOKENS`, naming the bound GPUs. Because it is hardware-dependent, it originally appeared once under Cost beside Session GPU time with the note "Prompt side (prefill) and reply side (decode) are not timed apart in these records." (plus the two session parts where separated, Q38). Amendment of 2026-11-16 (Q39): added the serving baseline's rate (`output_tokens` divided by baseline GPU-seconds per reply at full load, derivation `D-L1-SERVED-TOKENS`, unit `token/gpu_s`, baseline scope, single run across timed batches, no range) stored in `baseline` alongside `gpu_model`. By construction, served rate divided by proved rate equals the whole-sessions multiple (CO-5), verified by test against the stored board. Both rates appear beneath the multiple on the ladder and band ("2.027 proved · 2,669 served", followed once by "tokens/s per H200" naming the GPU; later simplified by Q41 so the served rate prints once in the model header and the proved rate prints under each row's multiple), formatted to four significant digits (and all integer digits) so dividing printed rates reproduces the printed multiple. Rows lacking either rate or not using the whole-sessions multiple omit this line. These rates never affect ranking or states; Cost vs serving remains the sole headline. Amendment of 2026-11-23 (Q54): on the ladder the served rate prints on the model's divider, named Serving, in the Cost vs serving column, and each row's proved rate prints its number and unit on one line under the multiple, in that column; the word "proved" is heard there, not printed (the system page's band keeps it). Amendment of 2026-11-26 (Q55): for every release after v1.0 the proved rate is `output_tokens` over the cost of a further reply (CO-9, pooled), with range `output_tokens` over the largest and the smallest session value, scope `prove.session`, derivation `D-L1-FURTHER-TOKENS`, so served over proved is the total multiple the row prints. The served rate is unchanged.
- CO-6. Every derived figure is computed in `iproofs.derive` from stored records (AGENTS.md rule 3) and checked by gate G4. Fixture `harness/tests/fixtures/derive/release-groups/` holds release timestamps from v0.1 run `2026-11-09-flashprove-fp-maverick-w1024-b24-prover-h200-hosted-1`: five groups of 24 with later per-reply times of 7.116, 7.136, 7.141, and 7.119 s, yielding `m = 7.128` GPU-seconds per request (the other three H200 runs yield 7.060, 7.082, and 7.195 vs v0.1's published 5.746).
- CO-9 (adopted 2026-11-26, Q55; every release after v1.0). **The cost of a further reply, with the one-time work apart.** The whole-sessions figure (CO-1) divides work done once by a session size the level chose (5 or 120 replies), so it moves with `N` for no reason a provider would recognise. CO-9 takes that work out of the per-reply figure and prints it on its own.
  - **One-time work `F`.** Work that depends only on the system's pin, the model and the request shape, never on a request, and whose result every later reply reuses. For a session it is the GPU-seconds from the start of `commit` to the start of `prove`: the commit call, and the harness taking its files (AGENTS.md rule 6). For a session that names a setup (`run.json#/setup`, a `setup/1` record, `iproofs.setups`) it adds the setup run's own GPU-seconds (`setup.json#/gpu_seconds`) and the restore of its state (`restore_seconds` × bound GPUs); the board reads the record beside the sessions (`results/<release>/<system>/_setups/<setup id>/setup.json`) and stops when its digest is not the one the session recorded. The `info` and `setup` calls stay outside, as in CO-1. `F` prints as a duration in GPU-seconds (or GPU-hours where a page counts in hours), the mean over the counted sessions with its range and `n`, never divided by `N`. Its mark is computed: the fewest replies at which `F` is at most 5 % of the total, `ceil(19 × F / c)`.
  - **The cost of a further reply `c`.** GPU-seconds held (bound GPUs × wall time, never weighted by utilisation) from the start of `prove` to the release of the session's last reply, over its `N` replies: everything a reply needs once the one-time work exists, generation included wherever it happens. A row sums its counted sessions' GPU-seconds and divides by their summed replies (costs are summarised, never ratios), and prints each session's own value as the range, with `n`. For one session, `F + N × c` is its time from the start of `commit` to its last reply (plus, with a setup, the setup and the restore), so no GPU-second is left out.
  - **Two parts.** Generation (the reply's tokens) and proving (everything the reply costs once its tokens exist: `c` less generation). Generation comes from the AD-4 marks where the adapter generates in a phase of its own (FlashProve). A system that generates inside `prove` (SASH) has no AD-4 phase: its generation is the prove phase its adapter reports as the reply's generation (`run.json#/adapter_phases/prove/<phase>`, RFC-0004; SASH's `ids`, the greedy continuation its integer model decodes, `systems/sash/README.md` §prove), taken only when the prove phases the adapter reports for that session sum to the harness-timed `prove` call within 1 % of the call; otherwise the row has no split, prints its total alone and records why. This narrows RFC-0004 INV-GRADE-2 for this one figure, an adapter-reported timing apportioning a harness-timed total: the part and the proving part computed from it keep their source in their labels (derivations `D-L1-FURTHER-GENERATION-ADAPTER` and `D-L1-FURTHER-PROVING-ADAPTER`, inputs pointing at the adapter's phases, a note naming source `adapter` and tier `reported`). The total never rests on the adapter.
  - **Two multiples.** Proving (`proving part / b`) and total (`c / b`), with `b` the baseline's GPU-seconds per reply (CO-4, unchanged), each with its range over the same baseline. A row also states its proving batch (the workload's `shape.batch_size`: 24 replies a proof batch for FlashProve, 1 for SASH), since the proving part depends on it.
  - **What the pair means.** A provider who lets the system write the reply pays about the total; a provider who serves with another engine and proves afterwards pays about the proving part. This release measures only the first route: no run serves with another engine and proves afterwards.
  - **Where each prints** (reversing, for these releases, Q29's whole-sessions display and Q47's parts under Cost alone). The ladder, the Overview page, the band and share cards print the two multiples of every row, large, each with its unit, the proved rate (CO-8) under the total; the ladder states the proving batch. The system page's Cost block prints the two parts in GPU-seconds per reply with scope, range and `n`, the one-time work with its mark, USD at the release's price, and, as diagnostics, the prove step's GPU utilisation and peak GPU memory (`run.json` metrics `prove_gpu_util_mean`, `prove_gpu_memory_peak`, D-STAT over the counted sessions); utilisation is never a ladder figure. Where a row has no split, the proving multiple prints as not measured, with its cause one step down. The sentence on the two routes stands at depth 3 under Cost, and in the rule on the Checks page. The whole-sessions figures (CO-1, CO-5, CO-7) stay computed and stored, under Cost.
  - **Labels.** `c` and its parts: unit `gpu_s/request` (printed "GPU-s/reply"), scope `prove.session`, grade `derived`, tier `reported`, derivations `D-L1-FURTHER`, `D-L1-FURTHER-GENERATION` (or `-ADAPTER`) and `D-L1-FURTHER-PROVING` (or `-ADAPTER`); the multiples `D-L1-MULTIPLE` at scope `prove.session`; `F`: unit `gpu_s`, scope `commit`, `D-L1-ONE-TIME`; its mark: unit `count`, `D-L1-ONE-TIME-MARK`; USD `D-L1-USD`. The board names the split's source (`further_reply_split`: `generation_marks`, `adapter_phases` or none) with each session's check.
  - **Which rule a release uses.** A release's id fixes it: v1.0 keeps the whole-sessions rule it was published under, so its stored board and every figure it printed stay as they are; every later release is built by CO-9, and its board records `cost_rule: "further-reply"`. `iproofs release board <release> --cost-rule <rule>` builds by the other rule, for a preview in a copy of the tree. The level file is not changed (LV-1).
  - **Unchanged.** CO-4's baseline, CO-2 and CO-3 (the steady `m`), the six checks, the order rule except its fallback (OR-3), and nothing ranked or divided across rungs.

- CO-10 (proposed 2026-11-27, Q56; awaiting the owner's decision; every release after v1.0). **Prompt side and reply side.** A server reads a prompt in one parallel pass and writes a reply one token at a time, so the two cost it differently; a prover computes every position alike. CO-10 gives every row two more multiples beside CO-9's, its overhead on the prompt side (prefill) and on the reply side (decode). They are diagnostics: they rank nothing, set no check, count toward no session or attempt cap (SE-3), and change no figure CO-9 or CO-5 prints. `levels/L1.yaml` and its digest are unchanged (LV-1), and so is v1.0's board.
  - **Request A.** Each rung with a system run on it has one request A: the level's request with a 1-token reply (`shape.output_tokens: 1`, `context_window` 513, `phase: prefill`), the same prompts, decoding and tokenizer. The level file names no such workload; the rung's serving record lists it beside the rung's own (`workloads/serving/<id>.yaml` `workloads`), and `iproofs.level.prompt_side_workload` finds it there by its shape and phase (`l1-l31-8b-p512-o1`, `l1-maverick-p512-o1`). It runs under `--level L1` (its manifest records the frozen digest) as a serving ladder only, on the rung's ladder prompts (PR-3: nothing new is drawn); the runner refuses a session, a setup or a control run on it. Its engine flags follow SRV-3 as written, `--max-model-len 513` (proposed; the alternative is 1,024, the rung's request's, so both share one engine configuration). A has no free constant: its prompts, decoding and engine are the request's and its reply length is 1, so choosing it after the freeze reopens nothing (Goals).
  - **Serving on each side.** `s_A` is request A's GPU-seconds per reply at its full load, by CO-4's rule unchanged (the first run by start time of the rung's serving record under the level's digest with a full load; "not saturated" holds as for the request). `s_B` is the rung's baseline (CO-4); a run of request A never enters it. The prompt side is `s_A`: 512 prompt positions read and the first reply token written. The reply side is `s_B − s_A`, the 511 further reply tokens (proposed: a difference of two full-load figures at different concurrencies, each the engine's own operating point, not a measured decode phase; at full load the engine interleaves the prefill of some requests with the decode of others). When `s_B ≤ s_A` the reply side is null with that cause. Each is one run: no range. Derivations `D-L1-BASELINE` on A, `D-L1-BASELINE-REPLY`, and `D-L1-PROMPT-SHARE` (`w = s_A / s_B`).
  - **A further reply on each side.** CO-9's cost of a further reply `c` splits into a prompt side and a reply side, each with a generation part and a proving part; the four sum to CO-9's two parts. (1) Where the adapter reports a phase's work per side, that is the measured core: an adapter phase named `<phase>__prompt` or `<phase>__reply` is that phase's part on one side (adapter-out/1 names; a name with `__` is a part of the phase before it, and CO-9's 1 % sum against the prove call counts whole phases only). The parts are taken only when the session meets CO-9's condition (its whole prove phases sum to the harness-timed prove call within 1 %) and no phase's parts exceed the phase. The generation's core is the parts of the system's generation phase (SASH `ids`, FlashProve `generate`); the proving's core is the parts of every other phase (SASH `prove`: the prove time of token block 0, the prompt's 512 positions with the head that writes the first reply token, and of block 1, the reply's 512 positions). (2) Work the system does once for both sides (the rest of each part: SASH's witness extraction, kernel emission and the rest of its prove phase; FlashProve's whole 1,024-position window) is apportioned by the positions proved on each side, the request's prompt and reply tokens (512 and 512) (proposed), and every such figure says "apportioned by position" in its note. (3) A generation with no per-side core stays unsplit: the generation on each side and the side totals are null with that cause, never a guess; the proving sides still print. A row whose further reply has no CO-9 split has no sides. Pooled as CO-9 pools (summed GPU-seconds over summed replies, each session's own value as the range, `n`). Unit `gpu_s/request`, scope `prove.session`, grade `derived`, tier `reported`, derivations `D-L1-PROMPT-GENERATION`, `D-L1-REPLY-GENERATION`, `D-L1-PROMPT-PROVING`, `D-L1-REPLY-PROVING`, `D-L1-PROMPT`, `D-L1-REPLY`; their inputs point at the adapter's phases and a note names source `adapter`, tier `reported` (INV-GRADE-2 narrowed as CO-9 narrows it).
  - **Multiples.** Prompt-side proving multiple: prompt-side proving cost over `s_A`; reply-side proving multiple: reply-side proving cost over `s_B − s_A` (derivations `D-L1-PROMPT-MULTIPLE`, `D-L1-REPLY-MULTIPLE`); the same two for the totals, generation included. With `w = s_A / s_B`, CO-9's multiple over `s_B` is `w ×` the prompt-side multiple `+ (1 − w) ×` the reply-side one (tested on a hand-computed case), so the pair says how the one figure divides between the two sides.
  - **Where it is stored.** The board carries the figures only under the further-reply rule and only where a run of request A is stored: the rung's `baseline.sides` and each row's `sides` (`board/1`, optional). Where they print, if anywhere, is the owner's decision; proposed: one step down from the Cost block of a system page (SI-8), never on the ladder or the Overview page.
  - CO-8's sentence "Prompt side (prefill) and reply side (decode) are not timed apart in these records" stays true of the whole-session records; CO-10 times the serving sides apart by request A and the prover sides by the adapter's parts where it reports them.

### The six checks

Each check terminates as `held`, `failed`, or `undecided`, rendered on the site as "passed", "failed", and "not decided" (amended 2026-11-16, Q37). Undecided checks carry one of four causes:
- `system limit`: "the system cannot do what this test needs (its publisher's words are quoted), so the row cannot pass"
- `not run`: "not run yet"
- `not resolved`: "the test ran, and its result does not count yet" (amended 2026-11-16, Q38; previously "the test ran and decided nothing")
- `not reproduced`: "a verifier accepted a changed input in our adapter; not yet repeated with the system's own command" (amended 2026-11-16, Q37)

Undecided checks are never framed as failures. Each displays its explanation note and, whenever a rule specifies the next action, prints what resolves it and who acts: for example, Verify without weights missing only a GPU-free re-run prints "To decide: the proofs of session <date · ordinal> verified again, in the run's image, on a host with no GPU. By us." (CH-4a), and `not reproduced` explains that we must repeat the mutated input using upstream's own CLI (Q38). Publishing `failed` from an adapter-executed control requires a reproduction record (CH-8).

| Check | Id | Passes when | Failed when | Evidence |
|---|---|---|---|---|
| RUN | `run` | three slots each have a complete session (SE-1), built from the public pin with no source change of ours (SASH's pin is a pull request written by this project's owner, SI-3; amended 2026-11-15), with no weakening flag | a slot reaches five incomplete runs or has a recorded refusal (SE-5), or a counted session used a weakening flag | `run.json` of every session |
| MODEL | `model` | P1 (RFC-0008: commit W, prove with W′, one weight changed) produced no accepted proof in 3 of 3 trials, and C3 (honest proof verified against commitment of W′) was refused in 3 of 3 trials | any trial of either accepted | `controls.json` |
| PROMPT | `prompt` | C2 (one prompt token changed at a seeded position) refused in 3 of 3 trials | any trial accepted | `controls.json` |
| REPLY | `reply` | every accepted proof covers all 512 reply tokens (RFC-0017 INV-REQ-2), and C1 was refused at the first, last, and one seeded interior reply position in 3 of 3 trials each | coverage falls short, or any trial accepted | `run.json`, `controls.json` |
| VERIFY WITHOUT WEIGHTS | `no_weight_file` | every counted verdict came from a verify call (a) with no GPU visible, (b) on a filesystem holding no model file of the workload (removed or never fetched), and (c) under a file-open trace naming no model file | the trace names a model file, or a verify call required one | `verify-trace/` of every session |
| FIDELITY | `fidelity` | the row's replies score above the rung's bar (§Fidelity) | the bar scores above the row | `fidelity.json` of the rung |

- CH-1. Checks execute against the honest proofs from counted sessions. MODEL, PROMPT, and REPLY reuse RFC-0008's controls, seeds, honest twins, and `void` rules, updating only trial counts and target positions. If a trial's honest twin fails acceptance, that trial is `void` and retries with the next seed (up to 10 seeds per series, with each C1 position forming its own series) until 3 valid trials complete.
- CH-1a. A failed P1 control prove counts as a prover refusal only when its log matches an entry in `system.yaml`'s `p1_refusals` (documented upstream stops signalling weight-commitment mismatch, e.g., FlashProve's `hc-own-node`), or when (a) the prover exits 0 while answering the request "failed" with no proof as documented at the pin and declared in `p1_refusals.failed_answer` (FlashProve `prover/docs/ends-in-short.md`, "What an exit gives away": "a failed check on a hidden value neither ends the process nor changes its status; the request, or its batch, is answered 'failed'"), (b) the same run's honest twin proof was accepted, and (c) no Python exception escaped the adapter and no layout guard fired (owner decision, 2026-11-13). Any other failure counts as inconclusive `error`, including bare harness exit strings ("<kind>: prove exited <code>"), adapter Python tracebacks (RFC-0008 §Outcomes), and file-layout guards such as FlashProve's `cp-weights-files`. Trial logs preserve the trailing lines of the newest control log after `| log:`. Each control prove receives real copied state from `setup` and `commit` (`io/state` and sibling output directories), created before the trial and removed afterward so only one copy resides on disk at a time. Discovery (2026-11-13): FlashProve session 1's P1 trials hit `FileExistsError` in the adapter, followed by two control runs hitting missing `/io/fit` (`FileNotFoundError`) and hard-linked weights (`cp-weights-files`); the third run (`runs/20261113T170513Z-l1-fp-p1-control-3`) verified its honest twin cleanly and answered "failed" with no proof on all three `W′` trials.
- CH-1b. P1 trials may come from a dedicated control run (`iproofs run --level L1 --session K --control-run --control-suite`) using slot `K`'s first prompt at batch 1 (`control: true` in `run.json`, excluded from sessions under SE-3). MODEL accepts P1 trials from a complete control run matching the counted sessions' level digest, workload, image, and adapter commit, while C1, C2, and C3 must always come from counted sessions. This accommodates provers whose commitments draw fresh per-commit secrets (like FlashProve), allowing P1 to re-run cleanly at the same pin when an in-session P1 hit an adapter error and session state is no longer on disk (found 2026-11-13).
- CH-1c (amended 2026-11-15). Three trials do not necessarily mean three distinct modified inputs: C1 at the first and last positions modifies the same token across trials, and C3/P1 reuse the same perturbed weights or commitment, verifying repeatability, whereas C2 and C1's interior position sample a new position each trial. For every control and position across MODEL, PROMPT, and REPLY, the board records counted trials, refusals, and distinct modified inputs (`trials` from `controls.json`) for display on the system page without altering any state.
- CH-2. Each system's MODEL weight perturbation is fixed in the level file prior to the first counted run: one stored weight in a dense tensor read on every request, shifted by one unit in the representation the system commits. Systems that quantize at load (SASH) MUST ensure the change survives quantization and moves the stored integer code. Adapters generate `W′` via their `perturb` subcommand (AD-5) so harness code stays format-agnostic. Systems with randomized commitments (FlashProve) verify the perturbation using upstream's weight-digest tool on `W` and `W′` rather than comparing commitment IDs. If no verifiable perturbation exists, MODEL stays `undecided` (`not run`). Because P1 and C3 are negative-control jobs, adapters MAY accept `W′` in place of published model files strictly within those jobs (AGENTS.md rule 4).
- CH-3. REPLY's interior index for trial `k` is `seeded_index(control_seed, "C1-interior", k, 510) + 1`, guaranteeing it never collides with the first or last position.
- CH-4. VERIFY WITHOUT WEIGHTS wraps the adapter's verify process in `strace -f -e trace=open,openat,openat2 -o <file>` (or the hosted equivalent), reducing the trace to opened paths and byte sizes in `verify-trace/<proof_id>.json`. Any path (or resolved realpath) matching `model.files` or located inside the model directory counts as a model file. If the tracing utility is missing from the container image, the check is `undecided` (`not run`).
- CH-4a. A verdict whose trace showed a visible GPU can still satisfy (a) through (c) via a GPU-free re-verification (`iproofs reverify RUN_DIR` or `hf-job.sh reverify` on `cpu-xl`), re-verifying the archived proof bytes in the exact run image under `strace` without fetching weights, stored once under `reverify/` (`reverify.json`, schema `reverify/1`, plus per-proof traces). It counts once it matches the run ID, image digest, and every proof's manifest SHA-256 with verdict `accept`, while displayed verify times remain the original session's.
- CH-5. When a system's own design makes a test impossible (for instance, a verifier that accepts no prompt input, preventing C2), that check records `undecided` (`system limit`) with the publisher's verbatim quote, and the row cannot pass.
- CH-6. `iproofs.checks` computes all six checks deterministically from stored records (`run.json`, `controls.json`, `verify-trace/`, and `fidelity.json`) with no manual reviewer overrides.
- CH-7. The six checks act strictly as the entry gate for ranking (§Order). They appear as a compact standing on ladder rows and in a full table on system pages, separate from the five-petal glyph (§The glyph).
- CH-8. An accepted tampering trial publishes as `failed` on MODEL, PROMPT, or REPLY only once accompanied by a reproduction record (`results/<release>/<system>/reproductions/<check>.json`) showing upstream's own command outside our adapter accepting the same altered input. Until reproduced, the check displays `undecided` (`not reproduced`) and follows disclosure procedures (RFC-0008 §Disclosure).

### Fidelity

In plain terms (amended 2026-11-16, Q37): proving systems usually run quantized copies of a model whose weights use fewer bits. Fidelity asks whether that quantized copy still answers like the publisher's original model at release precision. We send the same prompts to the original model, to the proving system, and to unproved `llama.cpp` reference copies: a second run of the original, an 8-bit copy (`Q8_0`), a 4-bit copy (`Q4_K_M`), and damaged copies. The 8-bit and 4-bit copies act as yardsticks. Three distinct concepts share the name and are disambiguated wherever they meet: the **Fidelity check** (FIDELITY, FI-6), which passes when proved replies outperform the rung's damaged bar on matched leading tokens at `p < 0.05`; the **Fidelity petal** (FM-1 to FM-7), which places that same score against the yardsticks; and the **Fidelity figure** (FI-10, SI-9), top-token agreement, which is purely informational. On the site, controls display as "8-bit copy", "4-bit copy" (with IDs in parentheses on system pages), and "the original, run again". Rules FI-1 through FI-15 remain unchanged.

- FI-1. Reference: the publisher's original weights (from the serving record, or the 16-bit release when the serving record is FP8), converted to GGUF via `llama.cpp`'s `convert_hf_to_gguf.py` at the level's pinned commit using `reference.dtype` (`bf16` for 16-bit models; `f32` for GPT-2), and executed greedily in `llama.cpp` across all `3·N` rung prompts for 512 tokens with EOS ignored. Replies are stored in `results/<release>/fidelity/<rung>/reference.jsonl`.
- FI-2. Controls specified by recipe in the level file run identically on the same prompts:
  - honest controls: a second run of the reference (`rerun`), `Q8_0`, and `Q4_K_M` (produced via `llama-quantize` from the reference GGUF);
  - damaged controls: `Q3_K_S`, `Q2_K`, the reference with a quarter of its layers dropped (`systems/ref-fidelity/drop_blocks.py`: every fourth block for dense models, 8 of 32 for Llama 3.1 8B; every fourth pair of blocks for Llama 4 Maverick, 12 of 48, preserving expert-index parity in `llama.cpp`), and a smaller model from the same publisher and tokenizer (Llama 3.2 1B Instruct on the 8B rung; Llama 4 Scout 17B-16E Instruct on Maverick).
  A proving system's committed file is never used as a control.
- FI-3. Score: for each reply, the count of leading tokens matching the reference reply (0 to 512).
- FI-4. Statistical test: a paired one-sided sign-flip test over per-prompt score differences using the mean difference as test statistic. For `n ≤ 20`, all `2^n` sign vectors are enumerated exactly; for `n > 20`, `fidelity.resamples` (200,000) sign vectors are drawn from `random.Random(seed)` where `seed` is the first 8 big-endian bytes of `sha256(randomness_bytes ‖ 0x00 ‖ id_A ‖ 0x00 ‖ id_B)`. The p-value counts sign vectors achieving at least the observed mean difference (ties included), using `(1 + hits) / (1 + resamples)` for Monte Carlo so `p` is never 0. "A scores above B" holds when `p < fidelity.alpha` (0.05).
- FI-5. Bar: among damaged controls beaten by every honest control, the one with the highest mean score. If no damaged control qualifies, the rung has no bar and FIDELITY is `undecided` (`not resolved`) for all rows on that rung.
- FI-6. A row's replies are the claimed outputs from accepted proofs across its three counted sessions (`n = 3·N`). FIDELITY is `held` if the row scores above the bar, `failed` if the bar scores above the row, and `undecided` (`not resolved`) otherwise.
- FI-7. Non-gating KL divergence: `llama-perplexity --kl-divergence-base` runs on the reference over the rung's KL windows, followed by `--kl-divergence` on each control and (when loadable by `llama.cpp`) the system's committed GGUF file. `llama.cpp` detokenizes and re-tokenizes the windows and scores the second half of each 512-token chunk, yielding mean KL divergence per scored token in nats (`nat/token`), labelled "computed by llama.cpp on the committed file, not the proved computation". Systems whose committed weights cannot load in `llama.cpp` print "not measured" with that reason unless their adapter implements the optional `logprobs` subcommand (AD-2) to emit next-token distributions over the same chunks for direct comparison.
- FI-8. `iproofs fidelity run` executes FI-1, FI-2, and FI-7 inside the `ref-fidelity` container on a GPU profile; `iproofs fidelity score` computes FI-3 through FI-6 on CPU from archived replies and writes `results/<release>/fidelity/<rung>/fidelity.json`.
- FI-9. **Fallback when pinned `llama.cpp` cannot run a 16-bit reference** (triggered by Llama 4 Maverick on 2026-11-12, where `llama.cpp` v0.9.0 crashed in `MUL_MAT_ID` with an illegal memory access on 8 H200 GPUs across all tested flags while its 8-bit file ran cleanly). In this case, the reference, `rerun`, and `other_model` controls run in vLLM at the serving baseline's pin (v0.32.0, `systems/ref-fidelity-vllm`) using identical greedy `ignore_eos` decoding across 512 tokens with prefix caching disabled and tensor parallelism across the job's GPUs, reversing prompt order in `rerun` so batching differs from the reference. Quantized controls still run in pinned `llama.cpp` (`fidelity run --part controls`, recorded in `fidelity-run-controls.json`), quantized via `llama-quantize` from a pinned BF16 GGUF conversion of the publisher's 16-bit release (for Maverick, Unsloth's BF16 GGUF at the workload's pinned revision, saving 2 h 10 min of CPU conversion on 803 GB). `drop_blocks` is omitted (since it operates on the 16-bit `llama.cpp` file), listed with that cause, and cannot set the bar (FI-5). FI-7 KL is skipped because `llama.cpp` lacks a 16-bit base. `fidelity score` merges both records after confirming matching level digests and prompt sets without altering the frozen level file.

#### Teacher-forced agreement and KL (amended 2026-11-13, FI-10 to FI-15)

This secondary fidelity measure appears beside FI-3 without gating any check, bar, or petal step (which continue using FI-3). Because FI-3 halts at the first differing token, a single early tie zeroes out all 500 subsequent tokens and makes small-`n` scores heavy-tailed; teacher-forced evaluation samples every reply position directly.

- FI-10. **Measure.** For each of the rung's `3·N` prompts, each engine receives the prompt followed by the stored 512-token reference reply (`reference.jsonl` from FI-1 or FI-9) as token IDs and predicts its top token (logit argmax, breaking ties by lowest token ID) at each of the 512 reply positions. **Alignment:** row `t` (`0 ≤ t ≤ 511`) conditions on the prompt plus the first `t` reference tokens to predict reference token `t`, with position 0 predicted right after the prompt's final token. **Score:** per prompt, the integer count of positions (0 to 512, unit `agreeing positions`) matching the reference token. Unlike FI-3, the engine always conditions on the reference prefix. `fidelity.score` in the level file chooses the gating metric: Level 1 fixes `matched_prefix` (FI-3), while a future level file (under LV-1 and Q20) could select `teacher_forced_agreement` once added to `level/1`.
- FI-11. **Non-gating tests.** Applies FI-4's paired sign-flip test in both directions ("row above control" and "control above row") using FI-4's alpha, exact enumeration for `n ≤ 20`, and resamples seeded with `teacher_forced/` prefixes so no random draws overlap FI-3. If a proving system's code declines a prompt (FI-13), that prompt scores 0 in the mean and tests (never dropped) and is listed with its cause alongside the mean over answering prompts. If a benchmark-driven control or the reference fails any prompt, the entire control run fails rather than scoring 0.
- FI-12. **Non-gating teacher-forced KL.** At each reply position, each engine outputs its top 256 tokens and log-probabilities. Position-level KL divergence (in nats) is computed over the partition consisting of tokens present in both top-256 lists (excluding any zero-probability entries, which merge into the tail bucket as of 2026-11-15 so KL stays finite) plus one residual bucket for all remaining tokens: given common-token probabilities `p` and `q` over set `S` with residual masses `m_p = 1 − Σ_S p` and `m_q = 1 − Σ_S q`, `KL = Σ_S p (ln p − ln q) + m_p (ln m_p − ln m_q)`. By the data-processing inequality, pooling never inflates KL and equals full-vocabulary KL when `S` holds all reference mass; mean `m_p` is reported alongside as `reference_rest_mass`. Residual masses below `10⁻⁶` (below float32 precision) are dropped on the reference side and clamped to `10⁻⁶` on the engine side. Prompt KL averages valid positions, and overall KL averages valid prompts (`nat/token`), noting prompt/position counts and any `positions_without_list` (e.g. `llama-server` omitting distributions mid-UTF-8). Raw 1 MB top-k dumps stay outside git (referenced by digest) while per-prompt values live in `kl.json`. Because top-256 lists only bound rather than determine exact `L∞` distance, no `L∞` metric is printed in Level 1 (amended 2026-11-16, Q37).
- FI-13. **Provenance.** Every row figure from FI-10 through FI-12 carries the verbatim disclaimer: "computed by the system's own code on the reference reply, not by the proved computation". Exact-match provers can only prove their own greedy reply, not a reference reply (AD-3). Per-system code used:
  - SASH: its witness extractor (`harness.witness.extract --head`) given the reference reply via `--ids` and the counted sessions' attention calibration, taking `tok_head` as top token and bf16 `key_head` order keys as logits. Unstated at the pin: whether `--ids` supports non-greedy replies (help text says "token ids (.npy) to run instead of the corpus's first --tokens"), whether extractor values match proved values bit-for-bit (source says "A witness and a spec are one object"), and whether segment proofs would accept them (not tested).
  - FlashProve: upstream's integer-model package (`IntegerModel.extend` with `gap_for`, matching `examples/score_reply.py` and AD-3), described by the publisher as "By design, this is the function that the repository's prover proves". Unstated at the pin: bit-exact parity with `cp_prove` at full scale ("What was compared with the prover is proof or no proof, and greedy choices"; "nothing was compared at full size"). Logits for FI-12 come from `extend`'s `record` argument (documented in its docstring and `OPERATING.md`, omitted from the README's "Python API"), scaling integer logits by `2^s` (which parameter docs call "the provider's statement: no equation ties it to the model").
  - Prompt-level rejections by the system's own code (SASH extractor assertions, FlashProve `RangeConditionFailed`) count as failed prompts with that error message; any other error invalidates the run and produces no figure.
- FI-14. **Execution and pinning.** `iproofs fidelity run --teacher-forced` drives either a rung's reference image (evaluating reference and controls: per-position `/completion` calls with slot caching in `llama.cpp`, or single `prompt_logprobs` calls per prompt in vLLM, keeping everything in token IDs with no detokenization) or a system adapter via `--system` (AD-7). `llama.cpp` passes accept only allowlisted documented `server_args` recorded in the run file (including `--swa-full` for Llama 4 Maverick, avoiding full-context re-evaluation on SWA caches, amended 2026-11-14). Proving systems execute inside a **scoring image** (`systems/<name>/Dockerfile.score`) layered directly on their counted sessions' pinned image digest to add only the `score` entrypoint without changing `system.yaml` or counted sessions; runs verify the upstream commit and any commitment-file digests (such as SASH's attention calibration). Before scoring reference replies, each system run executes `own_reply_check` on prompt 0's own proved reply: its top tokens MUST match that proved reply at all 512 positions (AD-3), or the run stops and stores nothing. Artifacts live in `results/<release>/teacher-forced/<rung>/`: `run-<name>.json` (`teacher-forced-run/1`), `top/<id>.jsonl`, and `kl.json`.
- FI-15. **Scoring.** `iproofs fidelity score --part teacher-forced` runs on CPU to compute FI-10 through FI-12 into `teacher-forced.json` (`teacher-forced/1`) without modifying `fidelity.json` (APP-1), including the reference engine's own `reference_pass` consistency check. Passes may span multiple partial runs (`offset` and `prompts`) as long as they partition all prompts with no gaps or overlaps; stopped runs save finished items, while runs saving nothing log exit codes and trailing output in `not-stored.json`. Merged scorings are append-only (RFC-0009 APP-1): later additions write `teacher-forced-K.json` and `kl-K.json` (`K ≥ 2`, `--scoring K --reason`, recording `replaces`), and the board reads the highest `K` (amended 2026-11-14).
- FI-16. **Tie to the proofs** (adopted 2026-11-14, owner request). Although FI-10 evaluates unproved code (FI-13), stored records verify agreement with proved replies on every prefix position covered by a proof. For a prompt with FI-3 matched prefix length `L`, at positions `0..L−1` and (when `L < 512`) at the divergence position `L`, the proved model saw the exact same prefix as FI-10 row `t`, so the `score` pass's top token MUST equal the proved token (AD-3). On CPU, the board counts total covered `positions`, `agreeing` positions, divergence `split_positions`, and `split_agreeing` counts across prompts with top tokens (omitted if proved replies are incomplete). This check is non-gating and says nothing about positions beyond `L`, so FI-13's disclaimer remains in force.

### The glyph

The glyph communicates how close a row is to an ideal prover across five petals: the publisher's stated soundness bound (whether proved and covering the run), what is stated and proved about hiding weights, empirical closeness of proved replies to the publisher's original model, how far a machine-checked soundness proof reaches toward the verifier program executed, and what trust assumptions sit outside cryptography. All five petals at Met means all five hold (amended 2026-11-16, Q37). Passing the six checks is the entry bar; the glyph tracks the remaining distance to ideal (owner decision 2026-11-10; petals updated 2026-11-13, Q6).

| Petal | Id | Protects | Basis | Lowered by | Question |
|---|---|---|---|---|---|
| Integrity | `unforgeable` | the customer | statement | Model, Prompt, Reply | The bound the system's publisher states on a false reply being accepted: whether it is proved, and whether it covers what the row runs. |
| Confidentiality | `weights_hidden` | the provider | statement | Verify without weights | What the publisher states and proves about a proof showing nothing of the weights' values. |
| Fidelity | `faithful_model` | the customer | test (our fidelity run) | Fidelity | How close the proved replies stay to the model publisher's own release, against the rung's controls, in FI-3's matched leading tokens. |
| Formally verified | `machine_checked` | the customer | statement | Model, Prompt, Reply (only where it is green); a recorded proof build | How far a machine-checked proof of soundness reaches toward the verifier program the row runs. |
| Trust assumptions | `no_trusted_party` | the customer | statement | nothing | What soundness rests on besides cryptographic assumptions. |

Display names above took effect on 2026-11-16 (Q37), replacing Unforgeable, Weights hidden, Close to the original, Machine-checked, and No third party trusted while preserving IDs, drawing order, basis, lowering rules, and questions. "Protects" identifies who relies on the guarantee: soundness protects the customer, while zero knowledge protects the provider. Any petal forced red by a failed check or failed proof build takes basis `test`.

The third petal was named Faithful model until 2026-11-15, briefly renamed Close to the original (Q24), and unified as **Fidelity** on 2026-11-16 (Q37, withdrawing Q24) so the petal, check, and figure share one name (qualified as Fidelity petal, Fidelity check, and Fidelity figure where needed) while keeping ID `faithful_model`. The petal grades FI-3's matched leading tokens rather than FI-10's top-token agreement, and system pages state this explicitly.

On system pages (depths 2 and 3), each petal pairs with its field term (amended 2026-11-15, Q26; 2026-11-16, Q37): Integrity ("soundness"), Confidentiality ("zero knowledge of the weights"), Fidelity ("quantization error, in matched leading tokens"), Formally verified ("machine-checked soundness proof"), and Trust assumptions ("trusted setup or party"). Each petal also carries a plain summary sentence shown in hover titles at depths 1 and 2 and on the Checks page (Q40). Under Q44 and Q45 (2026-11-17), system pages show each petal's plain question beneath its name, place the field term in the hover title and under "In the field's terms", and show what the grade comes from (`sources` from GL-5) at the top of the expanded evidence block.

Each petal maps its stored `step` and `state` ink to a plain display word:

| Step (`step`) | Ink (`state`) | Printed (amended 2026-11-16, Q37) |
|---|---|---|
| `green` | `green` | Met |
| `amber_upper` | `amber` | Mostly met |
| `amber_lower` | `amber` | Partly met |
| `red` | `red` | Not met (cause `stated`), Failed (cause `check_failed`), Not stated (cause `not_stated`; amended 2026-11-15: silence is not a "no") |
| null | `hollow` | Not decided |

Printed labels never mention colours (previously "green · in full", "amber · in part", "amber · in lesser part", "red · no", "red · not stated", and "undecided" prior to 2026-11-16); labels are capitalized on chips and line starts and lower-cased in prose.

Red petals carry a `cause`: `not_stated` (consulted documents are silent), `stated` (publisher states the property does not hold or facts fall below amber), or `check_failed` (lowered by a failed check or proof build, GL-2). Hollow petals carry `not_read`, `not_decided`, or `proof_build_not_run` (GL-3). Green and amber petals have null cause. Visually, Partly met cuts off the arm's end cell, `not_stated` red renders as a hollow red outline with unstruck text (remaining red under GL-1), and all other reds render solid with struck text (Q7).

- GL-1 (amended 2026-11-13). `iproofs.glyph` computes all four statement petals (Integrity, Confidentiality, Formally verified, and Trust assumptions) directly from quoted facts in `systems/<name>/properties.yaml` (`properties/2`), with no hand-typed states, steps, or reasons. Each fact carries its value, pinned verbatim quotes (matching substrings after collapsing whitespace runs while keeping markup and comment markers), and a `note` whenever the value rests on reviewer reading rather than explicit wording. CI validates schemas and offline invariants (pin, links, bound expressions/terms, trusted base), while reviewers verify quote fidelity. Silence evaluates to red ("not stated in the publisher's documents read at the pinned commit") listing linked documents consulted (owner decision, 2026-11-10: an unstated guarantee cannot be relied on). Under Q44 (2026-11-17), system pages phrase silence in each petal's plain terms ("nothing in the 4 documents we read on whether a proof hides the weights") with consulted files linked under Evidence, while the board keeps the GL-1 wording.
- GL-2 (amended 2026-11-13). Tests only lower petals, never raise them. A failed check sets affected petals to red (`check_failed`, basis `test`) regardless of documentation: Model, Prompt, or Reply lowers Integrity (and lowers Formally verified if green); Verify without weights lowers Confidentiality; Fidelity lowers the Fidelity petal. A matching proof build that failed, exited non-zero, or reported undeclared axioms lowers Formally verified to red (MC-4), whereas a stopped build lowers nothing (MC-4a). `lowered_by` records what triggered the downgrade. Undecided checks lower nothing, and passing checks never upgrade a statement ([RFC-0008 §Non-Goals](0008-negative-controls.md)).
- GL-3 (amended 2026-11-13). Undecided petals render hollow with an explicit cause: `not_read` (missing, non-`properties/2`, or commit-mismatched properties file, or missing run commit), `not_decided` (Fidelity petal when FIDELITY is undecided or scores are absent), or `proof_build_not_run` (Formally verified stated above red with no matching build or only a stopped build, MC-4a). Unread files are always hollow, never red.
- GL-4. Only benchmarked rows receive a glyph. Glyphs never alter rankings (OR-1 through OR-6 govern order strictly by cost among passed rows). Because glyph rules sit outside the frozen level file (§Terms), updating them amends this RFC without creating a new level (LV-1).
- GL-5 (amended 2026-11-13, 2026-11-15, 2026-11-16, 2026-11-17). `iproofs.glyph` writes each petal into `board.json` with `id`, `state`, `step`, `cause`, `basis`, `reason`, `quotes`, and `lowered_by` (plus `sources_read` on `not_stated` red, GL-1). Formally verified includes `formal` (stated step, reach, tool, theorem/link, trusted base, input code, scope card, `conclusion`, `ceiling`, `scope_bounds`, `limits`, and optional `build` with record path, toolchain, publisher command without timeout wrapper, start time, duration, exit code, status, and reported `axioms`), and Confidentiality includes `visible`, `forms`, and `visible_at_least` (both null when `not_read`). If any decision-critical fact carries a reviewer `note`, the petal sets `reading: true` (never set on `basis: test` petals). Petals carry no numeric score. Reasons are generated deterministically from stored files: initially compact (~110 chars), expanded under Q26 (2026-11-15) and Q37 (2026-11-16) into semicolon-separated clauses identifying every failing condition on Integrity (UF-9), ZK form and batch scope on Confidentiality (WH-6), midpoint verdicts and row mean on Fidelity (FM), and stated vs executed verifier, build ceiling, and absence of external review on Formally verified (MC-7). Q37 (2026-11-16) added optional `next` (GL-11); Q44 (2026-11-17) added `sources` (`test`, `statement`, `statement_reading`, `build`, `build_reading`, or null), `sources_count`, `read_facts`, `why`, and structured display payloads (`bound` with `q_cross` exponents where `q/2^t` crosses `2^-100` and `2^-80`, `hiding`, `fidelity` with unrounded-derived one-decimal thresholds plus `policy_cap`, `rerun_engine`, and `below_own_width`, and `trust` with matching `clause`), none of which alter computed states.
- GL-6. One fact, one petal (restoring [RFC-0016](0016-glyph-properties-and-states.md) ST-5): each fact influences exactly one petal. Bound magnitude and proved/conjectured status set Integrity; machine-checked proof scope sets Formally verified. Integrity treats stated and proved `bound.program` identically, leaving formal verification of that verifier code to Formally verified, and Confidentiality does not check whether prover code is formally verified.
- GL-7. Every petal is evaluated on its own as if the other four were green; no decision table reads another petal's state.
- GL-8. Nothing to add up (restoring [RFC-0016](0016-glyph-properties-and-states.md) INV-GLYPH-1): no totals, counts, averages, sorts, or filters across petals anywhere on the site or in `board.json`; `step` is always a string, never an integer.
- GL-10 (adopted 2026-11-15, Q25; updating AGENTS.md rule 9 in parallel). Any statement state resting on our reading of publisher text rather than an explicit sentence is marked "read as" with its supporting quotes and capped at `amber_upper` (Mostly met): if a decision table yields green with `reading: true`, it lowers to `amber_upper` and notes the reading in its reason (lower steps remain unchanged). This test applies identically across all systems: readings may only cite quoted theorems or prose, never construction labels like "STARK", "SNARK", or "hash-based".
- GL-9. `iproofs release freeze` rejects any release containing a listed run with an unread statement petal (GL-3), verifying directly against properties files and run commits rather than trusting `board.json`. `iproofs validate` likewise rejects frozen release boards containing any `not_read` petal.
- GL-11 (adopted 2026-11-16, Q37; updated Q40, Q44, Q45, Q53). **Next step and Missing items.** Along the exact decision path that sets a petal's step, `iproofs.glyph` computes `next: {to, needs}` (each need carrying `{text, by}` with `by` in `publisher` or `us`; `to` null for hollow or Failed petals; null at Met) and `to_met` (Q44: every item missing for Met grouped by target step in rule order, using structured `need` keys and shared UF-9 clause lists so reasons, next steps, and missing items stay synchronized; readings add a publisher-wording item, unbuilt theorems add our rebuild, hollow uses `decide`, Failed uses `repair`, and Met is empty). Each `read_facts` entry tracks `used` (whether the deciding rule read that fact, counted by `sources_count`), FM-5's `one_at_a_time` item identifies `llama.cpp` vs vLLM (which counts as no slot under Q30), and Formally verified's `formal` carries `said` mapping each fact to its own quotes. On system pages (Q45, amended 2026-11-22 by Q53), a closed row displays the first missing item in plain prose ("Nothing missing." at Met), the count, and one open square per item in the cell of the grade its group reaches (a decision or a repair in a cell of its own); opened, each item is listed in a few words under that grade with who acts.

#### Reading the tables

Each decision table evaluates top to bottom and stops at the first matching rule. When in doubt, the lower step wins. "Under" is strict (`80` and `100` are not under 80 or 100). A statement petal is **not read** under the conditions of GL-3, comparing against `system.upstream.commit` from the first counted session's manifest. A **silent** value is `false`, `not_said`, `not_stated`, null, or an empty list. Any `not_stated` red carries `sources_read` linked at the pin (GL-1).

#### Integrity (`unforgeable`)

Facts (`bound`):
- `stated`: whether a soundness bound is stated.
- `expression`: verbatim bound expression, appearing as a substring of one of its quotes.
- `terms`: integer exponents of every error term (e.g., `[124, 101]` for `q/2^124 + 2^-101`). `iproofs validate` extracts every `t` from `2^-t`, `2^(-t)`, or `/2^t` and verifies set equality with `terms` (when no power of 2 appears, such as SASH's "100 conjectured bits", each term must match a standalone whole number in the expression).
- `basis`: `proved`, `conjectured`, or `not_said`.
- `unit`: scope covered by one stated bound (`reply`, `proof`, `part`, `round`, or `not_said`).
- `adversary`: `any_prover` (holds against a prover fully controlling its own hardware with no hardware/third-party condition), `weaker`, or `not_said`.
- `parameters`: `row` (covers the exact parameters run), `other`, or `not_said`.
- `batch`: how batch members are covered (`each_member` for individually checked members, `together` only when checked together such as `N` times single-proof error, or `not_said`).
- `program`: `proved`, `stated`, or `not_stated` for whether the verifier binary executed is proved or stated to implement the bounded protocol/verifier (an explicit disclaimer that the bound does not cover that binary records `not_stated` with that quote).
- `conditions_shown`: true when publisher or harness records verify the theorem's preconditions on the row's files; false otherwise (including when unknown).

Top-level `verifiers` (amended 2026-11-15) names the verifier executed (`run`) and the verifier targeted by the bound/theorem (`stated`, or null), each validated against its quotes. It sets no step directly but appears in Integrity and Formally verified reasons.

A bound covers one reply when `unit` is `reply`, or `unit` is `proof` with `proofs.granularity: request` in `systems/<name>/system.yaml`. It covers the row's batch when `shape.batch_size` is 1 or `batch` is `each_member` (unrecorded batch sizes count as uncovered). Both fields come strictly from `system.yaml` and the workload file, never from reviewer notes or `run.json`. A bound covers the run when `adversary == any_prover`, `parameters == row`, `conditions_shown == true`, reply and batch coverage both hold, and `program` is `proved` or `stated`.

- UF-1. Model, Prompt, or Reply check failed: red, `check_failed`, basis `test`.
- UF-2. Not read: hollow, `not_read`.
- UF-3. `stated` is false or `terms` is empty: red, `not_stated`.
- UF-4. `adversary` is `weaker`: red, `stated`.
- UF-5. Any term is under 80: red, `stated`.
- UF-6. `basis` is `conjectured` or `not_said` and any term is under 100: red, `stated`.
- UF-7. `basis` is `proved`, the bound covers the run, and every term is 128 or more: green.
- UF-8. `basis` is `proved`, the bound covers the run, and every term is 100 or more: amber in part.
- UF-9 (amended 2026-11-15, Q26; 2026-11-16, Q37, Q40). Otherwise: amber in lesser part. Since 2026-11-16, reasons lead with the deciding cause ("not shown to cover this row:" followed by every failing condition in fixed order: `program`, `basis`, `adversary`, `unit`, `batch`, `parameters`, `conditions`, and exponent under 100) before printing "stated bound:" and the verbatim expression (UF-4 through UF-8 follow this same lead-with-cause pattern under Q40). Step evaluation still short-circuits in table order so `reading` reflects only facts required by the deciding rule.

The verbatim expression is always quoted, and the system page prints the level file's `security.words` under "Stated security" with its source (SI-3). Exponents `t` in `2^-t` are compared directly against cut points without deriving any composite bits figure (Q9). Cut points 128 and 100 follow the Ethereum Foundation's zkEVM security milestones (100-bit provable security by end of May 2026, 128-bit by end of 2026, matching `ethproofs`'s soundness bands). Cut point 80 falls below NIST SP 800-57 Part 1 Rev. 5 Table 4 (§5.6.3), which disallows strengths under 112 bits for applying protection, allows 112 only through 2030, and accepts 128 and above (clarified 2026-11-15); both 80 and 100 sit below NIST's floor and may rise in later levels. Protocol-level bounds qualify here once `program` is stated or proved; whether that program is formally verified belongs strictly to Formally verified (GL-6, Q8).

#### Formally verified (`machine_checked`)

Facts (`formal`):
- `reach`: `none` (explicitly not machine-checked); `part` (a component, constraint spec, or sub-protocol is machine-checked, with coverage count); `protocol` (either whole-protocol soundness or model-encoding relation is machine-checked, but not both); `protocol_and_statement` (both whole-protocol soundness and model computation relation are machine-checked against a reference model definition, but not the verifier binary executed); `verifier_run` (machine-checked soundness covers the exact verifier binary executed from input bytes to verdict); or `not_stated`.
- `conclusion` (amended 2026-11-15, MC-7): whether the theorem's conclusion targets a reference definition of the model's computation (`model`, excluding hash-only verifiers), `other`, or `not_stated`.
- `tool`, `theorem` (full tool-printed identifier), and `theorem_url` (at the pin).
- `toolchain`: `{name, version}` copied verbatim from the pinned toolchain file/doc, or null if unnamed.
- `trusted_base`: verbatim publisher list. `axioms`: declared axioms expected from the build, each listed in `trusted_base`.
- `input_code_unverified`: true if named input-parsing code lies outside the proof.
- `scope_card`: 3×3 matrix of soundness, zero knowledge, and completeness across protocol, verifier run, and prover run (`machine_checked`, `paper`, `tested`, or `not_stated`, each quoted, plus optional verbatim `bound` per row, amended 2026-11-15). Because soundness protects against cheating provers (verifier-side) and zero knowledge protects against cheating verifiers (prover-side), `iproofs.glyph` always overrides Soundness × prover run and Zero knowledge × verifier run to `does_not_apply`.

Stated step: `none` or `not_stated` -> red; `part` or `protocol` -> amber in lesser part; `protocol_and_statement` -> amber in part; `verifier_run` with non-empty `trusted_base` and `input_code_unverified: false` -> green; `verifier_run` otherwise -> amber in part.

Printed scale (amended 2026-11-16, Q37, Q38): `verifier_run` displays "the verifier code this row runs" (plus "with gaps (no trusted base listed, input-reading code outside the proof)" when incomplete); `protocol_and_statement` displays "the protocol, model included"; `protocol` displays "an abstraction of the protocol (the protocol without the model, or the model without the protocol)"; `part` displays "part of the protocol"; `none` displays "nothing, as the publisher states"; and `not_stated` displays "not stated". Only the verifier binary actually executed counts as code; formally verifying an unexecuted verifier counts at the protocol level, and prover code appears only on the scope card (GL-6). MC-6 reasons read "built at <pin>: <scale label>", prefixing the scale label with "stated:" or "read as:" (Not decided petals omit basis prefixes).

Proof builds: `results/<release>/proof-build/<system>/proof-build.json` (`proof-build/1`) records one unpatched execution of the publisher's theorem-checking command via `docs/runbooks/proof-build.sh` on Hugging Face Jobs, written mechanically by `iproofs proof-build record` (recording repo, commit, theorem name/link, pinned toolchain name/version and container image SHA-256, command, timestamps, duration, exit code, status `built | failed | stopped` with stop cause, trailing logs, and reported axioms). A build matches a row only when repo, commit, theorem, and non-null toolchain name and version match exactly (mismatched toolchains are called out explicitly in the reason). Setup failures before the build command launches, or full checks that exit 2 or 3 or fail without reaching Lake (e.g. insufficient memory before invoking Lake), produce no record while preserving job logs. Each system stores one record: a full check reaching a verdict (`built` or `failed`) replaces an earlier targeted build (preserving git history), whereas a stopped build, targeted build over a full check, or duplicate full check replaces nothing (Q43, amended 2026-11-15 and 2026-11-16).

- MC-1. Not read: hollow, `not_read`.
- MC-2. Stated step is red: red (`not_stated` for `not_stated`, `stated` for `none`).
- MC-3. Model, Prompt, or Reply check failed while stated step is green: red, `check_failed`, basis `test`.
- MC-4. Matching record has status `failed`, status `built` with non-zero exit code or reported axioms differing from `axioms`, or any status outside `built`/`failed`/`stopped`: red, `check_failed`, basis `test` (lowered by proof build), printing status/exit code or both axiom lists.
- MC-4a. Matching record has status `stopped`: hollow, `proof_build_not_run`, printing stop cause and exit code. A build is `stopped` when terminated externally before reaching a verdict: our timeout wrapper (exit 124, or 137 after timeout KILL, cause `timeout`) or external `SIGKILL`/`SIGTERM` including kernel OOM kills on the build or a Lake child process (exit 137 or 143, or matching killed-child log lines when every failed step of a full check invokes Lake, cause `signal`). Internal proof-assistant failures (Lean panics under `LEAN_ABORT_ON_PANIC=1` exiting 134, stack overflows, aborts, or crashes) are failed builds under MC-4 rather than stops. Infrastructure stops leave the petal hollow rather than implying a broken proof (owner decision, 2026-11-15) and never overwrite an existing stored record (Q43; exit code noted in the commit/changelog per AGENTS.md rule 5).
- MC-5. No matching build record (including null `toolchain`): hollow, `proof_build_not_run`; publisher statements alone never colour this petal (Q10).
- MC-6. Otherwise: stated step, subject to MC-7.
- MC-7 (adopted 2026-11-15, Q27). Exceeding amber in lesser part requires `conclusion == model` and reported axioms limited strictly to the proof assistant's standard axioms (for Lean: `propext`, `Classical.choice`, and `Quot.sound`; never `sorryAx` or `admit`), parsed automatically from tool output. Otherwise the petal caps at amber in lesser part and states why. `formal.ceiling` records the highest step achievable once built (`stated_step` capped by `conclusion`). Reasons name stated vs executed verifiers, print "once built: <ceiling> at most" when unbuilt, and note "statement not reviewed by an outside <tool> reader" whenever a theorem is named (Level 1 records no external statement audits). Note (amended 2026-11-15): MC-7 checks theorem axioms and conclusion target, not non-vacuity on the row's files (as FlashProve's `lean/THEOREM.md` notes, a theorem could hold vacuously if the Lean verifier rejected everything on non-example inputs). FlashProve's non-gating Lean verifier trial on kept proofs (TR-1) prints under Formally verified; requiring such a trial for steps above amber in lesser part stays open to the owner (Q34).

Formally verified grades soundness only; zero knowledge and completeness appear on the scope card. Under Q37, Q38, and Q45, system pages display soundness, zero knowledge, and completeness in order (as one concise glossary-linked line under the petals since Q45, noting our Run check's `N of N` accepted replies for completeness), followed by verbatim stated security and the scope card (columns "Protocol", "Verifier code this row runs", and "Prover code this row runs") as non-gating facts inside a disclosure. Every non-MC-1 outcome populates `formal` in `board.json`.

#### Confidentiality (`weights_hidden`)

Facts (`hiding`):
- `stated`: true, false, or `not_stated`.
- `verifier_gets_weights`: whether the verifier receives weights.
- `proof`: `none`, `protocol` (zero-knowledge theorem for protocol only), or `configuration_run` (theorem covers the executed configuration including batch size).
- `programs`: whether the executed programs are `stated`, `expected`, or `not_stated` to implement the proved hiding.
- `visible_listed`: whether a list of visible values is published (schema requires `visible` to be non-empty when true).
- `visible_at_least` (amended 2026-11-15): true when the publisher marks the visible-values list as a lower bound ("at least").
- `zk_kind`, `zk_model`, `zk_unit`, and `forms` (amended 2026-11-15): post-Fiat-Shamir ZK type (`statistical`, `computational`, `perfect`, or `not_said`), security model (`random_oracle`, `standard`, or `not_said`), statement unit (`request` or `batch`), and verbatim forms (e.g. honest-verifier ZK for the interactive protocol), printed for context without setting steps.
- `visible`: list of visible values, each quoted and tagged `statement_io` (prompt, reply, served/refused), `shape` (architecture and dimensions), `side_channel` (timing, lengths, failures, volume), or `fitted_to_weights` (only when the quote states the value depends on or is fitted to weights; displayed as "depends on the weights", amended 2026-11-15).

- WH-1. Verify without weights check failed: red, `check_failed`, basis `test`.
- WH-2. Not read: hollow, `not_read`.
- WH-3. `verifier_gets_weights` is true or `stated` is false: red, `stated`. `stated` is `not_stated`: red, `not_stated`.
- WH-4. `proof` is `none`: amber in lesser part.
- WH-5. `proof` is `configuration_run`, `programs` is `stated`, `visible_listed` is true, `visible` is non-empty, and no item has tag `fitted_to_weights`: green.
- WH-6. Otherwise: amber in part, naming every missing condition. Since 2026-11-15, `proof == protocol` reasons open with `zk_kind`, `zk_model`, and `zk_unit` ("one request a proof"), note "not for the row's N-reply batches" whenever single-request statements meet multi-reply batches, and list missing program/list conditions plus "K listed values depend on the weights".

Items tagged `statement_io`, `shape`, or `side_channel` are printed for transparency without lowering states. Scale labels (Q37, Q38) describe what was proved: Met ("Zero knowledge proved for what this row runs"), Mostly met ("Zero knowledge proved, with limits" under WH-6, or "Zero knowledge proved for what this row runs, on our reading" under GL-10), Partly met ("Stated, no proof"), Not met ("Not hidden"), and Not stated ("No guarantee stated"). Every Level 1 row also displays "Architecture: visible" with `verifier_inputs.architecture_visible` (or "the model is open-weights") because Level 1 uses open-weights models; architecture hiding is deferred to closed-weights levels (Q13).

#### Fidelity (`faithful_model`)

Computed purely from `fidelity.json` (`basis: test` on every branch) using two rung thresholds derived from honest controls over the same `n` prompts: `T_green = (mean(rerun) + mean(Q8_0)) / 2` and `T_upper = (mean(Q8_0) + mean(Q4_K_M)) / 2`. Either threshold is null (with cause) if a constituent control is missing, failed, or has a different prompt count.

A row is **shown above** threshold `T` when FI-4's paired sign-flip test on per-prompt differences `d_i = 2·s_i − (a_i + b_i)` yields `p < fidelity.alpha`, where `s_i` is the row's score and `a_i`, `b_i` are the two anchor controls' scores on prompt `i`. Because `d_i` is an integer equal to twice the row's distance from the prompt-wise midpoint and `mean(d) = 2·(mean(s) − T)`, the test pairs cleanly by prompt (amended 2026-11-15 from an unpaired `2n·s_i − (S_a + S_b)` formula that gave an honest 8B `Q8_0` copy `p = 0.21` over its own `T_upper` vs `8/2^15` paired, changing no published state). Tests are exact for `n ≤ 20` and seeded per FI-4 above 20 with `A = system_id` and `B = T_green | T_upper`. `iproofs fidelity score` writes `steps`, `step_tests`, and `slots` (the highest slot count across `fidelity-run*.json`, absent with `slots_cause` when vLLM ran any part because vLLM batches all prompts in one call regardless of CLI `--slots`, amended 2026-11-15) into `fidelity.json`. For append-only `fidelity.json` files written before 2026-11-13 lacking `steps` (FM-4a), the board computes these values on the fly from stored scores without editing `results/`. The board always cross-checks stored thresholds, `n`, and exact p-values against raw scores and halts on discrepancies (AGENTS.md rule 3), using `fidelity.json`'s `test.alpha` (matching `levels/L1.yaml` with no default). Reasons open with midpoint verdicts naming both controls and their means (3 significant digits under 100, whole numbers above), followed by the row's mean matched leading tokens (Q37), while `p`, `alpha`, and `n` stay in `fidelity.json` (GL-5).

- FM-1. FIDELITY failed: red, `check_failed`.
- FM-2. Missing `fidelity.json`, FIDELITY undecided, or no row scores: hollow, `not_decided`, with cause.
- FM-3. Claim card policy is not exact match, or claim card missing: amber in lesser part (claim permits tokens other than the model's top token).
- FM-4. Missing `step_tests` or null `T_green`/`T_upper` (missing or failed `rerun`, `Q8_0`, or `Q4_K_M`): amber in lesser part, naming the missing control and cause.
- FM-5. Shown above `T_green` and `slots == 1` (every part of the rung's fidelity run ran single-request in `llama.cpp`): green.
- FM-6. Shown above `T_upper`: amber in part (noting when `slots != 1` or missing `slots` blocked green despite beating `T_green`).
- FM-7. Otherwise (FIDELITY held): amber in lesser part (including rows above `T_green` but not `T_upper`).

Requiring `slots == 1` for green prevents batching variance from distorting the `rerun` control anchoring `T_green`. Every Level 1 rung (including GPT-2 F32) defines `rerun`, `Q8_0`, and `Q4_K_M` honest controls in `levels/L1.yaml`.

#### Trust assumptions (`no_trusted_party`)

Facts (`trust`):
- `rests_on`: `transparent` (soundness rests solely on cryptographic assumptions with no secret-generating setup, either stated explicitly or read from a quoted theorem/sentence with a note under GL-1 and capped at Mostly met under GL-10; construction names never qualify, and fixed public pre-hash files or deterministic public inputs are shared by all non-interactive proofs and do not count against transparency); `open_ceremony` (public-transcript ceremony requiring at least one honest participant); `fixed_parties` (honest party within a fixed set, or challenger in a challenge window); `single_party_setup`; `hardware_key`; `trusted_key`; or `not_stated`.
- `publicly_checkable`: true, false, or `not_said` (anyone can verify a proof file, versus interactive or designated-verifier checks).

- NT-1. Not read: hollow, `not_read`.
- NT-2. `rests_on == not_stated`: red, `not_stated`.
- NT-3. `rests_on` in `single_party_setup`, `hardware_key`, `trusted_key`: red, `stated`.
- NT-4. `rests_on == fixed_parties` or `publicly_checkable == false`: amber in lesser part.
- NT-5. `rests_on == open_ceremony`: amber in part.
- NT-6. Otherwise (`transparent`, and `publicly_checkable` true or `not_said`): green when `rests_on` carries no reviewer note ("stated to rest on cryptographic assumptions alone, with no setup that produced a secret"), or amber in part under GL-10 when `rests_on` carries a note ("cryptography only, as we read the publisher: no setup produced a secret; no quoted sentence says so in words, so Mostly met at most", Q37).

No reason claims a publisher stated something absent from its quotes, no check lowers this petal, and model-to-commitment identity is excluded here (Q12, RFC-0016 ST-6).

### Order

- OR-1. Only passed rows receive rankings, and ranking happens strictly within each rung.
- OR-2. Ranking requires a publisher-stated security level at the pin recorded in the level file (`systems.<id>.security.stated: true` with words and source); otherwise the row is passed but unranked ("publisher states no security level").
- OR-3. Row A ranks above Row B when both have steady multiples, A's mean multiple is at most `(1 − order.margin)` times B's, and A's highest session `m` is strictly below B's lowest session `m`. Any row with a steady multiple outranks one without, and two rows without steady multiples compare by the same rule on session cost per reply. Amendment of 2026-11-26 (Q55): for every release after v1.0, two rows without steady multiples compare by the same rule on the cost of a further reply (CO-9, pooled, its sessions' values as the spread) in place of session cost per reply. Rows with steady multiples still compare on `m`, which already leaves the one-time work out.
- OR-4. A row's position is `1 + (number of rows ranked above it)`, allowing ties. A lone passed, ranked row takes position 1, and positions show the rung's count of systems run. Amendment of 2026-11-15 (Q29): on rungs where only one system has run, position 1 renders as an outline rather than filled paper with "only system run on this model" (also on share cards, replacing "position 1 of 1") without altering `board.json`. Amendment of 2026-11-17 (Q49): on the ladder and Scale page, the outline square stands alone while "only system run on this model" moves to hover title and screen-reader text. Amendment of 2026-11-23 (Q54): on the ladder no square prints its count; a screen reader hears it ("1 of 3"), and the eye counts the rows under the model's divider. A share card keeps "position N of M".
- OR-5. Within each rung, ranked rows appear first, followed by passed-but-unranked rows (alphabetical), followed by rows that have not passed (alphabetical, displaying checks and figures with no position).
- OR-6 (amended 2026-11-13, Q19; 2026-11-15, SI-4a; 2026-11-23, Q54). The frontier is the largest rung holding a passed row whose publisher records Level 1's statement (SI-4a). `board.json` records the frontier rung, position-1 rows (or all passed rows if unranked), and `systems_run`. The overview badges that rung's section rather than duplicating its rows in a separate hero block (OR-4, SI-8). Amendment of 2026-11-23 (Q54): the badge is withdrawn. The ladder runs largest model first, so the largest model with a passed row is seen, not told; `board.json` still records the frontier and the Checks page keeps its rule.

### Adapter contract amendment (RFC-0005)

- AD-1. `verify` receives the 512-token prompt and 512-token claimed reply; adapters MUST configure upstream ranges to verify every reply token (FlashProve: `r = P − 1`, `e = P + R − 1`).
- AD-2. Optional `logprobs` subcommand: accepts tokenized KL `texts` and writes per-text full next-token log-probability matrices for the scored second half of each chunk (`row r` predicting token `n_ctx/2 + r + 1`, shape `positions × vocab`, little-endian `float16`) under `/io/logprobs/` for FI-7. Adapters without it remain valid.
- AD-3. Under exact match, replies MUST be the committed model's own greedy output (RFC-0017 TASK-3), generated by upstream's pinned tools; otherwise RUN is `undecided` (`system limit`).
- AD-4. Generation marks: adapters that run reply generation in a separate phase atomically rename empty files to `/io/marks/generation.start` and `/io/marks/generation.end`, timed by the release watcher like proof releases (CO-3).
- AD-5. Optional `perturb` subcommand (CPU-only): takes a model directory and the level's perturbation spec, writes `W′` to `/io/perturbed/`, and logs tensor, index, old/new stored values, and upstream weight digests for `W` and `W′` where available.
- AD-6. Optional `mutate_reply` subcommand for verifiers that read the reply directly from the proof rather than taking a separate claimed reply (SASH): alters a single reply token inside a proof directory (and any paired fields) while keeping all other bytes identical, deciding nothing itself. C1 verifies the mutated proof and counts only when upstream rejects it while accepting the honest twin (adapter-decided trials are `void`). Omitting `mutate_reply` leaves REPLY `undecided` (`system limit`).
- AD-7. Optional `score` subcommand (amended 2026-11-13, used only for FI-10 to FI-13): reads `requests_file` (per-line JSON with `prompt` and `reply` token IDs), `out_dir`, and `top_k`, writing per-request `<i>.json` (`top` tokens under FI-10 alignment, or `failed` with upstream's error) and (for `top_k > 0`) binary `<i>.topk` (`TFK1` magic, uint32 `positions` and `k`, then row-major little-endian int32 IDs and float32 nat log-probabilities sorted highest-first with lower ID breaking ties). Wraps documented upstream code only (AGENTS.md rule 1), proves nothing, and decides nothing; adapters without it remain valid and print "not measured".

### Levels

- LV-1. Frozen levels never change: rule changes require a new level file (`L2`), while releases under a level add runs without changing rules.
- LV-2. Every rung uses open weights released by the organisation that trained the model, chosen by the level (never by an entrant) and restricted to models whose context fits the request (GPT-2 is exactly 1,024 tokens). Level 1's rungs, largest first: Llama 4 Maverick, Llama 3.1 8B, and GPT-2.
- LV-3. Level 2 draft (published alongside Level 1 so teams can prepare): a 100-bit soundness floor recomputed by a third party from executed parameters, a KL bound over the proved computation added to the fidelity gate, and post-serving reply selection.

### Failure modes

| Failure | Response |
|---|---|
| Counted run references a different level digest | `release freeze` rejects it |
| Slot has no complete session | RUN is `undecided` (`not run`) under five attempts, `failed` at five |
| System deliberately refuses the request (SE-5) | RUN is `failed` immediately with refusal record; no further attempts in that slot |
| Session has fewer than 4 release groups | no steady state (`too few groups`); row prints session cost |
| Baseline ladder fails at a concurrency | that concurrency records failed; full load picks from remaining rungs, or rung has no multiple if none succeed |
| Fidelity control fails to run | omitted from bar selection and displayed as failed |
| Missing trace file for a counted verdict | VERIFY WITHOUT WEIGHTS is `undecided` (`not run`) |
| Missing, non-`properties/2`, or commit-mismatched properties file, or missing run commit | statement petal is hollow (`not_read`, GL-3); `release freeze` rejects the release (GL-9) |
| Formally verified stated above red with no matching proof build (wrong commit/theorem/toolchain, or null toolchain) | hollow (`proof_build_not_run`, MC-5) |
| Recorded proof build failed (including Lean panic/abort), exited non-zero, or reported undeclared axioms | Formally verified is red (`check_failed`, MC-4) |
| Recorded proof build hit timeout or received SIGKILL/SIGTERM (including OOM) | hollow (`proof_build_not_run`) with cause printed (MC-4a) |
| Teacher-forced control pass fails or is unbuilt | printed with cause and excluded from tests (FI-11) |
| System code declines a reference reply (FI-13) | prompt scores 0, listed with cause, stays in `n`; KL covers answering prompts |
| `score` fails for another reason or adapter lacks `score` | row prints "not measured" with cause; partial runs are not scored |
| Beacon relays disagree | `level beacon` fails; no prompt set is generated |

## Alternatives Considered

- **Defer all ranking until two systems share a verifier** (red-team revision 3). Conservative, but prevents any row from holding a position in Level 1; rejected by the owner on 2026-11-10.
- **Rank across rungs by cost multiple.** Tempting since multiples normalize out baseline serving cost, but rejected because a 400B MoE model and a dense 8B model have very different serving costs and proving scaling curves, confounding model effects with prover efficiency.
- **Keep RFC-0016's documentation glyph.** Rejected by the owner on 2026-11-10 because readers interpret coloured cells as tested facts.
- **Use different request shapes per rung (e.g., 512 + 64 on Maverick).** Retained strictly as a fallback if probes proved 512 + 512 infeasible, since varying request shapes would change the meaning of multiples across rungs.
- **Gate Level 1 on KL divergence.** Rejected for Level 1 because FI-7 runs outside the proved computation; KL is displayed non-gating while Level 2 plans to bind it to proved computation.
- **Enforce a hard security floor immediately.** Rejected for Level 1 because black-box checks cannot distinguish 60-bit from 128-bit bounds and publisher claims are not comparable without recomputation. OR-2 requires a stated level while Level 2 announces the floor; Integrity's exponent thresholds (UF-5 to UF-8) set non-ranking petal steps only (GL-4).
- **Retain the "Any model" petal.** Rejected (Q6) because system pages already state which model each row targets.
- **Compute a single benchmark-assigned bits figure.** Rejected (Q9) because interpreting security proofs into a single number is out-of-scope certification (RFC-0002 INV-CLAIM-2, §Alternatives) and conventions vary by tens of bits depending on query budgets; publisher expressions are quoted directly.
- **Colour Formally verified purely from publisher documentation.** Rejected (Q10) because the only system currently claiming formal verification is built by the maker of the AI model that helped draft these rules; keeping the petal hollow until a verified build runs (MC-5) prevents unverified self-grading.

## Drawbacks

- At launch, each rung contains only one system; the site shows system counts (or outline lone-row markers) beside every position.
- At 15 replies on the 8B rung, the fidelity gate is coarse (its bar is `Q3_K_S` at 1.4 mean matched tokens), catching only severe degradation. Neither launch row has FI-7 KL (SASH weights do not load in `llama.cpp`, and Maverick lacks a `llama.cpp` 16-bit base under FI-9), while FI-10 and FI-12 run on unproved upstream code and do not gate (clarified 2026-11-15).
- Black-box checks cannot distinguish a cryptographic proof from a plain signature; the site states clearly what is not tested.
- At drafting time, 512 + 512 had not yet run on either system at its pin (see RISK below).
- Statement petals depend on reviewer-transcribed facts; every fact carries a pinned quote, link, and reading note where applicable so errors are auditable.
- Because only FlashProve currently states a machine-checked proof, Formally verified rises above Not met on a single row (backed by one full check we ran, Q43), offering limited differentiation at launch.
- Maverick's fidelity run uses batching (vLLM batches all prompts in one call for reference/rerun, and `llama.cpp` ran quantized controls at 16 slots), keeping Maverick rows below green on the Fidelity petal (FM-5) until single-slot fidelity runs are completed (fixed on 2026-11-15 so the board no longer copied vLLM's CLI `slots: 1` argument).

RISK: FlashProve's native window is 1,024 tokens and its exact-match full-reply runs at the pin were scripted rather than run through released binaries (`integrations/LIMITS.md` L110 to L119), and SASH had never run 512 + 512. Plan: execute the `docs/runbooks/level-1.md` probes first and consult the owner on the fallback if either system cannot run the request.

## Testing Strategy

- `test_derive.py`: release-group steady calculation against the fixture (`7.128`), and rejection of uneven later groups.

- `test_further_reply.py` (CO-9): pooled cost against a hand-computed case with unequal replies, the further reply from `prove.start`, the one-time work with and without a setup and its mark (`ceil(19 × 70 / 42) = 32`), the split by AD-4 marks and by adapter phases with the 1 % check refused at 9 %, both multiples, the proved rate over served, the setup record's digest, OR-3's fallback reordering two rows, and v1.0's stored records by CO-9.

- `test_level.py`: `levels/L1.yaml` validation and beacon seed extraction from stored rounds.
- `test_glyph.py`: exhaustive branch coverage of UF-1 to UF-9, MC-1 to MC-6, WH-1 to WH-6, FM-1 to FM-7, and NT-1 to NT-6 (including strict `<` at 80 and 100), `system.yaml`/workload lookup for granularity and batch size, offline expression-vs-term checks, mismatched proof-build toolchains, missing run commits, threshold/test mismatch guards, and real `systems/flashprove` and `systems/sash` properties files.
